# Database / DBMS / RDB / Relational Model

<callout icon="📍" color="gray_bg">
**학습 범위**: Database · 1/7 · 데이터베이스와 관계 모델

데이터를 보관하는 대상과 관리하는 소프트웨어를 구분하고, 관계 모델의 의미에서 실제 DB 요청이 처리되는 흐름까지 살펴본다. SQL 예시는 PostgreSQL 18 기준이다.
</callout>

<table-of-contents />

## 1. 학습 목표

- Database, DBMS, RDB, RDBMS, SQL을 구분하여 설명한다.
- 파일 저장만으로 부족해지는 상황을 중복·제약·동시 접근·복구 관점에서 설명한다.
- 관계, 튜플, 속성, 도메인과 관계 연산의 의미를 구체적인 데이터로 설명한다.
- 논리적인 구조와 물리적인 접근 방법이 다른 이유를 이해한다.
- DB 연결부터 SQL 실행, 결과 수신까지의 단계를 나누어 장애를 조사한다.

## 2. 이 주제를 왜 배우는가

처음 만든 할 일 앱은 배열을 JSON 파일로 저장해도 잘 동작한다. 하지만 여러 사용자가 동시에 저장하거나, 같은 회원 정보를 주문 파일과 배송 파일에 각각 보관하기 시작하면 어려움이 생긴다. 한 파일만 바뀌어 이메일이 달라지거나, 두 요청이 서로의 변경을 덮어쓰거나, 저장 중 프로그램이 멈춰 일부만 기록될 수 있다.

DBMS는 이런 공통 문제를 관리하기 위한 기반이다. 다만 DBMS를 도입했다고 데이터의 의미와 업무 규칙까지 자동으로 정해지지는 않는다. 먼저 무엇을 보관하고 어떤 규칙을 지킬지 표현하고, 그 위에서 관리 시스템이 제공하는 기능을 사용해야 한다.

이번 페이지는 그 출발점이다. 테이블과 키를 구체적으로 설계하기 전에 **데이터의 모델, 데이터를 다루는 언어, 그 언어를 실행하는 프로그램**을 분리해서 이해한다.

## 3. 핵심 용어와 관계 모델

### 데이터와 관리 프로그램을 구분한다

| 용어 | 의미 | 쇼핑몰에 대입한 예 |
| --- | --- | --- |
| Database, DB | 목적에 맞게 조직하여 보관하는 데이터의 집합 | 회원·상품·주문 데이터와 그 구조 |
| DBMS | 데이터를 정의·조회·변경하고 접근·동시성·복구 등을 관리하는 소프트웨어 | PostgreSQL, MySQL |
| Relational Model | 데이터를 관계와 그 위의 연산·제약으로 표현하는 논리적 모델 | 회원 관계와 주문 관계를 키 값으로 연결 |
| RDB | 관계 모델을 바탕으로 구성한 데이터베이스 | 회원·주문 테이블로 구성한 DB |
| RDBMS | 관계형 데이터베이스를 관리하는 DBMS | PostgreSQL 서버 프로그램 |

실무에서는 “PostgreSQL 데이터베이스를 설치한다”처럼 제품과 데이터를 섞어 말하기도 한다. 학습할 때는 관리 대상인 DB와 관리 주체인 DBMS를 나누어 이해한다. SQL은 데이터를 정의하고 다루는 언어이며 DBMS 자체나 관계 모델과 같은 말이 아니다. [PostgreSQL Concepts](https://www.postgresql.org/docs/18/tutorial-concepts.html)를 참고한다.

### 애플리케이션에서 데이터까지의 흐름

```text
사용자의 주문 요청
    -> 애플리케이션: 주문 규칙과 입력 검증
    -> DB 연결을 통해 SQL 전달
    -> DBMS: SQL 해석, 실행 방법 선택, 제약·동시성 검사
    -> 저장된 데이터와 인덱스에 접근
    -> 결과 또는 오류 반환
    -> 애플리케이션이 사용자에게 응답
```

애플리케이션은 “재고가 부족하면 주문하지 않는다” 같은 업무 규칙을 구현한다. DBMS는 선언한 키와 제약 조건을 검사하고 데이터를 읽고 쓰는 실행을 관리한다. 애플리케이션이 잘못된 SQL을 보내도 DBMS가 모든 업무 의도를 알아서 복구해 주지는 않는다.

### 관계 모델의 relation은 무엇인가

수학적 **관계(relation)** 는 정해진 속성들의 값을 가진 **튜플(tuple)** 의 집합이다. 관계를 표로 나타내면 튜플은 행, 속성(attribute)은 열에 대응한다. 도메인(domain)은 각 속성에 허용되는 값의 범위를 뜻한다. 이름이 비슷한 **relationship**은 회원과 주문 사이의 연관처럼 개체 사이의 연결을 가리킨다.

관계 모델의 핵심은 논리적인 데이터 표현을 물리적인 저장 방식에서 분리하는 것이다. 사용자가 원하는 데이터의 조건을 표현하면 DBMS가 접근 방법을 선택한다. 회원의 저장 위치가 바뀌었다고 애플리케이션이 모든 디스크 주소를 다시 계산하는 구조가 아니다. [Codd의 관계 모델 논문 소개](https://research.ibm.com/publications/a-relational-model-of-data-for-large-shared-data-banks)에서 이 데이터 독립성의 목적을 확인할 수 있다.

다만 **SQL 테이블을 수학적 관계와 완전히 같다고 보면 안 된다.** 수학의 집합에는 같은 튜플이 중복되지 않지만 SQL 테이블과 조회 결과에는 제약이나 `DISTINCT`가 없다면 중복이 있을 수 있다. SQL에는 값이 없거나 알려지지 않았음을 나타내는 `NULL`도 있다. 행을 어떤 순서로 받고 싶다면 `ORDER BY`로 요청해야 한다. PK가 있다고 조회 결과의 순서까지 보장되지는 않는다. [PostgreSQL Table Basics](https://www.postgresql.org/docs/18/ddl-basics.html)를 참고한다.

### 관계를 다루는 기본 연산

| 연산 | 하는 일 | 예 |
| --- | --- | --- |
| 선택(selection) | 조건을 만족하는 행을 고름 | 재고가 1개 이상인 상품 |
| 투영(projection) | 필요한 속성을 고름 | 상품에서 이름과 가격만 확인 |
| 조인(join) | 조건에 맞는 튜플을 결합 | 주문의 회원 ID와 회원의 ID가 같은 행을 연결 |

조인은 값과 조건을 기준으로 데이터를 결합하는 연산이다. FK가 없어도 조인을 작성할 수 있다. FK는 연결된 값이 유효한지를 지키는 제약이며 조인 실행을 대신하는 명령이 아니다.

## 4. 파일을 저장하는 것과 DBMS를 쓰는 것의 차이

### 파일이 문제라기보다 관리 책임을 누가 지는지가 다르다

DBMS도 결국 저장 장치의 파일을 사용할 수 있다. 따라서 “파일은 데이터를 저장하지 못하고 DB만 저장한다”는 구분은 틀리다. 차이는 저장된 값을 찾고, 변경을 조정하고, 규칙을 검사하고, 장애에서 복구하는 책임을 어느 계층이 맡는지에 있다.

회원과 주문을 각각 CSV로 저장한 쇼핑몰을 생각해 보자. 고객센터는 이메일로 회원을 찾고, 배송 담당자는 주소로 주문을 찾으며, 매출 집계는 주문 금액을 합산한다. 요청 종류가 늘 때마다 전체 파일을 읽고 해석하는 코드를 따로 만들면 같은 값의 의미와 규칙이 여러 프로그램으로 흩어지기 쉽다.

| 해결할 문제 | 직접 파일을 관리한다면 | DBMS가 제공할 수 있는 기능 |
| --- | --- | --- |
| 원하는 조건의 데이터 검색 | 파일 파싱과 검색 코드 작성 | 질의 언어와 실행 계획 |
| 잘못된 값의 저장 방지 | 모든 쓰기 경로에서 규칙 검사 | 타입·키·제약 조건 |
| 여러 요청의 동시 변경 | 별도 동기화와 충돌 처리 | 트랜잭션·동시성 제어 |
| 중간 실패 후 상태 복구 | 기록 형식과 복구 로직 설계 | 로그와 복구 기능 |
| 사용자별 접근 제한 | 각 프로그램에서 권한 검사 | 역할과 객체 접근 권한 |

예를 들어 “주문은 존재하는 회원을 참조해야 한다”는 검사를 한 API에만 넣으면 관리 스크립트나 다른 서버가 검사를 빠뜨릴 수 있다. 저장 구조에 같은 규칙을 선언하면 그 DB를 통한 다른 쓰기 경로에도 적용할 수 있다. 반면 “이 고객에게 오늘 특별 할인을 적용할지” 같은 업무 판단은 별도 로직이 필요할 수 있다.

DBMS를 사용하면 설치·운영·자원 사용·접속 관리 비용도 생긴다. 작은 설정 파일을 읽는 문제까지 모두 DBMS로 옮겨야 하는 것은 아니다. 중요한 판단 기준은 데이터의 크기 하나가 아니라 **누가 동시에 바꾸며, 어떤 조회와 무결성·복구 요구가 있는가**다. 파일 기반 관리의 전형적인 한계는 [Database System Concepts 1장](https://db-book.com/slides-dir/PDF-dir/ch1.pdf)에서 설명한다.

## 5. 관계 모델을 값의 집합으로 이해하기

### 구조와 현재 내용은 다르다

`members(id, name, city)`라는 구조를 정의했다고 하자. 속성의 이름과 타입, 허용할 제약은 **스키마(schema)** 에 속하고, 지금 들어 있는 회원 세 명의 값은 특정 시점의 **인스턴스(instance)** 에 속한다.

```text
스키마: members(id, name, city)

현재 인스턴스:
(1, '하나', '서울')
(2, '준',   '부산')
(3, '서윤', '서울')
```

내일 회원이 네 명이 되어도 스키마가 반드시 바뀌는 것은 아니다. 반대로 `joined_at` 속성을 새로 도입하면 행 수가 그대로여도 구조는 바뀐다. “DB가 바뀌었다”는 표현을 볼 때 데이터 변경인지 구조 변경인지 구분해야 하는 이유다.

속성 값의 도메인은 타입과 연결되지만 업무 의미까지 포함해서 생각해야 한다. 정수 타입인 `age`와 `stock`은 저장 형식이 같아도 의미가 다르다. 음수 재고를 허용할지, 나이를 직접 보관할지 등은 모델링에서 결정할 사항이다.

### relation과 relationship을 혼동하지 않는다

관계 모델의 relation은 튜플의 집합을 뜻한다. 여러 테이블 사이에 FK 선이 있어야만 relation이 되는 것은 아니다. 회원 테이블 하나도 회원에 관한 관계를 표현한다. 반면 “회원이 주문한다”는 연결은 개체 사이의 relationship이다.

이 구분은 관계형이라는 이름을 “테이블끼리 연결되어 있다”는 특징 하나로 줄이지 않게 해 준다. 관계 모델은 데이터를 표현하는 방식뿐 아니라 그 표현 위에서 결과를 계산하는 연산과 유효한 상태를 제한하는 규칙을 함께 생각한다. DBMS가 연결 선을 화면에 보여 주는지와도 별개다.

### 행의 순서와 열의 의미

회원 관계에서 `(1, '하나', '서울')`과 다른 회원의 표시 순서를 바꾸어도 표현하는 회원 사실은 같다. SQL 조회의 표시 순서는 `ORDER BY`로 요청한다. 기본 키를 작은 숫자부터 넣었다는 사실이나 이전 실행에서 같은 순서가 나왔다는 사실은 계약이 아니다.

속성은 이름과 의미로 식별한다. SQL 테이블과 결과에는 열의 표시 순서가 있지만, 애플리케이션이 그 순서에 과도하게 의존하면 열 추가나 조회 목록 변경에 취약해진다. 필요한 열을 명시하는 습관은 데이터 계약을 더 분명히 한다. 스키마·인스턴스·순서의 구분은 [Database System Concepts 2장](https://db-book.com/slides-dir/PDF-dir/ch2.pdf)의 관계 모델 설명을 참고한다.

## 6. 관계 연산을 실제 데이터로 따라가기

다음 두 표를 생각해 보자. 회원 2는 아직 주문이 없고, 회원 1은 두 번 주문했다.

| `members.id` | name |
| --- | --- |
| 1 | 하나 |
| 2 | 준 |

| `purchases.id` | member_id | amount |
| --- | --- | --- |
| 100 | 1 | 30000 |
| 101 | 1 | 50000 |

**선택**은 `amount >= 40000`을 만족하는 주문 101을 고르는 일이다. **투영**은 주문의 모든 속성 중 `id`, `amount`만 남기는 일이다. SQL의 `SELECT`라는 단어가 이론의 선택 연산 하나만 뜻하는 것은 아니다. SQL에서는 조회 전체를 표현하며, 행 조건은 보통 `WHERE`, 출력할 열은 선택 목록으로 나타낸다.

**조인**은 회원 ID가 같은 조합을 연결한다. 위 데이터의 내부 조인 결과는 두 행이다. 하나의 회원 행이 주문 두 건과 각각 연결되기 때문이다. 회원 이름이 두 번 보인다고 DB가 중복 저장된 회원을 만들어 냈다고 단정하면 안 된다. **조회 결과의 한 행이 무엇을 나타내는지**를 다시 살펴야 한다.

```text
(100, '하나', 30000)
(101, '하나', 50000)
```

일반적인 내부 조인은 조건에 맞는 조합만 남기므로 주문이 없는 회원 2는 이 결과에 나타나지 않는다. 모든 회원을 남길지 여부는 조회 의미에 따라 정할 일이다. FK가 있으면 참조 값의 유효성을 검사할 수 있지만 어떤 회원을 결과에 남길지까지 대신 정해 주지는 않는다.

관계 연산의 결과도 다시 표 형태로 다룰 수 있어서 결과에 필터를 추가하거나 다른 관계와 결합할 수 있다. 이 조합 가능성 덕분에 저장된 테이블마다 전용 검색 프로그램을 새로 작성하지 않고도 여러 질문을 표현할 수 있다. SQL 조회의 구성은 [PostgreSQL Query Overview](https://www.postgresql.org/docs/18/queries-overview.html), 조인의 의미는 [Table Expressions](https://www.postgresql.org/docs/18/queries-table-expressions.html)를 참고한다.

## 7. DBMS 내부의 역할을 나누어 보기

DBMS의 내부 구현은 제품마다 다르지만 SQL이 문자열로 도착한 뒤 결과가 반환되기까지 다음과 같은 책임이 필요하다. 이 표는 이해를 위한 역할 구분이며 실제 프로세스가 정확히 한 칸씩 따로 존재한다는 뜻은 아니다.

| 역할 | 해결하는 질문 | 잘못되었을 때 보일 수 있는 증상 |
| --- | --- | --- |
| 연결·인증·권한 | 누가 어느 DB에 접근하는가 | 연결 거절, 권한 오류 |
| 구문·의미 분석 | 문장이 올바르고 대상 객체가 있는가 | 문법 오류, 없는 테이블 오류 |
| 최적화·실행 계획 | 같은 결과를 어떤 경로로 계산할까 | 과도한 스캔과 조인 비용 |
| 실행 | 선택한 연산을 실제로 수행하는가 | 반환 결과, 실행 중 오류 |
| 저장·버퍼 관리 | 필요한 페이지를 어디에서 읽고 보관할까 | 입출력 대기, 캐시 효과 |
| 무결성·동시성·복구 | 변경을 어떤 규칙으로 확정할까 | 제약 위반, 대기, 복구 작업 |

예를 들어 `SELECT * FROM memberz`는 저장 장치가 느리기 전에 대상 테이블을 찾지 못해 실패할 수 있다. 반면 올바른 회원 조회가 매우 느리다면 전체 행 수, 조건에 맞는 접근 경로, 대기 원인 등을 살핀다. “DB가 안 된다”를 하나의 고장으로 취급하면 원인을 찾기 어렵다.

최적화기는 SQL을 임의의 다른 질문으로 바꾸는 것이 아니다. 같은 의미를 유지하는 여러 접근 방법을 비교한다. 인덱스가 추가되었어도 같은 SQL을 그대로 사용할 수 있는 것은 이런 역할 분리 덕분이다. 내부 실행의 세부 알고리즘은 뒤의 인덱스 페이지에서 다룬다.

## 8. 논리적 표현과 물리적 저장을 분리하는 이유

### 물리적 독립성

회원 테이블이 커져 특정 검색 경로를 추가하거나 저장 장치의 배치를 바꿀 수 있다. 사용자가 `id = 1`인 회원을 원한다는 논리적 질문은 그대로다. 저장 위치를 호출자가 직접 지정하지 않으면 DBMS는 데이터 접근 방식을 바꿀 여지를 갖는다.

이것이 성능 변화까지 없어진다는 뜻은 아니다. 같은 결과를 반환하더라도 읽어야 할 페이지가 늘면 느려질 수 있다. **결과의 의미가 유지되는 것과 실행 비용이 일정한 것은 다르다.** 관계 모델의 데이터 독립성은 구현을 숨겨도 질의를 표현할 수 있게 하는 기반이지, 물리적 비용을 지우는 약속이 아니다.

### 논리 구조 변경의 영향

열을 없애거나 한 테이블을 여러 테이블로 나누는 변경은 애플리케이션의 조회 계약에 영향을 줄 수 있다. 물리적 위치를 숨긴다고 모든 논리적 스키마 변경까지 자동으로 호환되는 것은 아니다. 어떤 뷰나 API를 통해 기존 계약을 유지할지는 별도로 설계한다.

예를 들어 `members.name`을 삭제하고 이름을 다른 방식으로 저장하면 기존 SQL은 실패할 수 있다. 반면 동일한 열을 유지하면서 조회용 인덱스를 추가하는 변경은 보통 SQL의 의미를 바꿀 필요가 없다. 두 변경을 모두 “DB 구조 변경”이라고만 부르면 위험과 검증 범위를 잘못 잡게 된다.

## 9. PostgreSQL에서 DB·스키마·테이블을 구분하기

일반적인 스키마라는 단어 외에 PostgreSQL의 schema는 객체를 묶는 **이름 공간**이라는 구체적인 의미도 가진다.

```text
PostgreSQL 서버가 관리하는 cluster
  -> database: learning
       -> schema: public
            -> table: members
       -> schema: reporting
            -> view 또는 table 등
```

여기서 PostgreSQL의 cluster는 하나의 서버 인스턴스가 관리하는 데이터베이스 집합이라는 용어다. 반드시 여러 장비로 구성된 분산 클러스터를 뜻하지 않는다. 일반적인 연결 하나는 특정 DB를 대상으로 하며, 그 안의 객체는 `public.members`처럼 지정할 수 있다.

같은 DB의 서로 다른 스키마에 같은 테이블 이름을 둘 수 있으므로, “members가 없다”는 오류에는 이름뿐 아니라 접속한 DB와 스키마도 영향을 준다. 파일 경로를 보는 것처럼 이름을 하나씩 해석하면 혼동을 줄일 수 있다. 정확한 계층과 접근 규칙은 [PostgreSQL Schemas](https://www.postgresql.org/docs/18/ddl-schemas.html)를 참고한다.

## 10. 작은 데이터베이스를 만들고 조회하기

다음은 다른 페이지와 분리된 학습용 스키마에서 실행할 수 있는 예다. 예제의 PK·FK는 식별과 연결을 표현하는 최소한의 선언이며 다음 페이지에서 자세히 배운다.

```sql
CREATE SCHEMA db_model_lab;
SET search_path TO db_model_lab;

CREATE TABLE members (
    id integer PRIMARY KEY,
    name text NOT NULL
);

CREATE TABLE purchases (
    id integer PRIMARY KEY,
    member_id integer NOT NULL REFERENCES members(id),
    amount integer NOT NULL CHECK (amount >= 0)
);

INSERT INTO members VALUES (1, '하나'), (2, '준');
INSERT INTO purchases VALUES (100, 1, 30000), (101, 1, 50000);

SELECT p.id, m.name, p.amount
FROM purchases AS p
JOIN members AS m ON m.id = p.member_id
WHERE p.amount >= 40000
ORDER BY p.id;
```

결과는 주문 101, 회원 이름 하나, 금액 50000인 한 행이다. 이 결과를 만들기 위해 DBMS는 지정된 관계들을 결합하고 조건에 맞는 행을 고른다. SQL에 반복문이나 파일의 바이트 위치를 쓰지 않았어도 원하는 결과를 표현할 수 있다.

이 SQL의 표기 순서가 물리적인 실행 순서를 한 단계씩 강제하는 것은 아니다. DBMS는 의미를 유지하면서 필터를 적용할 위치와 접근 방법을 선택할 수 있다. 또한 `SET search_path`는 해당 세션의 이름 해석에 영향을 주므로 새 연결에서 실험한다면 다시 설정하거나 `db_model_lab.members`처럼 명시한다.

## 11. 연결부터 결과까지 실제 요청 흐름

1. 클라이언트는 서버 주소·접속 대상 DB·사용자 정보를 정한다.
2. 서버는 연결과 인증을 처리하고 사용할 세션을 준비한다.
3. 클라이언트가 SQL과 필요한 입력 값을 전달한다.
4. DBMS는 문법·객체·권한을 확인하고 실행 방법을 준비한다.
5. 실행 중 필요한 데이터와 인덱스에 접근하고 관련 규칙을 검사한다.
6. 조회 행이나 변경 결과 또는 오류를 클라이언트로 돌려준다.
7. 클라이언트는 받은 값을 애플리케이션 데이터로 해석해 사용자에게 응답한다.

웹 서비스에서는 HTTP 서버가 DBMS의 클라이언트가 된다. 브라우저가 웹 API의 클라이언트라는 설명과 충돌하지 않는다. 같은 프로그램도 어느 연결을 기준으로 보느냐에 따라 서버와 클라이언트 역할을 함께 가진다. PostgreSQL의 클라이언트/서버 구분은 [Architectural Fundamentals](https://www.postgresql.org/docs/18/tutorial-arch.html)에 설명되어 있다.

연결이 성립했다는 것과 SQL이 성공했다는 것, 애플리케이션이 결과를 모두 받았다는 것은 각각 다른 단계다. 인증 실패에는 아직 조회 결과가 없고, 테이블 이름 오류는 연결 후에 일어날 수 있다. 서버가 응답을 보냈더라도 네트워크 문제로 클라이언트가 끝까지 읽지 못할 수 있다. 프로토콜의 시작과 질의 응답 단계는 [Message Flow](https://www.postgresql.org/docs/18/protocol-flow.html)를 참고한다.

## 12. 흔한 오해와 주의점

### “SQL을 쓰면 모두 완전히 같은 DB다”

SQL을 지원하는 제품도 타입, 함수, 격리 수준 구현과 운영 방식이 다를 수 있다. 개념을 배울 때는 공통된 의미를 먼저 익히고 실행 예제의 제품과 버전을 기록한다. PostgreSQL이 JSON도 저장할 수 있다는 사실 역시 관계 모델을 사용하지 않는 제품이라는 뜻은 아니다.

### “스프레드시트처럼 보이면 관계형이다”

표 모양만으로는 충분하지 않다. 각 열의 의미, 허용할 값, 식별 규칙과 연산의 의미가 있어야 한다. 화면에 보이는 셀 좌표와 데이터의 논리적인 식별자를 같은 것으로 보지 않는다.

### “DBMS가 있으니 잘못된 데이터는 저장되지 않는다”

선언하지 않은 규칙까지 모두 보장할 수는 없다. 가격 열을 아무 문자열이나 허용하도록 만들고 업무 검증도 생략하면 DBMS 도입 자체가 올바른 가격을 보장하지 않는다. 무엇을 DB 제약으로 표현할지 판단하는 책임이 남는다.

## 13. 보안·성능·운영 관점

**보안**에서는 연결 권한과 데이터 접근 권한을 나눈다. DB에 연결할 수 있다고 모든 테이블을 수정할 수 있어야 하는 것은 아니다. 애플리케이션의 역할에 필요한 범위를 정하고, 외부 입력을 SQL 문장 구조와 혼합하지 않도록 매개변수 바인딩 기능을 사용한다. 구체적인 서버 구현은 이 페이지의 범위를 벗어난다.

**성능**에서는 DBMS가 수행한 계산과 데이터 전달량을 함께 본다. 필요하지 않은 수십 개 열이나 모든 회원을 가져온 뒤 애플리케이션에서 한 명만 고르는 방식은 DB가 빠르게 응답하더라도 전송과 처리 비용을 낭비할 수 있다. 질문을 필요한 범위로 표현하는 것부터 시작한다.

**운영**에서는 접속 위치와 오류 단계를 기록한다. 서버 주소가 맞는지, DB 이름이 맞는지, 어떤 사용자인지, 어느 스키마의 테이블인지 확인하면 다른 환경을 잘못 조회하는 문제를 줄일 수 있다. 문법 오류를 네트워크 튜닝으로 해결하려 하지 말고, 응답을 받기 전 실패인지 실행 중 실패인지부터 구분한다.

## 14. 핵심 정리

<callout icon="✅" color="green_bg">
관계 모델은 데이터를 표현하고 질문하는 논리적 기반이며, DBMS는 그 표현을 실제 저장·접근·변경으로 실행하는 시스템이다.
</callout>

- DB, DBMS, RDB, SQL은 서로 다른 대상을 가리킨다.
- 관계 모델의 relation은 튜플의 집합이며 테이블 사이의 연결만 뜻하지 않는다.
- 스키마는 구조, 인스턴스는 특정 시점의 내용이다.
- SQL은 필요한 결과를 표현하고 DBMS는 그 결과를 계산할 접근 방법을 선택한다.
- 물리적 독립성은 논리적인 질문을 저장 위치와 분리하지만 실행 비용까지 없애지는 않는다.
- 실제 문제는 연결·권한·객체 해석·실행·결과 수신 중 어느 단계인지부터 찾는다.

5. DB 연결은 되지만 테이블이 없다는 오류가 난다. 네트워크 확인 뒤에 어떤 접속 대상과 이름 공간을 확인해야 하며, SQL 성공과 결과 수신은 왜 별개인가?

## 2. 이 주제를 왜 배우는가

주문이 20건일 때는 어떤 방식으로 찾아도 빨라 보일 수 있다. 주문이 수백만 건이 되면 회원 한 명의 최근 20건을 위해 전체 주문을 반복해서 읽는 비용이 커진다. 인덱스는 원하는 범위를 적은 접근으로 찾게 도울 수 있지만, 모든 열에 추가하면 저장과 쓰기 비용도 늘어난다.

이번 페이지에서는 자료구조의 모양을 외우는 데서 멈추지 않는다. 구조가 왜 조회에 유리한지, 어떤 조회에는 도움이 작아지는지, 실제 DBMS가 왜 순차 스캔을 고르는지도 함께 살핀다.

실습은 별도 스키마를 만들고 다음처럼 준비한다. 데이터는 결과를 관찰하기 위한 합성 데이터이며 운영 성능을 대표하지 않는다. 이 페이지에서 제시하는 여러 인덱스는 비교 후보이므로 모두 운영에 추가하라는 뜻이 아니다.

```sql
CREATE SCHEMA db_index_lab;
SET search_path TO db_index_lab;

CREATE TABLE orders (
    id bigint PRIMARY KEY,
    user_id bigint NOT NULL,
    created_at timestamptz NOT NULL,
    status text NOT NULL
);
INSERT INTO orders
SELECT n, (n % 1000) + 1,
       timestamptz '2026-01-01 00:00:00+09' + n * interval '1 minute',
       CASE WHEN n % 100 = 0 THEN 'pending' ELSE 'paid' END
FROM generate_series(1, 50000) AS src(n);
ANALYZE orders;
```

3절의 인덱스를 만들기 전과 후에 같은 EXPLAIN 조회를 실행하면 접근 경로의 차이를 비교할 수 있다. 이미 PK용 인덱스는 있지만 회원별 시각 순서의 인덱스는 아직 없다는 점도 구분한다.

## 3. 인덱스와 B-Tree 계열의 기본 동작

### 인덱스는 데이터를 찾는 별도의 접근 경로다

**인덱스(index)** 는 특정 열의 값 등을 검색하기 좋게 조직한 자료구조다. 인덱스가 없으면 DBMS는 많은 행을 읽어 조건을 검사해야 할 수 있다. 인덱스가 있으면 값의 위치를 좁힌 뒤 필요한 행에 접근할 수 있다.

```sql
CREATE INDEX orders_user_created_idx
    ON orders (user_id, created_at DESC);

SELECT id, created_at
FROM orders
WHERE user_id = 1
ORDER BY created_at DESC
LIMIT 20;
```

이 인덱스는 회원별로 주문을 모으고 그 안에서 생성 시각을 정렬한 접근 경로를 제공한다. DBMS가 이 경로를 사용하면 회원 1의 주문 범위를 찾고 최근 주문부터 읽을 수 있다. 같은 생성 시각의 주문 사이에도 확정된 순서가 필요하다면 별도 정렬 기준을 추가해야 한다.

인덱스는 조회 결과 자체를 캐시한 것과 다르다. 데이터가 바뀌면 DBMS가 관련 인덱스도 관리하며, 인덱스를 만들었다고 모든 쿼리가 반드시 사용하는 것도 아니다. [PostgreSQL Indexes Introduction](https://www.postgresql.org/docs/18/indexes-intro.html)을 참고한다.

### 왜 단순한 이진 탐색 트리보다 넓은 트리를 사용하는가

저장 장치의 데이터를 읽을 때는 보통 행 하나의 필드만 읽기보다 일정 크기의 **페이지(page)** 단위로 접근한다. 트리의 높이가 크면 경로를 따라 여러 페이지에 접근해야 한다. 한 노드에 여러 키와 자식 포인터를 두면 한 번 읽은 페이지로 넓은 범위를 구분할 수 있다.

**B-Tree** 는 여러 자식을 가질 수 있는 균형 탐색 트리다. 키를 정렬해 보관하고 모든 리프가 같은 깊이를 갖도록 유지한다. 자식 수를 뜻하는 **분기 수(fan-out)** 가 크면 많은 데이터를 비교적 낮은 높이로 표현할 수 있다. B-Tree의 B를 binary라는 뜻으로 해석하지 않는다.

균형은 처음 만들 때만 맞추는 것이 아니다. 삽입으로 노드가 가득 차면 분할하고, 삭제로 너무 비면 재분배나 병합 등의 방법으로 구조를 유지한다. 페이지 접근 횟수에는 캐시 상태도 영향을 주므로 트리 높이가 곧 매번 발생하는 디스크 읽기 횟수는 아니다. 균형 다진 트리의 기본 성질은 [PostgreSQL B-Tree 문서](https://www.postgresql.org/docs/18/btree.html)에 설명되어 있다.

### B-Tree와 B+Tree의 구조 차이

교과서에서 둘을 구분할 때 사용하는 일반적인 구조는 다음과 같다. 제품 문서에서 B-Tree라고 부르는 이름은 더 넓은 계열을 가리킬 수 있다.

| 기준 | 일반적인 B-Tree | 일반적인 B+Tree |
| --- | --- | --- |
| 실제 데이터 항목 또는 행 참조 | 내부 노드와 리프에 둘 수 있음 | 리프에 모음 |
| 내부 노드의 주된 역할 | 검색 분기와 데이터 항목 보관 | 분리 키와 자식 포인터로 검색 안내 |
| 단일 키 탐색 | 내부 노드에서 끝날 수 있음 | 리프까지 내려감 |
| 범위 탐색 | 트리 순회로 진행 | 시작 리프를 찾고 연결된 리프를 따라 진행 |
| 내부 노드의 공간 사용 | 데이터 항목의 크기도 영향 | 비교적 많은 분기 정보를 담기 유리 |

아래는 B+Tree의 검색 경로를 설명하기 위한 그림이다. 숫자는 키이며 실제 노드의 최대 수용량을 나타내지는 않는다.

```text
                    [20 | 40]              내부 노드
                   /    |    \
          [5, 10] <-> [20, 25, 30] <-> [40, 50]    리프
             |             |              |
          행 참조들     행 참조들      행 참조들
```

`25`를 찾을 때 내부 노드에서 중간 자식으로 이동하고 리프의 항목을 찾는다. `25 이상 45 이하`를 찾을 때는 시작 위치부터 `25, 30`을 읽고 다음 리프로 이동해 `40`을 읽은 뒤 범위를 벗어나는 `50` 앞에서 멈춘다. 매 키마다 루트에서 다시 시작할 필요가 없다.

**리프에 데이터가 있다는 말이 테이블의 전체 행을 항상 복사한다는 뜻은 아니다.** 행이 저장된 위치를 가리키는 값일 수도 있다. CMU의 교육용 DBMS도 내부 페이지에는 분기 정보, 리프에는 키와 레코드 ID를 두도록 설명한다. [CMU B+Tree 프로젝트 명세](https://15445.courses.cs.cmu.edu/spring2025/project2/)를 참고한다.

PostgreSQL의 `btree` 역시 내부 페이지로 다음 레벨을 찾고, 리프의 항목이 테이블 행을 가리킨다. 공식 명칭이 B-Tree라는 이유만으로 위 표의 고전적인 B-Tree 구조를 그대로 대입하지 않는다. PostgreSQL에서는 인덱스와 테이블의 주 데이터 영역이 분리되어 있다. [B-Tree 구현 구조](https://www.postgresql.org/docs/18/btree.html#BTREE-STRUCTURE), [Index-Only Scans](https://www.postgresql.org/docs/18/indexes-index-only-scans.html)를 참고한다.

### 어떤 조회에서 도움이 되는가

정렬 가능한 키를 사용하는 B-Tree 계열은 동등 비교와 범위 비교에 적합하다. 조건에 맞으면 정렬된 결과를 읽는 데도 활용할 수 있다. 하지만 전체 검색 비용에는 일치한 인덱스 항목과 실제 행을 읽는 비용도 포함된다. 인덱스가 있어도 결과가 수십만 행이면 그 행을 읽고 전달하는 비용이 사라지지 않는다. [PostgreSQL Index Types](https://www.postgresql.org/docs/18/indexes-types.html)를 참고한다.

| 조회 조건 | 검토할 점 |
| --- | --- |
| `id = 10` | 적은 수의 행을 찾으면 효과적일 가능성이 큼 |
| `created_at`의 기간 범위 | 범위의 시작을 찾고 연속된 항목을 읽을 수 있음 |
| 회원별 최근 주문 20개 | 복합 키 순서와 정렬·제한 조건을 함께 검토 |
| 대부분의 행을 반환 | 인덱스를 거쳐 행을 찾는 것보다 순차 스캔이 유리할 수 있음 |
| 열에 함수를 적용한 조건 | 원래 열의 인덱스와 조건식이 맞는지 별도 확인 |

### 복합 인덱스는 열의 순서가 중요하다

`(user_id, created_at)`는 회원 ID 순서로 먼저 묶고 같은 회원 안에서 시각 순서로 정렬한다. 따라서 `user_id = 1`을 먼저 고정한 최근 주문 조회와 잘 맞는다. `created_at` 조건만 있는 조회가 같은 비용으로 동작한다고 가정하면 안 된다.

그렇다고 선두 열 조건이 없으면 절대 사용할 수 없다는 규칙도 아니다. PostgreSQL 18에는 데이터 분포에 따라 뒤쪽 열 조건을 활용하는 skip scan 같은 최적화가 있다. 우선 실제 쿼리의 조건과 정렬 순서에 맞춰 설계하고 실행 계획으로 확인한다. [PostgreSQL Multicolumn Indexes](https://www.postgresql.org/docs/18/indexes-multicolumn.html)를 참고한다.

### 인덱스의 장점에는 비용이 따른다

| 이득 | 함께 생기는 비용·한계 |
| --- | --- |
| 필요한 행의 검색 범위를 줄임 | 인덱스 저장 공간과 캐시 공간 사용 |
| 조인·정렬·제한 조회를 도울 수 있음 | 삽입·삭제·관련 갱신 시 인덱스 유지 작업 |
| 유일 인덱스로 중복 금지 구현 가능 | 키 비교와 동시성 처리 비용 |
| 적은 페이지 접근으로 조회 가능 | 페이지 분할과 구조 유지 비용 |

이메일처럼 서로 다른 값이 많고 소수 행을 찾는 조건은 좋은 후보가 될 수 있다. 상태가 두 종류뿐이고 그중 하나가 전체의 90%를 차지한다면 그 상태의 모든 행을 찾는 데는 효과가 작을 수 있다. **값 종류의 수, 실제 분포, 조회할 비율, 정렬·LIMIT 조건을 함께 본다.** “카디널리티가 낮으면 인덱스는 무조건 쓸모없다”로 외우지 않는다.

PK·유일성 제약과 일반 조회용 인덱스도 구분한다. PostgreSQL은 PK와 `UNIQUE`를 위해 유일 인덱스를 만들지만, FK를 선언했다고 참조하는 쪽 열의 인덱스를 자동으로 만들지는 않는다. [제약 조건과 인덱스](https://www.postgresql.org/docs/18/ddl-constraints.html#DDL-CONSTRAINTS-FK)를 참고한다.

### 실행 계획으로 가설을 확인한다

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, created_at
FROM orders
WHERE user_id = 1
ORDER BY created_at DESC
LIMIT 20;
```

`EXPLAIN`은 DBMS가 선택한 실행 계획을 보여 준다. `ANALYZE`를 붙이면 실제로 쿼리를 실행해 행 수와 시간 등을 측정하고, `BUFFERS`는 버퍼 접근 정보를 더한다. `Seq Scan`은 순차 스캔, `Index Scan`은 인덱스를 이용한 접근을 뜻한다.

확인할 것은 인덱스 사용 여부 하나가 아니다. 예상 행 수와 실제 행 수의 차이, 읽은 데이터의 양, 정렬 유무, 전체 시간을 함께 본다. 학습용 테이블의 행이 몇 개뿐이면 순차 스캔이 자연스러운 선택일 수 있다. `EXPLAIN ANALYZE`는 쓰기 쿼리도 실제 실행하므로 단순한 계획 조회와 구분한다. [PostgreSQL Using EXPLAIN](https://www.postgresql.org/docs/18/using-explain.html)을 참고한다.

## 4. 한 노드에 여러 키를 넣는 이유를 계산하기

### 높이가 낮으면 필요한 경로도 짧아진다

이진 탐색 트리는 한 분기에서 두 방향 중 하나를 선택한다. 반면 B-Tree 계열은 한 페이지에 여러 분리 키를 넣어 많은 자식 범위 중 하나를 선택한다. 한 페이지를 읽어 얻는 분기 정보가 많으면 루트에서 리프까지의 레벨 수를 줄이기 쉽다.

가령 내부 노드가 평균적으로 100개의 자식을 가리킨다고 단순화하면, 한 번 내려갈 때 후보 범위를 약 100분의 1로 좁힐 수 있다. 이는 정확한 실제 페이지 수 계산이 아니라 높은 fan-out의 효과를 보여 주는 모델이다. 실제 높이는 키 크기, 페이지 크기, 항목 수, 공간 사용률에 따라 달라진다.

트리 탐색의 높이가 대략 로그 규모라는 설명에도 전제가 있다. 정렬이 유지되고 높이 균형을 관리해야 하며, 원하는 키를 찾은 뒤 일치하는 항목과 행을 읽는 비용은 별도로 발생한다. 수백만 행을 반환하는 질의 전체를 “인덱스니까 O(log N)”이라고 말하면 출력 비용을 빠뜨린다.

### 큰 키는 한 페이지의 분기 수에 영향을 준다

같은 페이지 크기라도 짧은 정수 키와 긴 복합 문자열 키가 차지하는 공간은 다르다. 인덱스 항목이 커지면 한 페이지에 담을 수 있는 항목 수가 줄고 전체 인덱스가 커질 수 있다. 캐시에 보관할 수 있는 유용한 범위도 달라진다.

따라서 어떤 열을 인덱스에 추가할지는 “열 하나 더 있으면 더 많이 찾을 수 있다”만으로 결정하지 않는다. 실제 검색 키인지, 출력용 부가 값인지, 넓은 값을 반복 보관해야 하는지 구분한다. 저장 단위와 분기·리프 페이지의 구분은 [CMU B+Tree 명세](https://15445.courses.cs.cmu.edu/spring2025/project2/)를 참고한다.

## 5. 삽입과 삭제에서 균형을 유지하기

### 삽입은 위치 탐색 뒤에 공간 확보가 필요하다

설명용 B+Tree에서 리프 하나가 키 세 개까지 담는다고 하자. `[10, 20, 30]`에 25를 삽입하면 네 항목이 되어 수용량을 넘는다. 가능한 단순화된 분할 결과는 다음과 같다.

```text
삽입 전:  [10, 20, 30]
삽입 후:  [10, 20] <-> [25, 30]
상위 노드에는 오른쪽 범위가 25부터 시작함을 안내할 분리 키와 포인터 추가
```

B+Tree에서는 분리 키가 위로 복사되어 탐색을 안내할 수 있어도 실제 데이터 항목은 리프에 남는다. 부모도 가득 차면 부모의 분할이 이어질 수 있고, 루트를 분할하면 새 루트가 생겨 높이가 한 단계 늘어날 수 있다.

이 설명은 분할의 목적을 보여 주는 예다. 실제 제품의 공간 정책·중복 키 처리·동시 삽입 알고리즘을 그대로 재현한 것은 아니다. “INSERT는 리프의 빈칸에 값 하나를 쓴다”는 설명만으로는 페이지 분할과 상위 갱신 비용을 설명할 수 없다는 점이 핵심이다. PostgreSQL의 분할 전파는 [B-Tree Structure](https://www.postgresql.org/docs/18/btree.html#BTREE-STRUCTURE)에 정리되어 있다.

### 삭제는 모든 제품에서 즉시 같은 병합을 수행하지 않는다

교과서의 균형 트리는 삭제로 항목이 너무 적어지면 이웃에서 재분배하거나 노드를 병합하고 부모의 분기 정보도 조정한다. 하지만 DBMS는 여러 버전의 행과 동시 접근을 함께 관리하므로 SQL DELETE 한 번이 곧바로 이 도식의 물리적 병합 한 번이라는 뜻은 아니다.

PostgreSQL의 인덱스 항목 정리와 페이지 관리는 MVCC와 연결되어 있다. 이 페이지에서는 일반 자료구조의 삭제 규칙과 제품의 실제 정리 시점을 구분한다. 트리의 논리적인 검색 범위가 맞는지, 공간을 언제 회수하는지는 관련되지만 서로 다른 질문이다.

## 6. 범위 조회에서 절약되는 것과 남는 비용

회원 1의 최근 주문 20건을 찾는 과정을 나누면 다음과 같다.

1. 루트에서 회원 1의 키 범위로 내려간다.
2. 해당 리프의 시작 위치에서 시각 순서에 맞는 항목을 읽는다.
3. 필요한 원본 행 또는 인덱스에 있는 출력 값을 가져온다.
4. 20건을 충족하면 더 읽지 않고 멈출 수 있다.

이 경로가 유리한 이유는 전체를 정렬한 뒤 20건을 고르는 작업을 피할 수 있기 때문이다. 그러나 조건에 맞는 범위가 넓고 결과도 많으면 리프뿐 아니라 원본 행의 여러 페이지에 접근해야 할 수 있다. 이때 순차 읽기와 한 번의 정렬이 더 유리할 수도 있다.

`ORDER BY` 없이 인덱스를 쓰는 것만으로 애플리케이션의 표시 순서를 보장하지 않는다. 반환 순서를 계약으로 요구한다면 SQL에 표현해야 한다. 같은 시각의 행 사이에도 안정적인 순서가 필요하면 ID 같은 추가 기준을 정하고 인덱스 후보에도 반영한다. [Indexes and ORDER BY](https://www.postgresql.org/docs/18/indexes-ordering.html)를 참고한다.

## 7. 리프가 실제 행을 보관하는가, 행을 찾아가는가

“B+Tree의 리프에 데이터가 있다”는 설명에서 데이터의 의미는 구현에 따라 다르다. 테이블의 전체 행일 수도 있고, 다른 곳의 행을 찾기 위한 참조일 수도 있다. 이 차이가 한 번의 검색 뒤에 필요한 추가 접근을 바꾼다.

PostgreSQL의 일반 테이블은 주 데이터 영역인 heap과 인덱스가 분리되어 있다. 보통 인덱스에서 행의 위치를 찾고 heap의 행에 접근한다. 따라서 인덱스 항목을 찾았다고 필요한 모든 출력 열을 이미 읽은 것은 아니다.

반면 MySQL InnoDB의 clustered index에는 행 데이터가 함께 조직되고, secondary index 항목에는 해당 행의 PK가 포함된다. secondary index에서 찾은 뒤 clustered index를 통해 행에 접근할 수 있다. 같은 “PK 조회”, “보조 인덱스 조회”라도 제품의 저장 방식에 따라 경로가 달라진다. [PostgreSQL Index-Only Scans](https://www.postgresql.org/docs/18/indexes-index-only-scans.html), [InnoDB Clustered and Secondary Indexes](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html)를 참고한다.

이 구분 때문에 다른 제품에서 읽은 “PK 순서가 곧 테이블 저장 구조다”라는 설명을 PostgreSQL의 모든 테이블에 그대로 적용하면 안 된다. 자료구조의 공통 원리와 저장 엔진의 구현 계약을 구분한다.

## 8. 복합 인덱스를 사전식 순서로 읽기

`(user_id, created_at)`의 순서는 사전에서 성을 먼저 보고 같은 성 안에서 이름을 보는 방식과 비슷하다. 첫 열이 같은 범위 안에서 다음 열의 정렬이 의미를 가진다.

```text
(1, 10:00)
(1, 09:00)
(2, 11:00)
(2, 08:00)
```

시각이 전체적으로 11:00, 10:00, 09:00, 08:00 순으로 배열된 것은 아니다. 회원 조건이 없는 전체 최신 주문에는 회원별 최신 주문과 다른 인덱스가 더 알맞을 수 있다.

선두 열에 동등 조건을 주고 다음 열에 범위 조건을 주는 패턴은 검색 범위를 좁히기 쉽다. 범위 뒤쪽 열의 조건은 인덱스에서 검사할 수 있어도 스캔해야 할 구간 자체를 같은 정도로 줄여 주지 않을 수 있다. 실제 최적화에는 예외가 있으므로 “조건이 하나 빠지면 절대 못 쓴다” 같은 절대 규칙보다 정렬 구조와 실행 계획을 함께 읽는다.

복합 인덱스 하나와 각 열의 단일 인덱스 두 개도 같지 않다. 두 인덱스를 조합하는 계획이 가능해도 정렬된 하나의 연속 구간을 읽는 비용과 동일하다는 보장은 없다. 공통 원칙과 skip scan의 적용 조건은 [Multicolumn Indexes](https://www.postgresql.org/docs/18/indexes-multicolumn.html)에 설명되어 있다.

## 9. 조건식과 필요한 행의 범위에 맞는 변형

### 식 인덱스

열에 함수를 적용한 결과로 검색하면 원래 열의 정렬과 조건식이 직접 맞지 않을 수 있다. PostgreSQL에는 식의 계산 결과를 인덱스 키로 두는 기능이 있다. 예를 들어 `lower(code)`로 비교하는 조회에 `lower(code)`를 기준으로 한 인덱스를 검토할 수 있다.

이런 인덱스는 조회 때의 계산을 줄일 수 있지만 삽입·관련 갱신 때 식을 계산하고 결과를 유지해야 한다. 모든 함수가 허용되는 것도 아니다. [Indexes on Expressions](https://www.postgresql.org/docs/18/indexes-expressional.html)를 참고한다.

### 부분 인덱스

```sql
CREATE INDEX orders_pending_created_idx
ON orders (created_at DESC)
WHERE status = 'pending';
```

이 인덱스는 pending 주문만 포함한다. 상태가 두 종류뿐이어도 자주 찾는 pending이 전체에서 작은 비중이라면 유용한 후보가 될 수 있다. 반면 paid 조회에는 필요한 항목을 담고 있지 않다. 질의 조건이 인덱스가 포함하는 범위에 맞는지 DBMS가 판단할 수 있어야 한다. [Partial Indexes](https://www.postgresql.org/docs/18/indexes-partial.html)를 참고한다.

### 출력 열을 함께 보관하는 인덱스

```sql
CREATE INDEX orders_user_cover_idx
ON orders (user_id, created_at DESC)
INCLUDE (id);
```

`id`는 여기서 검색 순서의 키가 아니라 출력에 사용할 수 있는 부가 값이다. 필요한 값이 모두 있어도 PostgreSQL은 MVCC 가시성 확인에 따라 heap 접근이 남을 수 있으므로 “INCLUDE를 쓰면 항상 테이블을 전혀 읽지 않는다”고 말하지 않는다.

넓은 출력 값을 많이 포함하면 인덱스가 커진다. 포함할 수 있다는 사실과 포함하는 것이 이득이라는 결론을 구분한다. [Index-Only Scans and Covering Indexes](https://www.postgresql.org/docs/18/indexes-index-only-scans.html)를 참고한다.

## 10. 실행 계획에서 질문할 항목

실험 결과의 숫자는 장비·캐시·통계에 따라 달라진다. 다음 항목을 같은 입력과 조건에서 비교한다.

| 관찰 | 의미와 다음 확인 |
| --- | --- |
| `Index Cond` | 인덱스 탐색에 적용하는 조건 |
| `Filter`와 제거 행 | 찾은 뒤 추가로 거르는 행이 많은지 확인 |
| 예상 `rows`와 실제 `rows` | 분포나 상관관계 추정이 어긋나는지 확인 |
| `Sort` 노드 | 인덱스 순서만으로 요청한 정렬을 충족하는지 확인 |
| `Buffers` | 논리적인 접근과 실제 읽기·캐시 효과를 함께 확인 |
| 전체 실행 시간과 반환량 | 결과 전송 등 다른 비용도 남는지 확인 |

`cost`의 숫자를 그대로 밀리초로 읽지 않는다. 실행 계획의 추정 비용은 플래너의 비교 단위이고 `ANALYZE`의 실제 시간과 다른 값이다. 한 노드가 반복 실행되면 행 수와 `loops`도 함께 봐야 전체 작업량을 해석할 수 있다.

통계가 새 데이터 분포를 충분히 반영하지 못하면 인덱스가 있어도 좋은 계획을 고르기 어려울 수 있다. 그렇다고 느릴 때마다 인덱스 사용을 강제하는 것으로 해결하지 않는다. 원하는 행 수와 실제 읽은 양부터 비교한다. [Using EXPLAIN](https://www.postgresql.org/docs/18/using-explain.html), [Statistics Used by the Planner](https://www.postgresql.org/docs/18/planner-stats.html)를 참고한다.

## 11. 읽기 이득과 쓰기 비용을 같이 측정하기

INSERT는 원본 행뿐 아니라 관련 인덱스도 유지해야 한다. DELETE와 UPDATE 역시 제품의 버전 관리와 인덱스 정리 정책에 따라 추가 작업이 필요하다. 읽기 한 종류를 빠르게 한 인덱스가 모든 쓰기를 더 비싸게 만들 수 있다.

비슷한 복합 인덱스가 여러 개 쌓이면 중복된 선두 키를 반복 보관할 수 있다. 하지만 이름이 비슷하다고 바로 삭제하지 않는다. 유일성 보장에 사용되는지, 다른 정렬이나 부분 조건이 필요한지, 실제 사용되는 조회를 먼저 살핀다.

인덱스 생성 자체도 작업이다. PostgreSQL의 일반 CREATE INDEX는 쓰기와 충돌할 수 있고 큰 테이블에서는 오래 걸릴 수 있다. `CONCURRENTLY` 같은 기능에도 여러 단계와 제약이 있으므로 단어 하나로 “운영 영향 없음”을 보장하지 않는다. [CREATE INDEX](https://www.postgresql.org/docs/18/sql-createindex.html)를 참고한다.

## 12. 흔한 오해와 주의점

- **B-Tree는 이진 트리다**: 여러 키와 여러 자식으로 분기하는 구조다.
- **B+Tree의 모든 키는 리프에만 나온다**: 내부의 분리 키도 탐색을 안내하며 실제 항목이 리프에 모이는 것과 구분한다.
- **인덱스를 찾았으니 전체 비용은 로그 시간이다**: 일치 항목·원본 행·출력량의 비용이 남는다.
- **값 종류가 적은 열은 무조건 의미 없다**: 분포·반환 비율·부분 조건·정렬 제한까지 본다.
- **인덱스 순서가 화면 순서를 보장한다**: 필요한 순서는 SQL의 ORDER BY로 표현한다.
- **Index Scan이면 Seq Scan보다 무조건 좋다**: 전체 비용과 데이터량으로 판단한다.

## 13. 실무에서 검토하는 순서

먼저 느린 조회의 조건과 정렬·반환량을 기록한다. 그다음 테이블 크기와 값의 분포, 실행 계획의 읽기 범위를 확인한다. 이 근거로 키 순서와 범위를 정한 후보를 만들고 같은 조회를 다시 측정한다.

읽기가 빨라졌다면 저장 공간과 쓰기 비용도 살핀다. 테스트 환경에 데이터가 적거나 한 번 실행한 뒤 캐시가 따뜻해졌다는 이유만으로 큰 개선을 단정하지 않는다. 반대로 소량 데이터에서 인덱스가 선택되지 않았다고 설계 원리가 틀린 것은 아니다.

최종적으로 “인덱스를 추가했다”보다 **어떤 요청의 어떤 접근을 줄였으며, 그 대가로 무엇을 유지하는가**를 설명할 수 있어야 한다. 이 설명이 있으면 조회 패턴이 바뀌었을 때 인덱스도 다시 평가할 수 있다.

## 14. 핵심 정리

<callout icon="✅" color="green_bg">
인덱스는 검색할 범위를 줄이는 대신 공간과 유지 작업을 추가한다. B+Tree의 낮은 높이와 리프 순회가 어떤 조회에 이득이 되는지 실행 계획과 함께 설명한다.
</callout>

- 큰 fan-out과 균형이 탐색 경로를 짧게 유지한다.
- B+Tree의 내부 노드는 분기를 안내하고 실제 항목은 리프에 모인다.
- 삽입의 페이지 분할은 부모까지 이어질 수 있다.
- 리프의 실제 값과 행 접근 경로는 저장 엔진에 따라 다르다.
- 복합 키 순서·조건식·정렬·LIMIT·분포가 실제 효율을 좌우한다.
- 실행 계획의 추정과 실제 작업량, 읽기와 쓰기 비용을 함께 평가한다.

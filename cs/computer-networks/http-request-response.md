요청과 응답을 구성하는 부분, 메시지의 경계, 서버와 브라우저가 메시지를 해석하는 흐름을 다룬다. 텍스트 예시는 HTTP/1.1 기준이다.

## 1. 학습 목표

- 요청 줄·상태 줄·헤더·빈 줄·본문을 구분해 읽는다.
- HTTP 메시지의 끝과 TCP 연결의 끝을 구분한다.
- 브라우저·프록시·애플리케이션 서버를 지나는 요청 흐름을 설명한다.
- Network 패널과 로그를 연결해 실패한 단계를 좁힌다.

## 2. 이 주제를 왜 배우는가

HTTP 라이브러리는 URL과 객체를 넘기면 요청을 만들어 주지만, 전송된 메시지가 코드에서 생각한 것과 같다는 보장은 없다. 잘못된 본문 형식, 빠진 헤더, 리다이렉트, 프록시의 응답 등으로 예상과 다른 결과가 생긴다.

실제로 주고받은 메시지를 읽으면 “요청은 보냈다”를 더 구체적으로 설명할 수 있다. 연결이 실패한 것인지, 서버가 요청을 거절한 것인지, 응답 형식을 잘못 해석한 것인지 나누어 볼 수 있다.

## 3. HTTP/1.1 메시지의 큰 구조

```text
시작 줄
헤더 이름: 값
헤더 이름: 값
빈 줄
선택적인 본문
```

요청의 시작 줄은 **요청 줄(request line)**, 응답의 시작 줄은 **상태 줄(status line)** 이다. **헤더 필드**는 대상 호스트, 본문 형식, 메시지 경계처럼 수신자가 처리에 사용할 정보를 담는다. 빈 줄은 헤더 영역이 끝났다는 표시이며 본문은 그 뒤에 온다.

실제 HTTP/1.1 줄 구분은 CRLF 바이트이며 아래 코드 블록은 읽기 쉽게 표현한 것이다. 본문이 없는 메시지도 있다. 본문은 JSON만이 아니라 HTML, 이미지, 압축 데이터 등 임의의 바이트가 될 수 있다.

## 4. 요청 메시지를 한 줄씩 읽기

```http
POST /products HTTP/1.1
Host: shop.example.com
Content-Type: application/json
Accept: application/json
Content-Length: 14

{"name":"pen"}
```

| 부분 | 해석 |
| --- | --- |
| `POST` | 대상에게 데이터 처리를 요청하는 메서드 |
| `/products` | 이 요청의 대상 경로 |
| `HTTP/1.1` | 이 메시지의 프로토콜 버전 |
| `Host` | 대상 호스트, 비기본 포트면 포트도 포함할 수 있음 |
| `Content-Type` | 지금 보낸 본문의 미디어 타입 |
| `Accept` | 받고 싶은 응답의 미디어 타입 |
| `Content-Length` | 이 예시의 본문 길이, 14바이트 |

본문은 ASCII 문자로 정확히 `{"name":"pen"}`이며 끝에 추가 줄바꿈을 포함하지 않는다고 가정한다. UTF-8 한글은 보통 문자 하나가 여러 바이트이므로 문자열 길이와 바이트 수를 혼동하지 않는다. 실무에서는 HTTP 라이브러리가 길이와 전송 형식을 맞추게 한다.

일반적인 원 서버 요청에서는 경로와 쿼리를 요청 대상으로 보낸다. 프래그먼트는 보내지 않는다. 프록시·CONNECT 등 다른 요청 대상 형식도 있으므로 모든 요청 줄을 이 형식 하나로 단정하지 않는다.

## 5. 응답 메시지와 본문 해석

```http
HTTP/1.1 201 Created
Location: /products/7
Content-Type: application/json
Content-Length: 21

{"id":7,"name":"pen"}
```

`201`은 생성 결과를 알리는 상태 코드이고 `Created`는 설명 문구다. 프로그램의 판단은 코드에 근거해야 한다. `Location`은 생성된 리소스 위치를 알리며 `Content-Type`은 본문을 어떤 형식으로 해석할지 알려 준다. 이 ASCII 본문은 추가 줄바꿈을 제외하면 21바이트다.

서버가 JSON을 보냈다고 생각해도 실제 본문이 프록시가 만든 HTML 오류 페이지일 수 있다. 상태·헤더·원문 본문을 먼저 확인하고 파싱 오류만 보고 JSON 문법 문제라고 단정하지 않는다.

## 6. 메시지의 경계와 연결의 경계

TCP는 연속된 바이트를 전달하므로 수신자는 HTTP 메시지가 어디서 끝나는지 알아야 한다. HTTP/1.1에서는 응답 종류와 규칙에 따라 본문이 없거나, `Content-Length`로 크기를 알리거나, `Transfer-Encoding: chunked`로 나누어 보낼 수 있다. 일부 응답은 연결 종료가 본문의 끝이 되지만 이런 방식으로는 같은 연결을 계속 재사용할 수 없다.

```http
HTTP/1.1 200 OK
Transfer-Encoding: chunked
Content-Type: text/plain

5
hello
0

```

이 예시의 청크 크기 `5`는 16진수 길이이며 뒤에 `hello` 5바이트가 온다. `0` 청크가 끝을 알린다. 실제 전송에는 각 경계의 CRLF와 마지막 빈 줄이 포함된다. 청크는 HTTP/1.1의 프레이밍 단위이며 TCP 세그먼트와 일대일로 대응하지 않는다.

한 메시지에 `Content-Length`와 `Transfer-Encoding`을 임의로 함께 넣으면 안 된다. 중간 장비와 서버가 경계를 다르게 해석하는 문제가 보안 취약점으로 이어질 수 있다. [RFC 9112 §6](https://httpwg.org/specs/rfc9112.html#message.body) 참조.

## 7. 본문이 없는 응답과 정보 응답

모든 성공 응답에 본문이 있는 것은 아니다. HEAD 요청에 대한 응답은 GET과 대응하는 메타데이터를 전할 수 있지만 본문을 보내지 않는다. 204와 304 응답도 본문을 갖지 않는다. 헤더 뒤의 빈 줄이 있다고 항상 JSON을 읽으려 하면 파싱 실패가 생긴다.

또 하나의 요청에 최종 응답 전에 100번대 정보 응답이 올 수 있다. 예를 들어 서버가 큰 본문을 받기 전에 계속 보내도 된다는 `100 Continue`를 보낼 수 있다. “요청 하나에 응답 하나”는 보통 최종 결과를 말하는 간단한 모델이며 이런 중간 응답을 제외한 표현이다.

## 8. 관련 계층과 실제 처리 흐름

```text
브라우저가 요청 구성
  -> HTTP 연결을 담당하는 운영체제·보안 계층
  -> 앞단 프록시 또는 웹 서버
  -> 애플리케이션의 라우팅·본문 해석·처리
  -> 응답 작성과 전송
  -> 브라우저의 상태·헤더·본문 처리
```

서버의 **파서(parser)** 는 바이트를 메시지 구조로 해석한다. **라우팅**은 메서드와 대상 경로 등을 보고 처리할 코드를 고른다. 본문을 읽는 단계와 JSON으로 해석하는 단계, 비즈니스 처리를 실행하는 단계는 다르다.

프록시가 있다면 브라우저와 프록시의 연결, 프록시와 서버의 연결이 따로 존재할 수 있다. 프록시가 요청을 전달하기 전에 오류를 반환하면 애플리케이션 로그에는 요청이 없을 수 있다. 모든 응답이 최종 애플리케이션이 만든 응답은 아니다.

## 9. 브라우저 Network 패널로 읽는 순서

1. 요청 URL과 메서드, 실제 시작된 요청을 확인한다.
2. 리다이렉트가 있다면 각 요청과 응답을 따로 본다.
3. Request Headers와 Payload에서 보낸 형식·데이터를 확인한다.
4. Status와 Response Headers를 보고 서버가 내린 결정을 읽는다.
5. Response의 원문을 확인한 뒤 Preview의 해석 결과와 비교한다.
6. Timing에서 연결 준비·서버 대기·다운로드 중 어디에 시간이 쓰였는지 본다.

Network 패널은 HTTP/2·HTTP/3도 읽기 쉬운 헤더 형태로 보여 준다. 그것이 실제 선로에서 HTTP/1.1 텍스트가 전송됐다는 뜻은 아니다. Protocol 열을 함께 확인한다.

명령줄에서는 `curl -i https://example.com/`으로 응답 헤더와 본문을 볼 수 있다. `curl -v`는 연결과 교환 과정을 더 보여 주지만 출력에 인증 헤더나 쿠키가 들어갈 수 있으므로 공유 전 확인한다. 예시 명령은 사용자 환경에서 관찰할 방법이며 이 페이지 작성 과정에서 실행한 결과를 뜻하지 않는다.

## 10. 로그를 연결한 장애 분석

| 관찰 | 먼저 나눌 문제 |
| --- | --- |
| 연결 오류만 있고 HTTP 상태 없음 | DNS·TCP·TLS 단계와 클라이언트 정책 |
| 서버가 잘못된 요청 형식으로 거절 | 요청 줄·헤더·본문 프레이밍·파서 제한 |
| 상태는 성공인데 JSON 파싱 실패 | 응답 타입, 빈 본문, 실제 데이터 |
| 앞단에는 기록, 애플리케이션에는 없음 | 프록시의 라우팅·차단·업스트림 연결 |
| 응답 헤더 뒤 다운로드가 오래 걸림 | 큰 본문·느린 생성·전송 경로·수신 속도 |

운영에서는 요청 식별자를 프록시와 서버 로그에 함께 남기면 한 요청을 추적하기 쉽다. 다만 같은 요청처럼 보여도 자동 재시도와 리다이렉트로 여러 교환이 발생할 수 있어 시각·대상·메서드도 같이 본다.

## 11. 흔한 오해·보안·성능 주의점

**본문은 문자열 객체 그대로 전송되지 않는다.** JSON 직렬화와 인코딩을 거친 바이트가 전송된다. `Content-Type`만 JSON으로 적고 다른 형식의 데이터를 보내면 자동 변환되지 않는다.

**응답 도착은 화면 처리 완료가 아니다.** 다운로드 뒤 파싱과 애플리케이션 로직이 더 실행될 수 있다. 서버 로그의 완료 시간, 네트워크 전송 시간, 사용자 화면의 완료 시점을 구분한다.

서버는 헤더·본문 크기와 읽기 시간을 제한해야 한다. 클라이언트가 선언한 길이와 타입은 신뢰할 수 없는 입력이며 실제 수신과 파싱 규칙을 엄격히 맞춘다. 느린 본문이나 과도한 업로드가 연결 자원을 오래 점유할 수도 있다.

## 12. 핵심 정리

<callout icon="✅" color="green_bg">
HTTP 메시지는 시작 줄·헤더·선택적 본문으로 읽고, 길이와 프레이밍 규칙으로 경계를 판단한다. TCP 연결의 수와 HTTP 교환의 수는 같지 않다.
</callout>

- Content-Type은 보낸 본문, Accept는 원하는 응답 형식을 설명한다.
- 본문 길이는 문자 수가 아니라 전송 바이트 수다.
- 본문이 없는 응답과 중간 정보 응답도 정상 동작의 일부다.
- 실패 분석은 실제 메시지와 각 처리 단계의 로그를 연결해서 한다.

## 13. 이해도 확인 질문

1. 요청의 Content-Type과 Accept가 모두 `application/json`인 경우 각각 무엇에 대한 정보를 제공하는가?
2. UTF-8 한글 본문의 Content-Length를 JavaScript 문자열의 문자 수로 계산하면 어떤 문제가 생길 수 있는가?
3. TCP 연결 하나에서 응답을 여러 번 주고받으려면 수신자가 메시지의 경계를 어떻게 알 수 있어야 하는가?
4. JSON 파싱 오류가 발생했는데 실제 응답은 프록시의 HTML 오류 페이지였다. Network 패널과 로그를 어떤 순서로 확인하겠는가?
5. 204 응답을 받은 클라이언트가 무조건 JSON을 파싱하다 실패했다. 이 상황을 전송 실패와 구분해 설명해 보라.

## 2. 이 주제를 왜 배우는가

> 💡 OSI 7계층은 실제 인터넷이 정확히 7개의 독립된 층으로 구현되어 있다는 뜻이 아니다. 복잡한 통신 문제를 나누어 생각하기 위한 참조 모델이다.

예를 들어 “브라우저에서 페이지가 열리지 않는다”는 문제는 물리적인 케이블 문제일 수도 있고, IP 라우팅 문제일 수도 있으며, TCP 연결 문제, TLS 인증서 문제, HTTP 응답 문제일 수도 있다. OSI 모델은 이 문제들을 섞지 않고 어느 책임 영역에서 발생했는지 분해하게 해 준다.

TCP/IP 모델은 인터넷에서 실제로 널리 쓰이는 프로토콜 묶음을 중심으로 한 모델이고, OSI 모델은 통신 기능을 더 세분화한 개념적 모델이다. 실무에서는 둘 중 하나만 선택하는 것이 아니라, TCP/IP로 실제 동작을 설명하고 OSI로 문제를 분류하는 경우가 많다.

## 3. 계층화가 필요한 이유

통신 시스템은 매우 많은 일을 동시에 수행한다.

- 사용자가 원하는 데이터와 명령을 표현해야 한다.
- 데이터 형식을 서로 이해할 수 있게 해야 한다.
- 연결의 시작과 종료를 관리해야 한다.
- 데이터가 유실되지 않도록 관리해야 한다.
- 목적지 장비까지 경로를 찾아야 한다.
- 가까운 다음 장비에 실제로 전기·무선 신호를 전달해야 한다.

이 모든 기능을 하나의 거대한 규칙으로 만들면 변경과 디버깅이 어려워진다. 따라서 통신 기능을 역할별로 나누고, 각 계층이 바로 아래 계층의 서비스를 사용하도록 설계한다.

계층화의 장점은 다음과 같다.

- 한 계층의 구현이 바뀌어도 다른 계층에 미치는 영향을 줄일 수 있다.
- 프로토콜을 조합할 수 있다. 예를 들어 HTTP는 TCP 위에서, TCP는 IP 위에서 동작한다.
- 장애 원인을 계층별로 분리할 수 있다.
- 서로 다른 회사와 장비가 공통 규칙에 따라 상호 운용될 수 있다.

## 4. OSI 7계층 개요

OSI(Open Systems Interconnection) 모델은 통신 기능을 일곱 계층으로 나눈 참조 모델이다.

| 계층 | 이름 | 핵심 질문 |
| --- | --- | --- |
| 7 | 응용 계층 | 사용자 프로그램은 어떤 서비스를 요청하는가? |
| 6 | 표현 계층 | 데이터는 어떤 형식으로 표현·변환·암호화되는가? |
| 5 | 세션 계층 | 통신 대화는 어떻게 시작·유지·종료되는가? |
| 4 | 전송 계층 | 프로그램 간 데이터를 신뢰성 있게 전달할 것인가? |
| 3 | 네트워크 계층 | 다른 네트워크의 목적지까지 어떤 경로로 갈 것인가? |
| 2 | 데이터 링크 계층 | 같은 링크에서 다음 장비까지 어떻게 전달할 것인가? |
| 1 | 물리 계층 | 비트를 실제 신호로 어떻게 보낼 것인가? |

아래 계층일수록 실제 전송 매체와 가깝고, 위 계층일수록 사용자 프로그램과 가깝다.

## 5. 7계층부터 5계층

### 7계층: 응용 계층

응용 계층은 사용자가 직접 이용하는 네트워크 서비스와 가장 가까운 계층이다. 여기서 말하는 “응용”은 브라우저, 모바일 앱, 백엔드 서버 같은 애플리케이션이 네트워크를 통해 의미 있는 작업을 수행하도록 만드는 규칙을 뜻한다.

대표적인 프로토콜은 다음과 같다.

- HTTP: 웹 페이지와 API 요청·응답
- DNS: 도메인 이름을 IP 주소로 변환
- SMTP: 이메일 발송
- FTP: 파일 전송

HTTP 요청의 다음 예시는 응용 계층 메시지다.

```txt
GET /profile HTTP/1.1
Host: api.example.com
Authorization: Bearer <token>
```

이 메시지는 “어떤 리소스를 어떤 방식으로 요청하는가”를 표현한다. 그러나 이 요청을 실제 서버까지 전달하는 일은 전송 계층 이하가 담당한다.

### 6계층: 표현 계층

표현 계층은 송신자와 수신자가 데이터를 같은 방식으로 해석하도록 데이터 표현 형식을 다룬다. 문자 인코딩, 데이터 직렬화, 압축, 암호화가 이 계층의 대표적인 관심사다.

예를 들어 JSON은 데이터를 표현하는 형식이다.

```json
{
  "name": "haewon",
  "role": "student"
}
```

클라이언트와 서버가 모두 JSON이라는 형식을 알고 있어야 같은 데이터를 해석할 수 있다. 문자열 인코딩도 중요하다. UTF-8로 인코딩한 한글 텍스트를 다른 방식으로 해석하면 글자가 깨질 수 있다.

실제 인터넷 구현에서 표현 계층이 항상 별도 프로그램이나 프로토콜로 분리되어 있는 것은 아니다. HTTP의 `Content-Type`, `Content-Encoding` 같은 헤더, 애플리케이션의 JSON 직렬화 코드, TLS의 암호화 기능 등이 표현 계층의 역할과 연결되어 이해될 수 있다.

> 🔭 **미리보기: TLS**
>
> TLS는 통신 상대의 신원을 검증하고 전송 내용을 암호화하는 보안 프로토콜이다. OSI 모델에서는 표현 계층 또는 그 주변 역할로 설명되기도 하지만, 실제 구현에서는 여러 계층과 밀접하게 결합된다.

### 5계층: 세션 계층

세션 계층은 통신 당사자 사이의 대화, 즉 **세션(session)** 을 생성·유지·복구·종료하는 관점의 역할을 다룬다.

예를 들어 긴 통신이 진행될 때 “어디까지 처리했는가”, “연결이 끊겼다면 재개할 수 있는가”, “대화가 끝났는가” 같은 문제가 세션 관점의 문제다.

다만 현대 웹 개발에서 OSI 5계층이 명확한 하나의 독립 계층으로 구현되는 경우는 흔하지 않다. 세션 관리는 HTTP 쿠키, 인증 토큰, 애플리케이션 서버, 데이터베이스, WebSocket 등의 여러 기능으로 나뉘어 구현된다.

여기서 주의할 점은 **OSI의 세션 계층**과 웹 개발에서 말하는 **로그인 세션**이 완전히 같은 개념은 아니라는 것이다. 로그인 세션은 사용자 인증 상태를 유지하기 위한 애플리케이션 설계 방식이다.

> 🔭 **미리보기: 쿠키와 세션**
>
> HTTP는 기본적으로 각 요청을 독립적으로 처리하는 특성이 있어, 로그인 상태 같은 정보를 유지하려면 쿠키나 토큰 같은 추가 장치가 필요하다. 인증과 세션 관리는 이후 HTTP 상태 관리·인증 학습에서 자세히 다룬다.

## 6. 4계층부터 1계층

### 4계층: 전송 계층

전송 계층은 출발지 장비의 프로그램과 목적지 장비의 프로그램 사이에서 데이터를 전달한다. IP 주소가 장비를 찾는다면, 전송 계층의 포트 번호는 해당 장비 안에서 데이터를 받아야 할 프로그램을 찾는다.

대표 프로토콜은 TCP와 UDP다.

| 프로토콜 | 특징 | 적합한 예 |
| --- | --- | --- |
| TCP | 연결 설정, 순서 보장, 유실 감지와 재전송, 흐름 제어 | 웹 페이지, API, 파일 전송 |
| UDP | 간단한 전송, 낮은 부가 작업, 기본적인 전달 보장 없음 | 실시간 미디어, 게임, DNS 일부 사용 사례 |

TCP는 양쪽이 통신을 시작할 준비가 되었는지 확인하고, 보낸 데이터가 유실되면 재전송하며, 수신 측에 순서대로 전달되도록 관리한다. 이 때문에 신뢰성이 필요하지만 약간의 지연을 감수할 수 있는 웹 요청에 적합하다.

전송 계층에서 사용하는 데이터 단위를 TCP에서는 보통 **세그먼트(segment)** 라고 부른다. TCP 헤더에는 출발지 포트, 목적지 포트, 순서 번호 등 전달 제어를 위한 정보가 포함된다.

### 3계층: 네트워크 계층

네트워크 계층은 서로 다른 네트워크 사이에서 목적지까지 데이터를 전달하는 역할을 한다. 이 계층의 핵심 프로토콜은 IP다.

IP 패킷에는 출발지 IP 주소와 목적지 IP 주소가 들어간다. 라우터는 목적지 IP 주소를 보고 자신이 가진 라우팅 정보에 따라 다음 경로를 선택한다.

네트워크 계층의 핵심 특징은 종단 간 전달을 목표로 하지만, 전달 자체를 완전히 보장하지는 않는다는 점이다. 패킷 유실, 순서 변경, 중복은 발생할 수 있으며, 신뢰성 보장이 필요하다면 TCP나 애플리케이션이 이를 보완한다.

이 계층에서 자주 마주치는 장애는 다음과 같다.

- 잘못된 IP 주소 또는 서브넷 설정
- 기본 게이트웨이 설정 오류
- 라우팅 경로 누락
- 네트워크 ACL 또는 방화벽 정책에 의한 차단
- 목적지 서버의 네트워크 장애

### 2계층: 데이터 링크 계층

데이터 링크 계층은 같은 네트워크 링크에서 데이터를 안전하고 효율적으로 전달하는 역할을 한다. Ethernet과 Wi-Fi가 대표적인 예다.

이 계층은 IP 주소가 아니라 주로 MAC 주소를 사용하여 **현재 구간의 다음 장비**를 식별한다. 예를 들어 노트북이 외부 웹 서버로 데이터를 보낼 때, 노트북은 최종 웹 서버의 MAC 주소를 알아내는 것이 아니라 보통 자신의 기본 게이트웨이인 공유기의 MAC 주소로 프레임을 보낸다.

데이터 링크 계층의 전송 단위는 보통 **프레임(frame)** 이다. 프레임에는 출발지와 목적지 MAC 주소, 내부 데이터가 어떤 상위 프로토콜인지 나타내는 정보, 오류 검출을 위한 정보 등이 포함될 수 있다.

같은 IP 패킷이라도 라우터를 하나 지날 때마다 다음 링크에 맞게 새로운 프레임으로 감싸질 수 있다. 즉, IP 주소는 최종 목적지 관점에서 유지되지만, MAC 주소는 구간마다 바뀔 수 있다.

### 1계층: 물리 계층

물리 계층은 비트(bit)를 실제 전기 신호, 빛 신호, 전파 신호 등으로 전송하는 역할을 다룬다.

예를 들어 다음이 물리 계층과 관련된다.

- 이더넷 케이블
- 광섬유
- Wi-Fi 전파
- 커넥터와 포트의 물리적 규격
- 전압, 주파수, 변조 방식
- 전송 속도와 신호 품질

물리 계층에서 장애가 나면 가장 기초적인 통신부터 불가능해질 수 있다. 케이블이 빠졌거나, Wi-Fi 신호가 너무 약하거나, 네트워크 인터페이스가 비활성화된 경우가 대표적이다.

## 7. OSI 모델의 데이터 흐름

브라우저가 HTTP 요청을 보내는 과정을 OSI 모델로 보면, 상위 계층의 데이터가 하위 계층으로 내려가며 제어 정보가 붙는다.

```txt
7. 응용 계층: HTTP 요청 생성
6. 표현 계층: 문자 인코딩, JSON 직렬화, 압축·암호화 관련 처리
5. 세션 계층: 통신 상태 또는 대화 관리 관점
4. 전송 계층: TCP 헤더 추가, 포트와 신뢰성 관리
3. 네트워크 계층: IP 헤더 추가, 목적지 IP 주소와 라우팅
2. 데이터 링크 계층: 프레임 생성, 현재 링크의 MAC 주소 사용
1. 물리 계층: 전기·광·무선 신호로 전송
```

수신 측에서는 반대로 물리 계층에서 신호를 받고, 데이터 링크·네트워크·전송 계층의 정보를 차례로 처리한 뒤, 최종적으로 웹 서버가 HTTP 요청을 읽는다.

이 과정을 **캡슐화**와 **역캡슐화**라고 한다.

## 8. TCP/IP 모델과 OSI 모델

TCP/IP 모델은 인터넷에서 실제로 사용되는 프로토콜을 중심으로 구성된 모델이며, 보통 4계층으로 설명한다. OSI 모델은 이를 더 세밀하게 7계층으로 나눈 참조 모델이다.

| OSI 7계층 | TCP/IP 4계층 대응 | 대표 기술과 프로토콜 |
| --- | --- | --- |
| 응용 계층 | 응용 계층 | HTTP, DNS, SMTP |
| 표현 계층 | 응용 계층 | JSON, UTF-8, 압축, TLS 관련 기능 |
| 세션 계층 | 응용 계층 | 애플리케이션 세션 관리, 연결 상태 관리 |
| 전송 계층 | 전송 계층 | TCP, UDP, 포트 |
| 네트워크 계층 | 인터넷 계층 | IP, ICMP, 라우팅 |
| 데이터 링크 계층 | 네트워크 접근 계층 | Ethernet, Wi-Fi, MAC 주소 |
| 물리 계층 | 네트워크 접근 계층 | 케이블, 광섬유, 전파, 신호 |

### 왜 OSI는 7계층이고 TCP/IP는 4계층인가

OSI는 통신 기능을 개념적으로 더 세밀하게 분리한다. 특히 표현 계층과 세션 계층을 별도로 구분한다.

반면 TCP/IP 모델은 인터넷의 실제 프로토콜 스택을 설명하는 데 더 가깝다. 실제 웹 개발과 운영에서는 표현·세션 기능이 응용 프로그램, HTTP, TLS, 프레임워크 등에 분산되어 있는 경우가 많아 TCP/IP 모델처럼 묶어서 설명하는 편이 자연스럽다.

따라서 다음처럼 이해하면 좋다.

- **OSI 모델**: 통신 문제를 세밀하게 분류하는 사고 도구
- **TCP/IP 모델**: 인터넷이 실제로 동작하는 프로토콜 구조를 이해하는 도구

## 9. 웹 요청을 두 모델로 해석하기

사용자가 브라우저에서 다음 URL에 접속한다고 가정하자.

```txt
<https://www.example.com/search?q=network>
```

### 응용·표현·세션 관점

브라우저는 URL을 해석하고, 필요한 경우 도메인 이름을 IP 주소로 찾는다. 그다음 HTTP 요청을 만들며, 요청에는 경로 `/search`, 쿼리 문자열 `q=network`, 호스트 정보 등이 포함된다.

요청과 응답의 본문이 JSON이라면 JSON은 데이터를 표현하는 형식이다. 한글이 포함된 경우에는 UTF-8 같은 문자 인코딩이 중요하다. HTTPS라면 TLS가 통신 보호와 서버 신원 확인에 관여한다.

### 전송 계층 관점

브라우저는 보통 서버의 443번 포트에 연결한다. TCP는 출발지의 임시 포트와 목적지의 443번 포트를 사용해, 해당 데이터가 브라우저와 웹 서버 사이의 어느 통신에 속하는지 구분한다.

TCP는 손실된 세그먼트를 재전송하고 데이터 순서를 관리한다. 그래서 웹 서버는 HTTP 메시지를 순서가 정리된 바이트 흐름으로 받을 수 있다.

### 네트워크 계층 관점

IP 계층은 서버의 IP 주소를 목적지로 하는 패킷을 만든다. 라우터들은 목적지 IP 주소를 기반으로 다음 전달 경로를 결정한다.

클라이언트와 서버가 서로 다른 국가나 클라우드 리전에 있을 수 있어도 IP와 라우팅 덕분에 여러 네트워크를 거쳐 통신할 수 있다.

### 링크·물리 계층 관점

내 노트북은 첫 번째 구간에서 보통 Wi-Fi 또는 Ethernet을 사용해 공유기나 스위치에 프레임을 보낸다. 이때 목적지 MAC 주소는 최종 웹 서버가 아니라 다음 홉 장비의 MAC 주소다.

프레임은 무선 전파, 전기 신호, 광신호 등의 물리적 신호로 변환되어 전달된다. 라우터를 지날 때마다 링크 계층과 물리 계층의 전달 방식은 달라질 수 있다.

## 10. HTTP 요청과 계층 정보

다음은 HTTP 요청을 단순화한 예시다.

```txt
POST /api/orders HTTP/1.1
Host: api.example.com
Content-Type: application/json
Content-Length: 48

{"productId":42,"quantity":1}
```

이 메시지를 계층별로 해석하면 다음과 같다.

| 항목 | 관련 계층 | 의미 |
| --- | --- | --- |
| `POST /api/orders` | 응용 계층 | 주문 생성이라는 애플리케이션 요청 |
| `Host: api.example.com` | 응용 계층 | 같은 서버에서 어떤 호스트를 요청하는지 지정 |
| `Content-Type: application/json` | 표현 계층 관점 | 본문 데이터를 JSON으로 해석해야 함 |
| JSON 본문 | 응용·표현 계층 | 주문 데이터의 구조와 값 |
| 목적지 포트 443 | 전송 계층 | 서버의 HTTPS 서비스 프로세스를 식별 |
| 목적지 IP 주소 | 네트워크 계층 | 인터넷에서 목적지 서버 또는 네트워크를 식별 |
| 목적지 MAC 주소 | 데이터 링크 계층 | 현재 링크의 다음 장비를 식별 |

브라우저 개발자 도구의 Network 패널은 HTTP 헤더와 본문처럼 주로 응용 계층 정보를 보여 준다. 하지만 “연결이 거부됨”, “DNS 이름을 찾을 수 없음”, “인증서 오류” 같은 문제는 더 아래 계층 또는 보안 계층의 상태까지 함께 살펴야 한다.

## 11. 계층별 장애 사례

### 사례 1: Wi-Fi는 연결되었지만 어떤 사이트도 열리지 않는다

Wi-Fi 아이콘이 연결 상태라고 해서 인터넷 전체가 정상이라는 보장은 없다. 공유기와 노트북 사이의 링크는 정상일 수 있지만, 공유기에서 ISP로 나가는 경로, DNS 설정, 라우팅 문제가 있을 수 있다.

- 1\~2계층: 노트북과 공유기 사이의 연결 상태는 정상일 수 있다.
- 3계층: 외부 네트워크로 나가는 게이트웨이 또는 라우팅이 문제일 수 있다.
- 7계층: DNS 설정 문제라면 IP 주소를 직접 입력했을 때와 도메인으로 접근했을 때 결과가 달라질 수 있다.

### 사례 2: 서버 IP에는 연결되지만 웹 서비스가 열리지 않는다

서버까지 네트워크 경로가 있어도, 목적지 포트에 서버 프로그램이 대기하지 않으면 웹 서비스는 제공되지 않는다.

- 3계층: 서버 IP까지의 도달 가능성
- 4계층: 80 또는 443 같은 목적지 포트의 연결 가능성
- 7계층: 웹 서버가 HTTP 요청을 올바르게 처리하는지

예를 들어 서버에서 Nginx가 실행되지 않았거나 방화벽이 443 포트를 막고 있다면, IP는 살아 있어도 HTTPS 접속은 실패할 수 있다.

### 사례 3: 연결은 성공하지만 브라우저에 502 또는 500이 보인다

이 경우 네트워크의 하위 계층이 완전히 끊긴 문제라기보다, 대체로 프록시·웹 서버·애플리케이션·데이터베이스 같은 상위 계층의 문제일 가능성이 크다.

- `500 Internal Server Error`: 애플리케이션 처리 중 오류가 발생했을 가능성
- `502 Bad Gateway`: 프록시가 뒤쪽 애플리케이션 서버로부터 유효한 응답을 받지 못했을 가능성
- `503 Service Unavailable`: 서버가 일시적으로 요청을 처리할 수 없을 가능성

상태 코드는 응용 계층의 의사소통 수단이다. “네트워크가 정상”이라는 뜻이 아니라, HTTP 응답을 받을 정도의 연결은 이루어졌고 서버 또는 중간 장비가 특정 상태를 알렸다는 뜻이다.

## 12. 흔한 오해와 주의점

### “OSI 7계층은 인터넷의 실제 구현 순서다”

OSI 모델은 참조 모델이다. 실제 인터넷 소프트웨어는 계층을 완벽하게 분리하지 않으며, 하나의 기술이 여러 계층 역할과 관련될 수 있다.

### “TLS는 무조건 OSI 6계층이다”

TLS를 표현 계층과 연결해 설명할 수는 있지만, 실제 프로토콜 스택에서는 TCP와 HTTP 사이에서 동작하며 여러 계층과 상호작용한다. OSI 계층 하나로 기계적으로 고정하면 실제 동작을 오해할 수 있다.

### “세션 계층은 로그인 세션을 뜻한다”

OSI 세션 계층은 통신 대화의 관리라는 일반적 개념이다. 웹 서비스의 로그인 세션은 사용자 인증 상태를 관리하는 애플리케이션 기능이며, 둘은 관련이 있을 수 있지만 동일하지 않다.

### “HTTP 오류 코드가 보이면 네트워크 문제는 아니다”

HTTP 상태 코드를 받았다는 것은 적어도 HTTP 응답까지 도달했다는 중요한 단서다. 그러나 중간 프록시, 로드 밸런서, 인증 시스템, 서버 과부하 등 네트워크와 인프라 경계의 문제가 HTTP 오류로 나타날 수 있다.

### “계층은 서로 절대 영향을 주지 않는다”

계층은 역할을 분리하지만 실제 성능과 장애는 서로 영향을 준다. 예를 들어 패킷 손실은 TCP 재전송을 늘리고, 이는 HTTP 요청 시간을 길게 만들며, 결과적으로 사용자는 서버가 느리다고 느낄 수 있다.

## 13. 보안·성능·운영·디버깅 관점

### 보안 관점

보안은 특정 한 계층의 기능이 아니다. 물리 계층에서는 장비 접근 통제가 필요하고, 네트워크 계층과 전송 계층에서는 방화벽·네트워크 정책이 필요하며, 응용 계층에서는 인증·인가·입력 검증이 필요하다.

HTTPS는 전송 중인 HTTP 데이터를 보호하지만, 서버 코드의 권한 검증 오류나 SQL 인젝션 같은 응용 계층 취약점까지 자동으로 막지는 않는다. 계층별 방어가 필요한 이유다.

### 성능 관점

지연 시간은 계층별 요인의 합으로 나타난다.

- 물리·링크 계층: 무선 신호 품질, 링크 속도, 재전송
- 네트워크 계층: 경로 길이, 혼잡, RTT
- 전송 계층: TCP 연결 설정, 혼잡 제어, 패킷 손실 재전송
- 응용 계층: 서버 처리 시간, 데이터베이스 조회, 응답 크기

예를 들어 API 응답이 느릴 때 HTTP 서버 코드만 프로파일링하면 원인을 놓칠 수 있다. DNS 조회 시간, TLS 연결 시간, TCP 재전송, 서버 처리 시간, 응답 다운로드 시간을 나누어 관찰해야 한다.

### 운영·디버깅 관점

계층 모델을 디버깅 체크리스트로 사용할 수 있다.

1. 물리·링크: 장비 연결, Wi-Fi 상태, 인터페이스 상태를 확인한다.
2. 네트워크: IP 주소, 기본 게이트웨이, 라우팅, DNS 해석을 확인한다.
3. 전송: 서버 포트가 열려 있는지, 프로세스가 해당 포트에서 대기하는지 확인한다.
4. 보안 연결: 인증서, TLS 협상, 프록시 설정을 확인한다.
5. 응용: HTTP 상태 코드, 요청 헤더, 응답 본문, 서버 로그를 확인한다.

문제를 위에서 아래로 또는 아래에서 위로 일관되게 좁히면, “접속이 안 된다”는 모호한 증상을 재현 가능하고 확인 가능한 원인으로 바꿀 수 있다.

## 14. 핵심 정리

> ✅ - OSI 7계층은 통신 기능을 세분화해 이해하고 장애를 분류하기 위한 참조 모델이다.

- TCP/IP 모델은 실제 인터넷 프로토콜을 중심으로 한 실용적인 모델이며 보통 4계층으로 설명한다.
- OSI의 응용·표현·세션 계층은 TCP/IP 모델의 응용 계층에 대체로 묶여 이해된다.
- 전송 계층은 포트와 프로그램 간 통신을 담당하며 TCP와 UDP가 대표적이다.
- 네트워크 계층은 IP 주소와 라우팅으로 서로 다른 네트워크를 연결한다.
- 데이터 링크·물리 계층은 가까운 구간의 프레임 전달과 실제 신호 전송을 담당한다.
- 계층 모델은 암기 대상이 아니라, 웹 요청의 흐름을 복원하고 장애 원인을 좁히는 도구다.

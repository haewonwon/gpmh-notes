## 1. 학습 목표

이 페이지를 마치면 다음을 할 수 있어야 한다.

- 서로 다른 컴퓨터가 인터넷에서 통신하기 위해 필요한 구성 요소를 설명한다.
- 클라이언트, 서버, 네트워크 장비, 프로토콜의 역할을 구분한다.
- 웹 요청이 애플리케이션에서 네트워크로 내려가고, 반대편에서 다시 올라오는 흐름을 설명한다.
- TCP/IP 4계층의 책임을 구분하고, 각 계층의 대표 프로토콜을 연결한다.
- 문제 발생 시 “어느 계층부터 확인해야 하는가”를 판단한다.

## 2. 이 주제를 왜 배우는가

브라우저에서 URL을 열면 화면에는 결과만 보이지만, 실제로는 브라우저·운영체제·공유기·통신사 망·서버·서버 내부 프로그램이 협력한다. 이 과정에서 하나라도 실패하면 사용자는 “사이트가 안 열린다”는 하나의 증상만 보게 된다.

하지만 원인은 매우 다를 수 있다. 도메인 이름을 IP 주소로 바꾸지 못한 DNS 문제일 수도 있고, 서버까지의 경로가 끊긴 IP 네트워크 문제일 수도 있으며, 서버 프로그램이 요청을 처리하지 못한 HTTP 문제일 수도 있다. 계층을 이해하면 증상만 보고도 원인을 좁힐 수 있다.

TCP/IP 모델은 인터넷 통신의 역할을 나누는 대표적인 모델이다. 각 계층은 바로 위 계층이 원하는 일을 수행할 수 있도록 서비스를 제공하며, 아래 계층의 내부 구현을 모두 알 필요 없게 만든다.

## 3. 네트워크의 기본 구조

### 네트워크란 무엇인가

네트워크는 여러 장치가 데이터를 주고받을 수 있도록 연결된 구조다. 장치는 노트북, 스마트폰, 서버, 라우터, 프린터, IoT 기기처럼 네트워크 인터페이스를 가진 모든 장비를 포함한다.

통신하려면 단순히 케이블이나 Wi-Fi로 연결되는 것만으로는 부족하다. 다음 문제가 해결되어야 한다.

- 누가 누구에게 보내는지 식별해야 한다.
- 목적지까지 어떤 경로로 전달할지 결정해야 한다.
- 여러 프로그램이 동시에 통신할 때 데이터를 올바른 프로그램에 전달해야 한다.
- 데이터가 손실되거나 순서가 바뀌었을 때 어떻게 처리할지 정해야 한다.
- 데이터의 형식과 해석 방법을 송신자와 수신자가 합의해야 한다.

이 합의를 **프로토콜(protocol)** 이라고 한다. 프로토콜은 통신 참여자들이 따르는 규칙이다. 예를 들어 HTTP는 웹 요청과 응답의 형식을 정하고, IP는 인터넷에서 목적지를 찾아가는 방식의 기본 규칙을 정한다.

### 클라이언트와 서버

웹 환경에서 **클라이언트(client)** 는 서비스를 요청하는 쪽이고, **서버(server)** 는 요청을 받아 처리하고 응답하는 쪽이다.

- 브라우저는 대표적인 클라이언트다.
- API 서버는 대표적인 서버다.
- 같은 컴퓨터도 상황에 따라 클라이언트와 서버가 될 수 있다.
- 역할은 장비의 종류가 아니라 통신 순간의 행동으로 결정된다.

예를 들어 브라우저가 `https://example.com`에 데이터를 요청하면 브라우저는 클라이언트다. 서버는 요청을 처리한 뒤 HTML, JSON, 이미지 같은 데이터를 응답한다.

서버는 보통 인터넷에서 접근 가능한 주소를 가지고 요청을 기다린다. 반면 개인 노트북이나 스마트폰은 일반적으로 요청을 먼저 보내는 쪽이며, 공유기나 방화벽 뒤에 위치하는 경우가 많다.

### 인터넷은 하나의 거대한 네트워크다

인터넷은 하나의 회사가 운영하는 단일 네트워크가 아니다. 수많은 작은 네트워크가 서로 연결된 **네트워크들의 네트워크**다.

집에서 웹 서버에 접속할 때 데이터는 대략 다음과 같은 구간을 지난다.

1. 내 컴퓨터 또는 스마트폰
2. 집 또는 학교의 Wi-Fi 공유기
3. 인터넷 서비스 제공자(ISP)의 네트워크
4. 여러 중간 통신 사업자의 네트워크
5. 서버가 있는 클라우드 또는 회사 네트워크
6. 목적지 서버

중간 장비와 네트워크가 많아도 통신이 가능한 이유는, 참여자들이 공통된 프로토콜을 사용하기 때문이다. TCP/IP는 이 인터넷 통신의 공통 기반이다.

## 4. 데이터를 구분하는 주소들

통신에서는 “어느 장비”, “어느 프로그램”, “어떤 서비스”인지 구분해야 한다. 이를 위해 서로 다른 범위의 식별자가 사용된다.

| 식별자 | 주로 쓰이는 범위 | 해결하는 문제 | 예시 |
| --- | --- | --- | --- |
| MAC 주소 | 같은 로컬 네트워크 | 가까운 구간에서 어느 네트워크 인터페이스로 보낼지 식별 | `00:1A:2B:3C:4D:5E` |
| IP 주소 | 인터넷 전체 | 출발지와 목적지 장비를 식별하고 경로를 찾음 | `203.0.113.10` |
| 포트 번호 | 한 장비 내부 | 수신 데이터를 어느 프로그램에 전달할지 구분 | `443`, `3000`, `8080` |
| 도메인 이름 | 사람이 사용하는 이름 | 기억하기 어려운 IP 주소 대신 서비스 이름 사용 | `example.com` |

### IP 주소

**IP 주소**는 인터넷에서 장비 또는 네트워크 인터페이스를 식별하는 논리적 주소다. 웹 브라우저는 사람이 입력한 `example.com`이라는 이름을 그대로 인터넷에 전달하는 것이 아니라, 먼저 해당 이름에 대응하는 IP 주소를 찾아야 한다.

예를 들어 어떤 서버가 `203.0.113.10`이라는 IP 주소를 가진다고 하자. 인터넷의 라우터들은 이 주소를 보고 목적지 방향으로 패킷을 전달한다.

IP 주소는 “어디에 있는 장비 또는 네트워크인가”를 나타내는 데 사용된다. 그러나 IP 주소만으로는 해당 컴퓨터에서 어느 프로그램이 데이터를 받아야 하는지 알 수 없다. 이 문제를 포트 번호가 해결한다.

### 포트 번호

**포트(port)** 는 하나의 컴퓨터 안에서 네트워크 통신을 사용하는 프로그램을 구분하는 번호다. 하나의 서버 IP 주소에서 웹 서버, 데이터베이스, SSH 서버 등 여러 서비스가 동시에 실행될 수 있기 때문에 필요하다.

예를 들어 다음 두 주소는 같은 서버를 가리키지만, 서로 다른 서비스로 연결될 수 있다.

- `203.0.113.10:443` — 일반적으로 HTTPS 웹 서비스
- `203.0.113.10:22` — 일반적으로 SSH 원격 접속 서비스

브라우저가 HTTPS 웹 사이트에 연결할 때 보통 목적지 포트는 443이다. 개발 중인 Node.js 서버가 `localhost:3000`에서 실행된다면, `3000`은 내 컴퓨터의 특정 서버 프로그램을 가리키는 포트 번호다.

포트 번호는 서비스 이름 그 자체가 아니다. 443을 쓰는 프로그램이 반드시 HTTPS 서버라는 보장은 없고, 3000번 포트에 어떤 프로그램을 띄울지는 개발자나 운영자가 정할 수 있다.

### MAC 주소

**MAC 주소**는 네트워크 인터페이스 카드에 연결된 식별자다. 주로 같은 로컬 네트워크, 예를 들어 집 Wi-Fi 내부에서 가까운 다음 장비를 찾는 데 사용된다.

중요한 점은 MAC 주소가 인터넷 전체의 목적지를 찾는 주소가 아니라는 것이다. 내 컴퓨터에서 서버로 가는 동안 데이터는 여러 라우터를 지나며, 각 구간에서 사용되는 MAC 주소는 바뀔 수 있다. 반면 IP 패킷의 목적지 IP 주소는 일반적으로 최종 목적지까지 유지된다.

## 5. 패킷 교환과 라우팅

### 데이터를 잘게 나누는 이유

인터넷은 보통 데이터를 한 번에 거대한 덩어리로 보내지 않는다. 데이터를 적절한 크기의 작은 단위로 나누어 전송한다. 이러한 전송 단위를 흔히 **패킷(packet)** 이라고 부른다.

데이터를 나누면 다음과 같은 이점이 있다.

- 하나의 큰 전송이 네트워크를 오래 독점하지 않는다.
- 여러 사용자의 데이터가 네트워크를 번갈아 사용할 수 있다.
- 일부 데이터가 손실되어도 전체를 처음부터 다시 보내지 않고 필요한 부분만 재전송할 수 있다.
- 중간 장비가 목적지에 따라 데이터를 더 유연하게 전달할 수 있다.

다만 각 패킷이 서로 다른 경로를 지날 수 있고, 도착 순서가 바뀌거나 일부가 유실될 수 있다. 이러한 문제를 어떻게 다룰지는 전송 계층, 특히 TCP가 담당한다.

### 라우터의 역할

**라우터(router)** 는 서로 다른 네트워크 사이에서 패킷을 전달하는 장비다. 라우터는 패킷의 목적지 IP 주소를 보고, 자신이 가진 경로 정보에 따라 다음으로 보낼 장비를 선택한다.

라우터는 “이 패킷이 최종 서버까지 실제로 도착했는가”를 보장하지 않는다. 일반적으로 IP 계층은 최선 노력(best effort) 방식으로 전달한다. 즉, 가능한 경로를 따라 전달하려 하지만 혼잡, 장애, 설정 오류 등으로 패킷이 유실될 수 있다.

이러한 한계 때문에 애플리케이션이 신뢰성 있는 통신을 원할 때 TCP 같은 전송 계층 프로토콜을 사용한다.

## 6. TCP/IP 계층 모델

TCP/IP 모델은 인터넷 통신을 역할별로 나눈 모델이다. 실무에서는 보통 다음 4계층으로 설명한다.

| TCP/IP 계층 | 핵심 책임 | 대표 예시 |
| --- | --- | --- |
| 응용 계층 | 사용자 프로그램이 사용할 통신 규칙과 데이터 형식 정의 | HTTP, DNS, SMTP |
| 전송 계층 | 프로그램 간 통신, 포트, 신뢰성·흐름 제어 | TCP, UDP |
| 인터넷 계층 | 장비 간 주소 지정과 네트워크 간 전달 | IP, ICMP |
| 네트워크 접근 계층 | 실제 링크에서 프레임을 전달 | Ethernet, Wi-Fi |

> 💡 계층은 “데이터가 실제로 물리적으로 네 겹으로 존재한다”는 뜻이 아니다. 복잡한 통신 문제를 역할별로 나누어 설계하고 이해하기 위한 모델이다.

### 응용 계층

응용 계층은 사용자가 직접 사용하는 프로그램과 가장 가까운 계층이다. 브라우저, 모바일 앱, 백엔드 서버, 이메일 프로그램 등이 이 계층의 프로토콜을 사용한다.

대표적인 프로토콜은 다음과 같다.

- **HTTP**: 브라우저와 웹 서버가 웹 문서, API 데이터 등을 요청하고 응답하는 규칙
- **DNS**: 도메인 이름을 IP 주소로 찾는 규칙
- **SMTP**: 이메일을 보내는 규칙

응용 계층은 “사용자가 무엇을 요청하는가”를 표현한다. 예를 들어 HTTP 요청의 `GET /products`는 상품 목록을 요청한다는 애플리케이션 의미를 가진다.

하지만 HTTP는 인터넷에서 실제로 패킷을 전달하지 않는다. 아래 전송 계층에 데이터를 맡기고, 전송 계층은 다시 인터넷 계층에 맡긴다.

### 전송 계층

전송 계층은 장비와 장비의 통신을 넘어, 한 장비에서 실행 중인 **프로그램과 프로그램 사이의 통신**을 다룬다. 이때 포트 번호가 사용된다.

대표 프로토콜은 TCP와 UDP다.

- **TCP**: 연결을 설정하고, 데이터의 순서·유실 여부를 관리하여 신뢰성 있는 바이트 스트림을 제공한다.
- **UDP**: 최소한의 정보만 덧붙여 빠르게 보내며, 전달·순서·재전송을 기본적으로 보장하지 않는다.

웹의 HTTP/1.1과 HTTP/2는 일반적으로 TCP 위에서 동작한다. TCP는 손실된 데이터를 다시 보내고, 순서가 뒤바뀐 데이터를 정리하므로 HTTP 같은 요청·응답 통신이 안정적으로 데이터를 주고받는 데 도움을 준다.

> 🔭 **미리보기: QUIC와 HTTP/3**
>
> HTTP/3는 TCP 대신 UDP를 기반으로 설계된 QUIC 위에서 동작한다. 왜 새로운 전송 방식이 필요했는지는 이후 HTTP 버전과 성능 학습에서 다룬다.

### 인터넷 계층

인터넷 계층은 서로 다른 네트워크 사이에서 패킷을 목적지까지 전달하는 역할을 맡는다. 대표 프로토콜은 IP다.

IP의 핵심 책임은 다음과 같다.

- 출발지와 목적지 IP 주소를 담는다.
- 라우터가 목적지 방향을 판단할 수 있게 한다.
- 네트워크를 여러 개 거쳐 목적지까지 패킷을 전달한다.

IP는 데이터가 반드시 도착한다고 보장하지 않는다. 또한 순서가 유지된다고 보장하지도 않는다. IP가 단순한 전달 기능에 집중하기 때문에 인터넷은 다양한 네트워크를 연결할 수 있고, 신뢰성 같은 추가 기능은 필요에 따라 TCP나 애플리케이션이 맡는다.

### 네트워크 접근 계층

네트워크 접근 계층은 실제 연결된 네트워크 구간에서 데이터를 전달한다. Ethernet 유선 LAN, Wi-Fi 같은 기술이 여기에 속한다.

이 계층에서는 데이터를 **프레임(frame)** 형태로 다루며, 가까운 다음 장비까지 데이터를 전달하기 위해 MAC 주소를 사용한다.

예를 들어 내 노트북이 Wi-Fi 공유기를 통해 인터넷으로 나갈 때 첫 구간은 노트북과 공유기 사이의 Wi-Fi 링크다. 이 구간에서 프레임은 공유기의 MAC 주소를 목적지로 삼을 수 있다. 공유기는 IP 패킷을 확인한 뒤, 다음 네트워크 구간에 맞는 새로운 프레임으로 다시 감싸서 전달한다.

## 7. 캡슐화와 역캡슐화

### 캡슐화

**캡슐화(encapsulation)** 는 상위 계층의 데이터를 하위 계층이 자신의 제어 정보를 덧붙여 감싸는 과정이다.

브라우저가 서버에 HTTP 요청을 보낼 때 대략 다음과 같이 진행된다.

1. 응용 계층: HTTP 요청 메시지를 만든다.
2. 전송 계층: TCP가 출발지·목적지 포트, 순서 정보 등을 담은 헤더를 붙인다.
3. 인터넷 계층: IP가 출발지·목적지 IP 주소를 담은 헤더를 붙인다.
4. 네트워크 접근 계층: Ethernet 또는 Wi-Fi가 현재 링크의 MAC 주소 정보를 담아 프레임을 만든다.
5. 네트워크 장치가 비트 신호로 변환하여 전송한다.

각 계층이 붙이는 정보는 해당 계층의 문제를 해결하기 위한 것이다. HTTP는 어떤 웹 리소스를 요청하는지 표현하고, TCP는 어떤 프로그램으로 전달할지와 신뢰성을 다루며, IP는 어느 장비로 갈지 결정하고, 링크 계층은 바로 다음 장비까지 전달한다.

### 역캡슐화

서버에 데이터가 도착하면 반대 과정이 일어난다.

1. 네트워크 인터페이스가 프레임을 받는다.
2. 링크 계층이 자신의 MAC 주소와 프레임 형식을 확인한다.
3. 인터넷 계층이 목적지 IP 주소를 확인한다.
4. 전송 계층이 목적지 포트 번호를 확인해 적절한 프로그램으로 전달한다.
5. 웹 서버가 HTTP 요청을 읽고 처리한다.

서버가 응답을 만들면 동일한 원리로 다시 캡슐화하여 클라이언트로 보낸다.

## 8. 실제 웹 요청 흐름

사용자가 브라우저 주소창에 다음 주소를 입력했다고 가정하자.

```txt
<https://shop.example.com/products>
```

전체 흐름은 단순히 “브라우저가 서버에 요청한다”보다 훨씬 길다.

1. 브라우저는 `shop.example.com`의 IP 주소를 알아내야 한다.
2. 브라우저는 서버의 IP 주소와 서비스 포트를 대상으로 연결을 준비한다.
3. 브라우저는 HTTP 요청을 만든다.
4. 운영체제의 네트워크 기능이 TCP, IP, 링크 계층 정보를 순서대로 붙인다.
5. 내 컴퓨터는 로컬 네트워크의 공유기 또는 게이트웨이로 프레임을 보낸다.
6. 여러 라우터가 목적지 IP 주소를 기준으로 패킷을 전달한다.
7. 서버의 운영체제가 받은 데이터를 목적지 포트에 연결된 웹 서버 프로세스로 전달한다.
8. 웹 서버는 HTTP 요청을 해석하고 필요한 처리를 수행한다.
9. 서버는 HTTP 응답을 만들고 반대 경로로 전송한다.
10. 브라우저는 응답을 받아 화면을 렌더링한다.

> 🔭 **미리보기: DNS**
>
> DNS는 `shop.example.com`처럼 사람이 읽는 도메인 이름을 IP 주소로 변환하는 분산 시스템이다. 이름 해석 과정과 캐시는 DNS 학습에서 자세히 다룬다.

> 🔭 **미리보기: TLS**
>
> HTTPS의 `S`는 TLS를 사용한다는 뜻이며, TLS는 서버 신원을 검증하고 통신 내용을 암호화한다. 인증서와 핸드셰이크는 HTTPS·웹 보안 학습에서 자세히 다룬다.

## 9. HTTP 메시지 예시

브라우저가 서버에 보내는 HTTP 요청은 응용 계층 데이터다. 단순화한 HTTP/1.1 요청은 다음과 같다.

```txt
GET /products HTTP/1.1
Host: shop.example.com
Accept: text/html
User-Agent: Mozilla/5.0
```

각 줄의 의미는 다음과 같다.

- `GET /products HTTP/1.1`: `GET` 메서드로 `/products` 리소스를 요청한다.
- `Host: shop.example.com`: 하나의 서버 IP에서 여러 웹 사이트를 운영할 수 있으므로, 어떤 호스트를 원하는지 지정한다.
- `Accept: text/html`: 클라이언트가 받을 수 있는 응답 형식을 알린다.
- `User-Agent`: 요청을 보낸 클라이언트의 종류와 특성을 전달할 수 있다.

이 HTTP 메시지는 그대로 인터넷을 떠다니는 것이 아니다. 전송 중에는 TCP 세그먼트, IP 패킷, 링크 프레임으로 차례로 감싸진다.

```txt
[Ethernet 또는 Wi-Fi 헤더]
  [IP 헤더]
    [TCP 헤더]
      [HTTP 요청 메시지]
```

수신 서버는 반대로 링크 프레임, IP 정보, TCP 정보를 차례로 처리한 뒤 HTTP 메시지를 웹 서버 프로그램에 전달한다.

## 10. 계층별 장애 분석

문제가 발생했을 때 가장 유용한 질문은 “어느 계층의 문제인가?”다. 아래는 대표적인 증상과 확인 방향이다.

| 증상 | 우선 의심할 범위 | 확인 관점 |
| --- | --- | --- |
| Wi-Fi 자체에 연결되지 않음 | 네트워크 접근 계층 | 무선 연결 상태, 공유기, 케이블, 네트워크 인터페이스 |
| IP 주소는 알지만 서버에 도달하지 못함 | 인터넷 계층 | 라우팅, 방화벽, 서버 네트워크, 목적지 IP |
| 서버 IP에는 도달하지만 특정 서비스만 연결 실패 | 전송 계층 | 포트 개방 여부, 서버 프로세스 실행 여부, 방화벽 규칙 |
| 연결은 되었지만 API가 500 오류를 응답 | 응용 계층 | 서버 코드, 데이터베이스, HTTP 요청 형식, 애플리케이션 로그 |
| 도메인으로는 접속 실패하지만 IP로는 접속 가능 | 이름 해석 단계 | DNS 레코드, DNS 서버, 캐시 |

예를 들어 브라우저에서 “사이트에 연결할 수 없음”이 나타났다고 해서 웹 서버 코드만 확인하면 안 된다. DNS, 라우팅, 포트, TLS, HTTP 응답 등 단계별로 범위를 좁혀야 한다.

## 11. 흔한 오해와 주의점

### “IP 주소는 컴퓨터 한 대의 고유 번호다”

항상 그렇지는 않다. IP 주소는 네트워크 인터페이스 또는 네트워크 연결 지점에 할당되며, DHCP 환경에서는 바뀔 수 있다. 또한 공유기 뒤의 여러 기기는 사설 IP를 사용하고 외부 인터넷에서는 하나의 공인 IP로 보일 수 있다.

### “포트 번호는 서버마다 하나뿐이다”

하나의 서버는 여러 포트를 사용할 수 있고, 같은 포트 번호를 사용하는 서비스도 서로 다른 IP 주소에 존재할 수 있다. 실제 통신의 종점은 보통 IP 주소와 포트 번호의 조합으로 생각해야 한다.

### “TCP/IP 4계층은 실제 장비의 구성과 정확히 일치한다”

계층 모델은 역할을 나누어 이해하기 위한 추상화다. 실제 운영체제, NIC, 라우터, 프록시, 브라우저는 여러 계층의 기능을 함께 수행할 수 있다.

### “패킷은 출발지부터 목적지까지 항상 같은 길로 간다”

인터넷 경로는 네트워크 상태와 라우팅 정책에 따라 달라질 수 있다. 요청과 응답도 반드시 같은 경로를 왕복하지는 않는다.

### “TCP를 사용하면 어떤 문제도 발생하지 않는다”

TCP는 손실과 순서 문제를 다루지만, 서버 장애, 잘못된 DNS 설정, 방화벽 차단, 애플리케이션 오류, 너무 긴 응답 시간까지 자동으로 해결하지는 않는다.

## 12. 보안·성능·운영 관점

### 보안 관점

포트가 열려 있다는 것은 외부 또는 내부 네트워크에서 특정 프로그램에 연결할 수 있다는 뜻이다. 필요하지 않은 포트를 공개하면 공격 표면이 커질 수 있으므로, 방화벽과 보안 그룹으로 허용할 접근을 제한해야 한다.

IP 주소와 포트만으로 상대방의 신원을 보장할 수는 없다. HTTPS 환경에서는 TLS 인증서를 통해 접속한 서버가 의도한 서버인지 검증하고, 통신 내용이 중간에 노출되거나 변조되는 위험을 줄인다.

### 성능 관점

웹 요청 시간은 서버 코드 실행 시간만으로 결정되지 않는다. DNS 조회, 연결 설정, 네트워크 왕복 시간(RTT), 전송할 데이터의 크기, 패킷 손실, 서버 처리 시간이 모두 영향을 준다.

특히 물리적 거리가 멀수록 RTT가 커질 수 있다. 작은 API 응답이라도 여러 번 왕복해야 하는 구조라면 사용자가 느끼는 지연이 커진다.

### 운영·디버깅 관점

문제를 분석할 때는 계층을 따라 확인한다.

1. 네트워크 연결이 있는지 확인한다.
2. 도메인 이름이 올바른 IP 주소로 해석되는지 확인한다.
3. 목적지 IP까지 경로가 있는지 확인한다.
4. 목적지 포트가 열려 있고 서버 프로세스가 실행 중인지 확인한다.
5. HTTP 요청과 응답, 서버 로그를 확인한다.

브라우저 개발자 도구의 Network 패널은 응용 계층의 HTTP 요청·응답을 관찰하는 데 유용하다. 반면 DNS나 TCP 연결 실패는 브라우저 메시지, 운영체제 네트워크 진단, 서버 및 인프라 로그를 함께 확인해야 원인을 찾을 수 있다.

## 13. 핵심 정리

> ✅ - 네트워크는 장치들이 프로토콜이라는 공통 규칙에 따라 데이터를 주고받는 구조다.

- 인터넷은 여러 독립된 네트워크가 라우터로 연결된 네트워크들의 네트워크다.
- IP 주소는 인터넷에서 목적지 장비 또는 인터페이스를 찾는 데 사용되고, 포트 번호는 그 장비 안의 프로그램을 찾는 데 사용된다.
- TCP/IP 모델은 응용, 전송, 인터넷, 네트워크 접근 계층으로 역할을 나눈다.
- HTTP 요청은 응용 계층의 데이터이며, TCP·IP·링크 계층 정보로 감싸져 네트워크를 통과한다.
- 장애는 “사이트가 안 된다”로 보이더라도 DNS, IP, 포트, TCP, HTTP 등 서로 다른 계층에서 발생할 수 있다.

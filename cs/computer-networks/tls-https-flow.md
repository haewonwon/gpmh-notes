**학습 범위**: Track C · Network / HTTP · TLS / HTTPS 동작 흐름 기초

일반적인 인증서 기반 TLS 1.3 전체 핸드셰이크와 HTTP/1.1·HTTP/2의 HTTPS 연결을 기준으로 설명한다. TLS 1.2·재개 연결·HTTP/3는 차이를 명시하며 암호 알고리즘의 수학적 구현은 다루지 않는다.
</callout>

## 1. 학습 목표

- 기밀성·무결성·상대 인증이 필요한 위협을 설명한다.
- TCP 연결과 TLS 핸드셰이크, HTTP 교환을 구분한다.
- 인증서·공개키·서명·키 합의·대칭키의 역할을 설명한다.
- TLS 1.3의 일반적인 메시지 순서와 인증서 검증을 복원한다.
- 인증서 장애·보안 종료 지점·연결 준비 시간을 분석한다.

## 2. 이 주제를 왜 배우는가

네트워크 경로에 있는 장비가 통신 내용을 읽거나 바꿀 수 있다고 가정해 보자. IP 주소로 서버에 도달하고 TCP로 바이트 순서를 맞추는 것만으로는 그 서버가 의도한 상대인지, 받은 메시지가 중간에 바뀌지 않았는지 확인할 수 없다.

**TLS(Transport Layer Security)** 는 통신 상대를 인증하고 전송 데이터의 기밀성과 무결성을 보호하는 보안 프로토콜이다. HTTPS는 HTTP를 이런 보호된 통신으로 사용하는 방식이다. 올바른 상대 검증과 안전한 키 관리가 이루어져야 암호화의 목적이 성립한다.

## 3. 공개키·서명·대칭키·키 합의를 구분한다

| 개념 | 기본 역할 | 이 페이지의 TLS 연결에서 쓰임 |
| --- | --- | --- |
| 공개키·개인키 | 공개 정보와 비밀 정보가 서로 다른 비대칭 암호 재료 | 서버의 인증과 서명 검증 |
| 디지털 서명 | 개인키 보유자가 만든 서명을 공개키로 검증 | 인증서·협상 내용의 진위 확인 |
| 대칭키 암호 | 양쪽이 공유한 비밀 키로 효율적으로 데이터 보호 | HTTP 데이터의 암호화와 무결성 보호 |
| 키 합의 | 비밀 키 자체를 그대로 보내지 않고 공통 비밀 재료 도출 | 세션별 보호 키를 만들 준비 |

공개키는 공개해도 되는 값이며 개인키는 비밀로 지켜야 한다. 인증서에 서버 개인키를 넣어 보내는 것이 아니다. 또 “개인키로 HTTP 본문을 암호화하고 누구나 공개키로 푼다”는 설명은 TLS의 기밀성 보호 방식이 아니다.

일반적인 TLS 1.3 전체 핸드셰이크에서는 임시 Diffie-Hellman 계열 키 합의로 공유 비밀을 만들고 여기서 방향·단계별 보호 키를 도출한다. 서버 인증서의 키는 이 협상에 대한 서명 검증에 쓰인다. HTTP 바이트마다 공개키 암호 연산을 하는 구조가 아니다. [RFC 8446 §2](https://www.rfc-editor.org/rfc/rfc8446.html#section-2) 참조.

## 4. 인증서와 신뢰 체인

**인증서(certificate)** 는 서버 이름·공개키·유효 기간 등을 서명으로 연결한 문서다. **인증 기관(CA)** 은 이런 연결을 검증하고 서명하는 주체이며, 브라우저나 운영체제는 신뢰하는 루트 목록을 바탕으로 인증 경로를 검증한다.

```text
클라이언트가 신뢰하는 루트
  -> 중간 CA 인증서 검증
  -> 서버 인증서 검증
  -> 요청한 서버 이름·기간·용도 등 확인
```

서버는 필요한 중간 인증서와 서버 인증서를 제공해야 한다. 서버가 어떤 루트 인증서를 보냈다는 이유만으로 클라이언트가 새로 신뢰하는 것은 아니다. 신뢰의 출발점은 클라이언트의 정책과 신뢰 저장소다.

브라우저는 요청한 호스트 이름이 인증서의 SAN(Subject Alternative Name)에 적절하게 포함되는지 확인한다. 유효 기간·서명·인증 경로·용도 등도 검증한다. 신뢰할 수 있는 CA가 서명했어도 다른 이름의 인증서는 현재 접속 상대를 증명하지 못한다. [RFC 9525](https://www.rfc-editor.org/rfc/rfc9525.html)는 서버 신원 검증을 규정한다.

## 5. 관련 계층과 세 단계의 연결 준비

HTTP/1.1 또는 HTTP/2를 사용하는 새 HTTPS 연결은 보통 다음 순서다.

```text
DNS: 이름에 대응하는 주소 찾기
TCP: 주소·포트의 양방향 연결 상태 만들기
TLS: 서버 인증·키 준비·협상 무결성 확인
HTTP: 보호된 연결 안에서 요청·응답 교환
```

TLS는 실제 요청 경로를 라우팅하거나 주문을 저장하지 않는다. TCP 연결 성공 뒤 TLS 검증에서 실패할 수 있고 TLS 성공 뒤 HTTP 권한 검사에서 거절될 수도 있다. HTTP/3는 QUIC 안에 TLS 기반 보안 협상이 통합되어 있어 앞에 별도 TCP Handshake를 붙이지 않는다.

## 6. TLS 1.3 전체 핸드셰이크의 실제 흐름

아래는 일반적인 서버 인증서 기반 연결이며 클라이언트 인증서와 재개·조기 데이터는 생략했다. 각 줄은 논리적인 TLS 메시지로 실제 패킷 하나와 일대일 대응하지 않는다.

```text
클라이언트                                      서버
ClientHello ------------------------------->
  지원 버전·알고리즘·키 공유 정보 등
                 <---------------- ServerHello
                                      선택 결과·키 공유 정보
                 <---------------- EncryptedExtensions
                 <---------------- Certificate
                 <---------------- CertificateVerify
                 <---------------- Finished
인증서·서명·Finished 검증
Finished ---------------------------------->
암호화된 HTTP 데이터 <---------------------> 암호화된 HTTP 데이터
```

1. **ClientHello**에서 클라이언트가 지원하는 버전·암호 조합과 키 합의에 필요한 정보를 제안한다.
2. **ServerHello**에서 서버가 선택 결과와 자신의 키 공유 정보를 보낸다. 양쪽은 공유 비밀 재료에서 협상 보호 키를 도출할 수 있다.
3. **EncryptedExtensions**는 선택된 추가 설정을 알린다. TLS 1.3에서는 이 단계와 인증서 등 이후의 주요 협상 메시지가 암호화된다.
4. **Certificate**는 서버의 인증서 체인을 제공한다. 클라이언트는 이름과 신뢰 경로 등을 검증한다.
5. **CertificateVerify**는 서버가 인증서 공개키에 대응하는 개인키를 보유하고 이번 협상에 참여했음을 서명으로 증명한다.
6. **Finished**는 협상 기록의 무결성과 필요한 키 보유를 확인한다. 클라이언트도 검증 뒤 자신의 Finished를 보내고 애플리케이션 데이터를 보호해 주고받는다.

서버가 추가 키 공유 정보를 요구하는 HelloRetryRequest 같은 변형도 있다. TLS 1.2는 메시지와 키 교환 조합이 다르므로 이 순서를 모든 TLS 버전에 그대로 적용하지 않는다.

## 7. 서버 이름 선택과 HTTP 프로토콜 선택

하나의 IP에서 여러 HTTPS 호스트를 운영하면 HTTP 요청의 Host를 읽기 전에 어떤 인증서를 제시할지 결정해야 한다. **SNI(Server Name Indication)** 는 클라이언트가 TLS 협상에 서버 이름을 알리는 확장이다. HTTP Host와 관련은 있지만 전달 단계와 역할이 다르다.

**ALPN(Application-Layer Protocol Negotiation)** 은 TLS에서 사용할 응용 프로토콜을 합의하는 확장이다. 예를 들어 서버와 클라이언트가 지원하는 경우 `h2`를 선택해 HTTP/2를 사용하거나 `http/1.1`을 사용할 수 있다. TLS 버전과 HTTP 버전은 별도로 협상·해석한다.

일반적인 암호화되지 않은 ClientHello의 SNI는 중간에서 보일 수 있다. HTTPS가 IP·포트·패킷 크기·타이밍까지 모두 숨기는 것도 아니다. 서버 이름을 추가로 보호하는 협상 방식의 적용 여부는 별도 조건이며 HTTP 본문 암호화와 구분한다.

## 8. TLS 레코드와 HTTP 메시지의 관계

TLS는 상위 데이터를 **레코드(record)** 단위로 보호한다. 레코드 하나가 HTTP 메시지 하나이거나 TCP 세그먼트 하나라는 보장은 없다. 큰 메시지는 나뉠 수 있고 여러 데이터가 전송 중 재구성될 수 있다.

```text
HTTP 요청 바이트
  -> TLS 레코드로 보호
  -> TCP 바이트 스트림으로 전송
  -> 서버에서 TLS 검증·복호화
  -> HTTP 파서가 메시지 해석
```

브라우저 Network 패널에는 복호화한 HTTP 정보가 보인다. 반면 외부 패킷 캡처는 일반적으로 보호된 레코드를 관찰한다. 운영상의 복호화 디버깅에서는 키 재료와 평문이 노출될 수 있으므로 캡처 파일의 취급 범위도 확인해야 한다.

## 9. 연결 재개·순방향 비밀성·0-RTT

**연결 재개(resumption)** 는 이전 협상에서 얻은 티켓·비밀 재료를 이용해 새 연결 준비를 줄이는 방식이다. 같은 연결을 계속 쓰는 Keep-Alive와 다르며, 사용자의 로그인 세션과도 다르다. 재개되었다고 로그인했다는 뜻은 아니다.

임시 키 합의를 적절히 사용하는 연결에서는 서버의 장기 인증 개인키가 나중에 유출되더라도 과거에 캡처한 데이터의 복호화를 어렵게 하는 **순방향 비밀성(forward secrecy)** 을 얻을 수 있다. 모든 TLS 모드가 같은 성질을 갖는다고 일반화하지 말고 협상 방식과 키 관리 조건을 본다.

TLS 1.3의 **0-RTT 조기 데이터**는 일부 재개 연결에서 협상 완료 전 데이터를 보내 지연을 줄이는 선택 기능이다. 일반 데이터와 다른 재전송·재생 공격 위험이 있으므로 결제 같은 작업을 무조건 조기 데이터로 허용하면 안 된다. 서버와 애플리케이션이 재생에 대한 안전성을 판단해야 한다. [RFC 8446 §8](https://www.rfc-editor.org/rfc/rfc8446.html#section-8) 참조.

## 10. 인증서 오류와 연결 로그 해석

다음은 특정 도구의 실제 출력이 아닌 설명용 로그다.

```text
TCP connected: 203.0.113.10:443
TLS version: TLSv1.3
ALPN selected: h2
Certificate name check: failed
HTTP request: not sent
```

이 경우 TCP 연결은 되었지만 서버 신원 검증을 통과하지 못했으므로 정상 HTTP 교환 전에 중단한 것이다. 웹 서버의 API 처리 코드를 먼저 고치기보다 접속 이름·SNI·인증서 SAN·앞단 가상 호스트 구성을 조사한다.

| 증상 | 먼저 확인할 내용 |
| --- | --- |
| 이름 불일치 | URL 호스트, SNI, 인증서 SAN, 잘못 연결된 프록시 |
| 만료·아직 유효하지 않음 | 인증서 기간, 클라이언트·서버 시간 |
| 신뢰 경로 실패 | 중간 인증서 누락, 클라이언트 신뢰 저장소 |
| 협상 실패 | 양쪽 버전·알고리즘·보안 정책, 서버 오류 로그 |
| TLS 성공 후 HTTP 오류 | 요청 형식, 인증·권한, 애플리케이션·업스트림 |

`curl -v https://example.com/`이나 브라우저의 보안 정보를 통해 검증 결과와 사용 프로토콜을 관찰할 수 있다. 검증을 끄는 옵션으로 접속이 된다는 사실은 신원 검증 문제가 해결됐다는 뜻이 아니다.

## 11. 보안 종료 지점과 운영 책임

```text
브라우저 -- TLS 연결 A --> 로드 밸런서 -- 연결 B --> 서버
```

로드 밸런서에서 복호화하면 연결 A의 TLS 보호는 그 지점까지다. 연결 B를 평문으로 할지 별도 TLS로 보호할지 결정하고 내부 신뢰 경계를 확인한다. 연결 B도 TLS라면 그 구간의 서버 검증과 인증서 관리가 따로 필요하다.

일반적인 HTTPS에서 인증하는 것은 서버다. 클라이언트 인증서를 쓰는 상호 TLS는 별도 설정이며, 일반 사용자 로그인·권한 검사를 대신한다고 단정하면 안 된다. 서버 개인키·세션 티켓 키를 비밀로 보관하고 인증서 자동 갱신과 배포 후 실제 제공 체인을 확인한다.

## 12. 성능을 단계별로 관찰하기

새 직접 TCP 기반 HTTPS 연결을 측정할 때 curl의 시간 항목을 사용할 수 있다.

```bash
curl -sS -o /dev/null -w 'dns=%{time_namelookup}\nconnect=%{time_connect}\ntls=%{time_appconnect}\nfirst=%{time_starttransfer}\ntotal=%{time_total}\n' https://example.com/
```

이 값들은 대체로 시작부터 해당 단계까지의 누적 시간이다. 단순한 새 직접 연결에서는 `time_appconnect - time_connect`를 TLS 준비 구간을 살펴보는 근사로 사용할 수 있다. DNS·TCP·TLS 시간을 모두 개별 소요 시간이라고 더하면 중복 계산한다.

프록시·리다이렉트·재사용·HTTP/3가 끼면 해석 조건이 달라진다. TLS 1.3의 일반적인 협상은 TLS 자체의 왕복을 줄이지만 DNS·TCP·서버 처리 시간이 사라지는 것은 아니다. Keep-Alive·재개·응답 크기·서버 지연을 함께 측정한다.

## 13. 흔한 오해와 핵심 정리

- **인증서 공개키로 HTTP 전체를 계속 암호화한다**: 일반적인 TLS 1.3은 키 합의와 인증 뒤 도출한 대칭 보호 키를 사용한다.
- **인증서가 유효하면 어떤 호스트로 접속해도 된다**: 요청한 서버 이름도 맞아야 한다.
- **TLS 세션 재개는 로그인 복구다**: 전송 보안 상태와 사용자 로그인은 별개다.
- **HTTPS는 모든 중간 구간과 종점 데이터를 보호한다**: 실제 종료 지점과 서버 내부 처리는 따로 확인한다.

TLS의 핵심은 키를 준비하는 과정과 상대·협상 기록을 검증하는 과정을 함께 수행하는 것이다. 검증된 보호 구간 안에서 HTTP를 교환하며, 장애 분석도 DNS·TCP·TLS·HTTP의 진행 단계를 구분한다.
</callout>

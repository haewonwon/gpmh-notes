**학습 범위**: Track C · Network / HTTP · DNS

도메인 이름에 대응하는 정보를 찾는 과정을 분산된 이름 공간·리졸버·권한 서버·캐시로 설명한다. 예시 응답은 학습용이며 실제 DNS 조회 결과가 아니다.
</callout>

## 1. 학습 목표

- DNS가 저장하는 정보와 IP 전달의 책임을 구분한다.
- 재귀 리졸버, 루트·TLD·권한 서버의 역할을 설명한다.
- A·AAAA·CNAME·NS·TTL과 주요 응답 상태를 읽는다.
- 변경 전후의 캐시 차이와 DNS 단계의 장애를 분석한다.

## 2. 이 주제를 왜 배우는가

사람은 `shop.example.com` 같은 이름으로 서비스를 기억하지만 네트워크는 IP 주소를 사용해 패킷을 전달한다. 서버 주소가 바뀔 때마다 모든 사용자가 새 IP를 외우는 방식은 유지하기 어렵다. **DNS(Domain Name System)** 는 이름과 관련 정보를 분산해 관리하고 조회하는 시스템이다.

도메인만 접속되지 않거나 DNS 변경 뒤 일부 사용자만 옛 서버로 가는 현상은 서버 코드를 고쳐도 해결되지 않는다. 이름의 정보를 누가 관리하고, 누가 대신 찾아 주며, 누가 결과를 보관하는지 구분해야 한다.

## 3. 도메인 이름과 계층적 이름 공간

도메인 이름은 점으로 구분된 **레이블(label)** 로 구성된다. `shop.example.com.`을 오른쪽부터 보면 루트 `.`, 최상위 도메인인 `com`, 그 아래 `example`, 그 아래 `shop`으로 이어진다. 끝의 점은 완전한 이름을 나타내며 일반적인 URL에서는 생략한다.

DNS 전체를 하나의 서버가 저장하지 않는다. 상위 영역은 하위 영역을 담당하는 서버를 가리키도록 **위임(delegation)** 한다. **존(zone)** 은 어떤 권한 서버가 관리하는 DNS 데이터의 범위이며, 도메인 트리의 모든 하위 이름을 반드시 한 존이 담당하는 것은 아니다.

DNS 질문은 보통 이름·레코드 타입·클래스의 조합이다. 따라서 같은 이름에도 IPv4 주소를 묻는 질문과 메일 서버를 묻는 질문의 답이 다르다. URL 전체의 경로나 쿼리를 DNS에 전달하지 않는다.

## 4. 리졸버와 권한 서버의 역할

| 참여자 | 역할 |
| --- | --- |
| 클라이언트의 stub resolver | 운영체제 등을 통해 이름 조회를 요청 |
| 재귀 리졸버 | 클라이언트를 대신해 답을 찾고 캐시 |
| 루트 이름 서버 | 해당 TLD를 담당할 서버 정보로 안내 |
| TLD 이름 서버 | 등록된 도메인의 권한 서버 정보로 안내 |
| 권한 이름 서버 | 자신이 담당하는 존의 레코드를 제공 |

브라우저와 운영체제에는 자체 캐시나 다른 조회 경로가 있을 수 있다. 브라우저가 설정된 보안 DNS 리졸버를 쓰면 운영체제 기본 조회와 결과가 다를 수도 있다. 아래 흐름은 일반적인 재귀 리졸버를 이용하며 필요한 캐시가 없는 경우를 단순화한 것이다.

## 5. 재귀 질의와 반복 질의의 실제 흐름

```text
클라이언트 -> 재귀 리졸버: shop.example.com의 A 레코드를 찾아 줘
재귀 리졸버 -> 루트: com의 담당 서버 안내
재귀 리졸버 -> com TLD: example.com의 권한 서버 안내
재귀 리졸버 -> 권한 서버: shop.example.com의 A 응답
재귀 리졸버 -> 클라이언트: 최종 결과 반환
```

**재귀 질의**는 상대가 최종 답이나 오류를 찾아 돌려주길 요청하는 방식이다. **반복 질의**에서는 서버가 자신이 아는 답이나 다음에 물어볼 서버 정보를 주고, 질의한 쪽이 다음 단계를 진행한다. 보통 클라이언트는 재귀 리졸버에 맡기고 리졸버가 계층을 따라 반복적으로 조회한다.

캐시에 위임 정보나 최종 답이 남아 있다면 일부 단계는 생략된다. 브라우저가 페이지를 열 때마다 루트부터 모든 서버를 방문하는 것은 아니다. 루트 서버가 개별 사이트의 모든 IP 주소를 알려 주는 것도 아니다. [RFC 1034 §4.3](https://www.rfc-editor.org/rfc/rfc1034.html#section-4.3) 참조.

## 6. 자주 보는 레코드와 DNS가 하지 않는 일

| 타입 | 담는 정보 | 예시 의미 |
| --- | --- | --- |
| A | IPv4 주소 | 이름을 `203.0.113.10`에 대응 |
| AAAA | IPv6 주소 | 이름을 `2001:db8::10`에 대응 |
| CNAME | 다른 이름에 대한 별칭 | `shop`을 다른 정식 이름으로 연결 |
| NS | 존의 권한 이름 서버 | 어느 서버가 해당 존을 담당하는지 안내 |
| MX | 메일 교환 서버 | 메일을 받을 서버와 우선순위 |
| TXT | 텍스트 데이터 | 서비스 소유 확인 등에서 사용 |

하나의 이름이 여러 주소를 가질 수 있고 여러 이름이 같은 주소를 가리킬 수도 있다. CNAME은 IP 주소가 아니라 다른 이름을 가리킨다. 따라서 별칭을 따라가 최종 주소를 찾아야 할 수 있다.

DNS가 주소를 알려 줬다는 것은 그 주소의 서버가 정상 수신 중이라는 뜻이 아니다. DNS는 TCP 연결, URL의 `/products` 처리, 사용자 인증을 수행하지 않는다. DNS 기반의 여러 주소 응답만으로 애플리케이션의 정교한 부하 분산이나 장애 감지가 자동 완성되는 것도 아니다.

## 7. TTL과 캐시, 변경이 한 번에 보이지 않는 이유

**TTL(Time To Live)** 은 레코드를 캐시에 보관할 수 있는 시간을 초 단위로 나타낸다. IP의 TTL이 홉 제한인 것과 용도가 다르다. 리졸버 캐시에서 반환된 TTL은 일반적으로 남은 시간으로 줄어든다.

권한 서버의 주소를 바꿔도 이미 캐시된 옛 답은 그 캐시의 남은 시간 동안 사용될 수 있다. TTL을 낮출 계획이라면 변경 전에 충분히 낮춰야 한다. 변경 순간 새 TTL만 낮춰도 이미 보관된 긴 TTL을 소급해서 줄이지는 못한다. 실제 갱신은 클라이언트 캐시·구현·장애 시 정책 등의 영향도 받는다.

존재하지 않는다는 응답도 캐시될 수 있다. 오타로 조회한 이름을 나중에 만들었는데 계속 실패한다면 **부정 캐시(negative cache)** 도 살펴본다. [RFC 2308](https://www.rfc-editor.org/rfc/rfc2308.html)은 이 동작을 설명한다.

## 8. 관련 계층과 전송 방식

DNS는 주소를 다루지만 TCP/IP 모델에서는 **응용 계층 프로토콜**이다. DNS 메시지는 TCP·UDP 같은 전송 계층과 IP를 이용해 전달된다. 주고받는 데이터의 내용과 계층의 역할을 혼동하지 않는다.

전통적인 DNS는 UDP 53을 자주 사용하지만 TCP 53도 필요하다. UDP 응답이 잘렸음을 나타내는 `TC` 비트를 받으면 TCP로 재시도할 수 있고, TCP를 처음부터 사용할 수도 있다. 따라서 UDP 53만 열면 모든 DNS가 동작한다고 가정하면 안 된다. [RFC 7766](https://www.rfc-editor.org/rfc/rfc7766.html) 참조.

DNS 조회 구간을 암호화하는 방식도 있지만 이는 접속 대상 웹 서버와의 HTTPS 연결과 별개다. 암호화와 상대 검증의 기본 원리는 커리큘럼의 TLS / HTTPS 동작 흐름 기초에서 다룬다.

## 9. DNS 응답과 진단 명령 예시

다음은 `dig shop.example.com A`와 비슷한 형태의 가상 응답이다.

```text
;; status: NOERROR
;; QUESTION SECTION:
;shop.example.com.          IN A
;; ANSWER SECTION:
shop.example.com.      300  IN CNAME edge.example.net.
edge.example.net.      60   IN A     203.0.113.10
```

질문은 `shop.example.com`의 A 레코드다. 첫 답은 별칭이며, 최종 IPv4 주소는 두 번째 레코드에 있다. `300`과 `60`은 각 레코드의 TTL이고 `IN`은 인터넷 클래스다. 서로 다른 레코드의 캐시 수명은 같을 필요가 없다.

| 결과 | 해석과 다음 확인 |
| --- | --- |
| NOERROR와 원하는 답 | 이름 조회는 성공, 실제 연결은 별도 확인 |
| NOERROR이나 답 없음 | 그 이름에 요청한 타입의 레코드가 없을 수 있음 |
| NXDOMAIN | 질의한 이름이 존재하지 않는다는 응답 |
| SERVFAIL | 서버가 처리 실패, 위임·검증·상위 조회 등 조사 |
| 응답 없음·타임아웃 | 리졸버 접근, 전송 경로, 방화벽 등을 조사 |

`dig example.com A`, `dig example.com AAAA`로 타입을 나누어 보고, `dig @1.1.1.1 example.com A`로 특정 리졸버의 결과를 비교할 수 있다. `dig +trace example.com`은 위임 경로를 관찰하는 데 도움이 되지만 브라우저의 캐시·보안 DNS 경로를 그대로 재현하지는 않는다.

## 10. 흔한 오해와 주의점

- **도메인 하나는 IP 하나다**: 여러 레코드와 여러 주소가 있을 수 있다.
- **DNS 변경은 전 세계에 파일이 복사되는 과정이다**: 권한 데이터 변경과 여러 캐시의 만료를 구분한다.
- **IP 직접 접속이 되면 DNS만 문제다**: 서비스가 호스트 이름에 따라 다르게 응답할 수도 있어 비교 조건을 맞춰야 한다.
- **HTTP 오류도 DNS 오류다**: 실제 HTTP 응답을 받았다면 적어도 그 응답을 준 상대까지 이름 조회와 연결은 진행된 것이다.

## 11. 보안·성능·운영·디버깅 관점

잘못된 DNS 정보는 사용자를 의도하지 않은 주소로 보낼 수 있다. **DNSSEC**는 서명으로 DNS 데이터의 출처와 무결성을 검증하는 체계이며 조회 내용을 숨기는 암호화 기능은 아니다. HTTPS의 서버 이름 검증도 별도로 필요하다.

운영에서는 변경 전 레코드·권한 서버·기존 TTL을 기록하고, 권한 응답과 재귀 리졸버의 캐시 응답을 나누어 확인한다. 사내망과 외부망에서 같은 이름에 다른 답을 주는 구성이 있을 수 있으므로 조회 위치도 함께 기록한다.

DNS 시간이 길면 HTTP 서버가 빨라도 최초 요청은 느리다. 캐시는 조회 횟수와 지연을 줄이는 대신 변경 반영을 늦출 수 있다. 낮은 TTL이 항상 좋은 것이 아니라 변경 대응 속도와 조회 부하 사이의 선택이다.

## 12. 핵심 정리

<callout icon="✅" color="green_bg">
DNS는 계층적으로 위임된 이름 정보를 리졸버가 찾아 주는 시스템이다. 권한 데이터, 캐시된 데이터, 조회 뒤의 실제 연결을 분리해서 보아야 한다.
</callout>

- 이름·레코드 타입에 따라 질문과 답이 달라진다.
- 리졸버는 캐시가 없을 때 필요한 권한 정보를 따라간다.
- TTL과 부정 캐시는 변경 전후의 서로 다른 결과를 설명한다.
- DNS 성공은 웹 서비스의 정상 처리까지 보장하지 않는다.

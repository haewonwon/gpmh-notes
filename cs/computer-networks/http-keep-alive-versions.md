## 1. 학습 목표

- HTTP 지속 연결과 TCP keepalive의 목적을 구분한다.
- HTTP 버전별 연결 재사용·동시 처리·손실 영향을 비교한다.
- Connection·Keep-Alive 헤더의 적용 범위를 설명한다.
- 요청 시간을 연결 준비·서버 대기·전송으로 나누어 관찰한다.

## 2. 이 주제를 왜 배우는가

화면 하나에 HTML·CSS·스크립트·이미지·API 요청이 필요하다고 하자. 요청마다 연결을 새로 만들면 데이터 전송 전에 TCP와 보안 연결을 준비하는 비용을 반복해서 낸다. 각 응답이 작아도 먼 서버와 여러 번 왕복하면 느려질 수 있다.

**지속 연결(persistent connection)** 은 한 연결을 여러 요청·응답에 재사용하는 방식이다. 연결 재사용은 준비 비용을 줄이고, 여러 요청을 효율적으로 함께 처리하는 전송 방식은 리소스 간 대기를 줄인다. HTTP 버전은 이 두 문제를 어떻게 해결하는지가 다르다.

## 3. HTTP Keep-Alive와 TCP keepalive

| 개념 | 목적 | 주로 다루는 정보 |
| --- | --- | --- |
| HTTP 지속 연결 | 후속 HTTP 교환에 연결 재사용 | HTTP 버전, 메시지 경계, 연결 정책 |
| HTTP의 Keep-Alive 헤더 | 일부 HTTP/1.x 구현의 연결 유지 힌트 | timeout·max 등 구현별 매개변수 |
| TCP keepalive | 오랫동안 조용한 TCP 상대의 생존 확인 보조 | TCP 탐침, 운영체제의 시간 설정 |

TCP keepalive가 켜졌다고 HTTP 요청을 계속 보낼 수 있는 것은 아니다. 프록시가 유휴 연결을 먼저 닫을 수도 있고 HTTP 계층이 종료를 결정할 수도 있다. 반대로 TCP keepalive를 쓰지 않아도 HTTP 연결을 재사용할 수 있다.

연결 재사용은 로그인 상태 유지와도 다르다. 연결이 새로 생겨도 로그인은 이어질 수 있고 한 연결에서 여러 요청이 오더라도 사용자를 식별할 정보가 따로 필요하다.

## 4. HTTP/1.0과 HTTP/1.1의 연결 정책

HTTP/1.0은 기본적으로 요청·응답 뒤 연결을 닫는 방식이다. 일부 구현은 keep-alive 확장으로 지속 연결을 사용한다. HTTP/1.1은 **기본적으로 지속 연결**이며, `Connection: keep-alive`를 매번 넣어야만 재사용할 수 있는 것이 아니다.

HTTP/1.1에서 한쪽이 `Connection: close`를 보내면 현재 교환 뒤 그 연결을 끝내겠다는 뜻이다. 지속 연결이어도 서버나 중간 장비는 정책·장애·자원 제한으로 닫을 수 있다. 클라이언트는 연결이 영원히 살아 있다고 가정하지 않는다.

연결을 재사용하려면 각 메시지의 끝을 알아야 한다. 본문을 읽지 않고 다음 응답으로 넘어가거나 잘못된 Content-Length를 사용하면 경계가 흐트러진다. [RFC 9112 §9.3](https://httpwg.org/specs/rfc9112.html#persistent.connections)는 연결 재사용과 본문 소비 조건을 설명한다.

## 5. HTTP/1.1의 순차 처리와 파이프라이닝

일반적인 HTTP/1.1 연결에서는 요청을 보내고 응답을 받은 뒤 다음 교환을 진행한다. 여러 리소스를 빨리 받기 위해 브라우저가 여러 연결을 사용할 수 있지만 연결 수와 자원 비용이 늘어난다.

**파이프라이닝(pipelining)** 은 앞선 응답을 기다리지 않고 같은 연결로 여러 요청을 연달아 보내는 방식이다. 그러나 응답은 요청 순서대로 보내야 하므로 앞 응답이 늦으면 뒤의 준비된 응답도 기다린다. 호환성과 처리 문제 때문에 일반적인 브라우저 HTTP/1.1 동작에서 널리 사용하는 해결책은 아니다.

```text
일반적 HTTP/1.1 연결
요청 A -> 응답 A -> 요청 B -> 응답 B

파이프라이닝
요청 A -> 요청 B -> 응답 A -> 응답 B
                         앞 응답 지연이 뒤 응답을 막을 수 있음
```

## 6. HTTP/2: 프레임과 스트림 다중화

HTTP/2는 메시지를 작은 **프레임(frame)** 으로 나누고 **스트림(stream)** 식별자로 각각의 교환을 구분한다. **다중화(multiplexing)** 는 한 연결에서 여러 스트림의 프레임을 섞어 보내 독립적인 교환을 진행하는 방식이다. 텍스트 응답 A 전체를 끝내야만 B를 보낼 수 있던 제약을 줄인다.

```text
하나의 TCP 연결
A의 헤더 -> B의 헤더 -> A의 데이터 일부 -> B의 데이터 -> A의 나머지
```

HTTP/2는 헤더 압축도 사용해 반복되는 헤더 전송량을 줄인다. 메서드·상태 코드·리소스라는 HTTP 의미는 유지되지만 실제 전송 형식은 HTTP/1.1 텍스트가 아니다.

그러나 TCP는 연결 전체를 하나의 순서 있는 바이트 스트림으로 제공한다. 중간 바이트가 손실되면 그 뒤의 다른 HTTP/2 스트림 데이터도 TCP 복구를 기다릴 수 있다. 이것이 전송 계층의 **선두 차단(head-of-line blocking)** 이다. 다중화가 모든 종류의 대기를 없애는 것은 아니다. [RFC 9113](https://httpwg.org/specs/rfc9113.html) 참조.

## 7. HTTP/3: QUIC 위의 HTTP

HTTP/3는 UDP 기반의 **QUIC**를 사용한다. QUIC는 UDP 위에서 연결 상태, 신뢰성 있는 스트림, 흐름·혼잡 제어와 TLS 기반 보안 협상을 제공한다. 따라서 “UDP이므로 HTTP 데이터가 빠져도 그대로 처리한다”는 해석은 잘못이다.

QUIC는 스트림별로 필요한 순서를 관리하므로 한 스트림의 데이터 손실이 다른 스트림의 전달을 TCP처럼 같은 바이트 순서 때문에 모두 막지는 않는다. 다만 연결이 공유하는 혼잡 제어, 경로 대역폭, 헤더 해석 의존성, 애플리케이션 자원 등의 영향은 남는다.

HTTP/3가 모든 환경에서 무조건 빠른 것은 아니다. 네트워크 손실, 서버·클라이언트 구현, 연결 재사용 여부, UDP 허용 정책이 결과를 바꾼다. QUIC가 차단된 경로에서는 지원 구성에 따라 HTTP/2 등 다른 방식으로 연결할 수 있다. [RFC 9114](https://www.rfc-editor.org/rfc/rfc9114.html)와 [RFC 9000](https://www.rfc-editor.org/rfc/rfc9000.html) 참조.

## 8. 버전별 비교와 계층 구분

| 항목 | HTTP/1.1 | HTTP/2 | HTTP/3 |
| --- | --- | --- | --- |
| 일반적인 기반 | TCP, HTTPS이면 TLS 추가 | TCP, 브라우저 웹에서는 보통 TLS | UDP 위의 QUIC, TLS 보안 통합 |
| 표현 | 텍스트 시작 줄·헤더와 본문 | 바이너리 프레임·스트림 | QUIC 스트림 위의 HTTP 프레임 |
| 연결 재사용 | 기본 지속 연결 | 연결 안의 여러 스트림 | QUIC 연결 안의 여러 스트림 |
| 요청 동시 진행 | 보통 여러 연결, 파이프라이닝에는 순서 제약 | 한 연결에서 다중화 | 한 연결에서 다중화 |
| 주요 손실 영향 | TCP 바이트 순서에 묶임 | 서로 다른 스트림도 TCP 복구 영향 | 스트림 간 전송 순서 차단 감소 |

HTTP 버전과 TLS 버전은 다른 축이다. HTTP/2를 쓴다고 TLS 1.2를 쓴다는 뜻은 아니며 HTTP/3의 숫자가 TLS 버전을 뜻하지도 않는다.

## 9. 헤더와 실제 연결 흐름 예시

HTTP/1.1에서 아래 응답은 본문 2바이트의 끝이 명확하며 `Connection: close`가 없다. 그 밖의 연결 조건이 맞으면 후속 교환에 재사용할 수 있다.

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 2

{}
```

다음 응답은 현재 응답 뒤 연결을 종료할 의사를 알린다.

```http
HTTP/1.1 200 OK
Content-Length: 0
Connection: close

```

`Connection`과 `Keep-Alive` 같은 연결 전용 헤더를 HTTP/2·HTTP/3 메시지에 그대로 추가하지 않는다. 각 버전은 자체 연결 관리 규칙을 사용한다. 프록시가 HTTP/1.1을 HTTP/2로 바꿀 때도 이런 필드를 정리해야 한다.

<callout icon="🔭" color="gray_bg">
**[미리보기: ALPN과 TLS 연결 준비]**

HTTPS 연결에서는 TLS 협상 과정의 ALPN으로 HTTP/1.1과 HTTP/2 같은 응용 프로토콜을 선택할 수 있다. 구체적인 협상 흐름은 커리큘럼의 TLS / HTTPS 동작 흐름 기초에서 다룬다.
</callout>

## 10. Network 패널과 시간 측정

브라우저 Network 패널에서 Protocol 열을 켜 `http/1.1`, `h2`, `h3`를 확인한다. 화면이 표시하는 버전은 브라우저와 접속 상대 사이의 구간이며 프록시 뒤 서버와의 버전은 다를 수 있다. 지원 여부만으로 실제 선택 버전을 추정하지 않는다.

첫 요청과 같은 대상의 후속 요청을 비교해 DNS·연결·TLS 시간이 반복되는지 살펴본다. 재사용한 요청에서는 준비 단계가 생략되어 보일 수 있으며, 브라우저 캐시에서 처리된 요청과 실제 연결 재사용은 구분한다.

**TTFB(Time To First Byte)** 는 첫 응답 바이트까지의 시간이다. 네트워크 왕복, 앞단 큐, 서버 처리 등이 섞일 수 있으므로 서버 함수 실행 시간과 같다고 해석하지 않는다. 측정 도구마다 시작 기준도 확인해야 한다.

## 11. 흔한 오해와 운영·보안·성능 관점

연결 풀은 재사용할 연결을 보관하는 구조다. 유휴 연결이 프록시에서 이미 닫혔는데 클라이언트 풀이 다시 쓰면 초기 실패가 생길 수 있다. 클라이언트·프록시·서버의 유휴 시간 제한과 재시도 정책을 함께 맞춘다. 비멱등 요청은 실패 시 무조건 다시 보내면 안 된다.

연결을 오래 유지하면 설정 비용은 줄지만 소켓·메모리·파일 디스크립터를 계속 사용한다. 연결 수 제한과 종료 정책이 필요하며 “모든 연결을 최대한 오래”가 항상 최적은 아니다. 다중화 연결 하나가 끊기면 그 안의 여러 요청이 영향을 받을 수도 있다.

버전 업그레이드가 큰 본문·느린 서버·불필요한 연속 요청을 자동으로 없애지는 않는다. 실제 병목이 연결 준비인지, 서버 처리인지, 전송량인지 측정한 뒤 개선 방향을 선택한다.

## 12. 핵심 정리

<callout icon="✅" color="green_bg">
연결 재사용은 준비 비용을 줄이고, HTTP/2·HTTP/3의 다중화는 여러 교환의 대기를 줄인다. HTTP/3는 스트림별 전달로 TCP가 공유하던 순서 제약도 줄인다.
</callout>

- HTTP/1.1은 기본적으로 지속 연결이다.
- HTTP 지속 연결과 TCP keepalive는 목적이 다르다.
- HTTP/2·HTTP/3에 HTTP/1.x의 연결 전용 헤더를 복사하지 않는다.
- 실제 사용 버전과 병목은 클라이언트·서버·구간별로 확인한다.

**학습 범위**: Track C · Network / HTTP · Cookie / Session

무상태 HTTP에서 요청들을 같은 로그인 상태로 연결하는 원리를 다룬다. 브라우저 쿠키와 서버에 상태를 저장하는 세션 방식이 중심이며, 토큰 인증 구현은 범위에 포함하지 않는다.
</callout>

<table-of-contents />

## 1. 학습 목표

- 쿠키의 저장·전송과 서버 세션의 상태 관리 책임을 구분한다.
- 로그인·후속 요청·로그아웃의 흐름을 메시지로 설명한다.
- Domain·Path·Secure·HttpOnly·SameSite의 역할과 한계를 구분한다.
- 세션 탈취·고정·위조 요청의 원리와 기본 방어를 설명한다.

## 2. 이 주제를 왜 배우는가

서버가 로그인 요청을 처리했다고 해도 다음 요청의 TCP 연결이 같다는 이유로 사용자를 식별할 수는 없다. 네트워크 연결은 닫히거나 바뀔 수 있고 여러 요청을 처리하는 서버도 달라질 수 있다. 로그인 결과를 후속 요청에 연결할 식별 정보가 필요하다.

**쿠키(cookie)** 는 서버가 브라우저에 저장하도록 요청하고 조건이 맞는 후속 요청에 브라우저가 전달하는 작은 이름·값 데이터다. **세션(session)** 은 여러 요청에 걸쳐 이어지는 애플리케이션 상태와 그 관리 단위다. 여기서는 브라우저가 세션 ID를 쿠키로 보내고 서버가 그 ID에 해당하는 상태를 찾는 방식을 살펴본다.

## 3. 쿠키와 세션의 역할 구분

| 대상 | 보관 위치·담는 정보 | 책임 |
| --- | --- | --- |
| 세션 ID 쿠키 | 브라우저, 추측하기 어려운 식별자 | 후속 요청에 식별자 전달 |
| 서버 세션 | 서버 측 저장소, 사용자 ID·만료 등 | 요청을 로그인 상태와 연결 |
| 인증 처리 | 서버 | 자격 증명을 검증하고 세션 생성 |
| 권한 검사 | 서버 | 현재 사용자의 대상 작업 허용 여부 판단 |

쿠키를 쓴다고 모두 로그인 데이터인 것은 아니다. 언어 설정이나 표시 선호도도 저장할 수 있다. 또 세션의 개념 자체가 반드시 쿠키에 종속되는 것도 아니다. 이 페이지는 가장 일반적인 브라우저 세션 ID 쿠키 모델을 기준으로 한다.

세션 ID는 서버 상태를 찾는 열쇠다. 비밀번호를 그대로 쿠키에 저장할 필요가 없으며, 서버가 신뢰할 사용자 ID를 브라우저가 임의로 적어 보내게 해서도 안 된다. 세션 ID를 얻은 공격자가 사용자를 가장할 수 있으므로 비밀 정보처럼 취급한다.

## 4. 로그인부터 후속 요청까지의 실제 흐름

```text
브라우저 -- 로그인 정보 --> 서버
서버: 자격 검증 -> 새 세션 ID 생성 -> 서버 세션 저장
브라우저 <-- Set-Cookie -- 서버
브라우저: 정책에 따라 쿠키 저장
브라우저 -- Cookie: 세션 ID --> 서버
서버: ID 조회 -> 만료·상태 확인 -> 권한 검사 -> 처리
```

서버는 암호학적으로 추측하기 어려운 세션 ID를 생성한다. 세션 데이터는 “ID에 대응하는 사용자, 만료 시간, 필요한 상태”처럼 관리할 수 있다. 클라이언트가 보낸 ID만 존재한다고 모두 승인하지 말고 유효한 서버 상태와 권한을 확인한다.

브라우저는 URL과 쿠키 속성, 요청 상황, 개인정보 정책 등을 적용해 쿠키를 보낸다. 서버가 Set-Cookie를 보냈다고 다음 모든 요청에 무조건 전달되는 것은 아니다.

## 5. Set-Cookie와 Cookie 헤더 읽기

다음은 HTTPS 로그인 응답에서 발췌한 가상 헤더다. `demo_random_id`는 설명용이며 실제 세션 ID 생성 규칙이 아니다.

```http
Set-Cookie: __Host-session=demo_random_id; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=1800
```

브라우저가 저장하고 전송 조건이 맞으면 후속 요청에는 다음처럼 이름·값을 보낸다.

```http
GET /me HTTP/1.1
Host: shop.example.com
Cookie: __Host-session=demo_random_id
```

`Secure`, `HttpOnly`, `SameSite` 같은 저장 속성을 Cookie 헤더에 그대로 되돌려 보내는 것은 아니다. 서버는 Set-Cookie로 저장·변경을 요청하고 브라우저는 Cookie로 해당 요청에 보낼 값을 전달한다. 여러 쿠키를 설정할 때는 Set-Cookie 필드를 각각 사용한다.

## 6. Domain·Path와 쿠키 전송 범위

**Domain을 생략**하면 일반적으로 설정한 호스트에만 보내는 host-only 쿠키가 된다. `shop.example.com`이 `Domain=example.com`을 설정하면 조건에 맞는 그 도메인과 하위 호스트들에 보낼 수 있어 범위가 넓어진다. 관계없는 도메인이나 공용 접미사에 마음대로 설정할 수는 없다.

**Path**는 요청 경로의 일치 조건이다. `Path=/account`는 그 경로 범위의 요청에 쿠키를 보내도록 제한한다. 그러나 Path는 악성 스크립트나 같은 사이트 내의 신뢰 경계를 격리하는 보안 장벽이 아니다.

쿠키는 포트별로 격리되지 않는다. 같은 호스트의 3000번과 8080번 서비스가 서로 완전히 분리된 쿠키 저장소를 가진다고 생각하면 안 된다. 서로 다른 신뢰 수준의 서비스를 배치할 때 호스트 범위도 고려한다.

예시의 `__Host-` 접두사는 이를 지원하는 브라우저에서 Secure, `Path=/`, Domain 생략을 요구한다. 이 조건은 쿠키 범위를 좁히는 데 도움을 주지만 세션 ID 유출이나 서버 권한 오류를 자동으로 막지는 않는다. [MDN Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie) 참조.

## 7. Secure·HttpOnly·SameSite가 막는 것

| 속성 | 주된 목적 | 해결하지 못하는 문제 |
| --- | --- | --- |
| Secure | HTTPS 같은 보호된 요청으로 전송 제한 | 종점 로그 노출·서버 침해·사용자 권한 오류 |
| HttpOnly | document.cookie 등 스크립트 API 접근 제한 | 악성 스크립트가 사용자 권한으로 요청하는 행위 전체 |
| SameSite | 사이트 간 요청에서 쿠키를 보낼 조건 제한 | 모든 위조 요청·같은 사이트의 공격·XSS |

**XSS**는 공격자 스크립트가 피해 사이트의 문맥에서 실행되는 취약점이다. HttpOnly는 쿠키 값을 직접 읽어 훔치기 어렵게 하지만 악성 코드가 브라우저를 통해 요청을 실행하는 것까지 없애지는 않는다.

SameSite의 **사이트(site)** 는 호스트 전체가 일치하는지와 다른 판단이다. 일반적으로 스킴과 등록 가능한 도메인을 기준으로 하므로 같은 사이트의 하위 도메인도 서로 다른 출처일 수 있다. `Strict`는 사이트 간 요청에 더 엄격하고, `Lax`는 일부 최상위 안전한 탐색 등을 허용하며, `None`은 사이트 간 전송을 허용하는 설정으로 Secure가 필요하다.

브라우저의 제3자 쿠키 제한이나 사용자 설정은 별도로 적용될 수 있다. `SameSite=None; Secure`만으로 모든 환경에서 사이트 간 쿠키가 전달된다고 보장하지 않는다.

## 8. 만료와 로그아웃은 양쪽 상태를 정리한다

**Max-Age**는 저장 수명을 초로, **Expires**는 만료 시각을 지정한다. 둘 다 있으면 Max-Age가 우선한다. 둘 다 없는 세션 쿠키의 종료 시점은 브라우저 세션과 복원 동작의 영향을 받으므로 “창을 닫으면 무조건 사라진다”로 판단하지 않는다.

브라우저 쿠키 수명과 서버 세션 유효 기간은 별개다. 쿠키가 남아 있어도 서버 세션이 만료되면 로그인이 끝날 수 있다. 유휴 만료와 절대 만료처럼 서버가 정책을 정하고 직접 검사해야 한다.

로그아웃에서는 서버 세션을 무효화하고 브라우저 쿠키도 삭제하도록 응답한다. 쿠키 삭제는 원래의 이름·Domain·Path 범위에 맞게 만료시키는 방식이다. 예시 host-only 쿠키의 삭제 헤더는 다음처럼 표현할 수 있다.

```http
Set-Cookie: __Host-session=; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=0
```

브라우저에서만 쿠키를 지우면 이미 복사된 ID가 서버에서 계속 유효할 수 있다. 서버에서만 무효화해도 낡은 쿠키가 불필요하게 남을 수 있으므로 양쪽 책임을 구분한다.

## 9. 세션 탈취·고정·CSRF의 위협 모델

**세션 탈취**는 공격자가 유효한 ID를 얻어 피해자 요청처럼 보내는 것이다. 평문 전송·XSS·로그 노출 등을 줄이고 ID를 URL에 넣지 않으며, 서버 만료와 필요 시 강제 무효화를 마련한다.

**세션 고정(session fixation)** 은 공격자가 알고 있는 ID를 피해자가 로그인 뒤에도 쓰도록 만드는 공격이다. 로그인이나 권한 상승 뒤에는 새 ID를 발급하고 이전 ID를 무효화한다. 단순히 쿠키 수명을 늘리는 것으로 해결하지 않는다.

**CSRF(Cross-Site Request Forgery)** 는 다른 사이트가 피해자의 브라우저를 이용해 의도하지 않은 작업 요청을 보내게 하는 공격이다. 브라우저가 조건에 맞는 인증 쿠키를 자동 첨부하기 때문에 공격자가 쿠키 값을 직접 읽지 못해도 시도할 수 있다. 상태를 바꾸는 요청에는 CSRF 토큰·Origin 확인·적절한 SameSite 정책 등의 방어를 적용하고 GET이 파괴적 작업을 수행하지 않게 한다.

이 방어들은 서로 목적이 다르다. Secure 하나, HttpOnly 하나로 모든 세션 공격이 사라지는 것은 아니다. [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) 참조.

## 10. 관련 계층과 브라우저 관찰 순서

쿠키 헤더는 응용 계층 정보다. TCP 연결 재사용이나 IP 주소가 세션 상태를 대신 전달하는 것은 아니다. HTTPS는 전송 중 값을 보호하며, 브라우저는 쿠키 저장·전송 정책을, 서버는 세션 유효성과 권한을 담당한다.

1. Network에서 로그인 응답의 Set-Cookie와 브라우저의 차단 이유를 확인한다.
2. 쿠키 저장소에서 이름·호스트·Path·만료·속성을 확인한다.
3. 후속 요청의 Cookie가 실제로 포함되었는지 본다.
4. 포함되었다면 서버에서 ID 조회·만료·권한 검사 결과를 확인한다.
5. 로그아웃 뒤 서버 무효화와 쿠키 삭제가 모두 되었는지 확인한다.

HttpOnly 쿠키가 document.cookie에 없다고 저장 실패는 아니다. 저장소·네트워크 화면으로 확인한다. 브라우저 자바스크립트에서 Set-Cookie 응답 헤더를 일반 헤더처럼 읽을 수 없는 것도 정책에 따른 동작이다.

## 11. 흔한 오해와 성능·운영 관점

세션 저장소가 서버 한 대의 메모리에만 있으면 다음 요청이 다른 서버로 가거나 서버가 재시작될 때 로그인 상태를 찾지 못할 수 있다. 여러 서버에서 세션을 어떻게 공유·일관되게 무효화할지 정해야 한다. 공유 저장소도 장애·지연·만료 관리가 필요하다.

브라우저는 조건에 맞는 쿠키를 반복해서 전송하므로 쿠키에 큰 데이터를 넣으면 요청량이 늘어난다. 저장량 제한도 브라우저마다 있으므로 최소한의 식별 정보만 유지하고 민감한 서버 상태는 서버에서 관리하는 것이 기본적인 선택이다.

세션 장애 로그에는 원본 ID를 그대로 남기지 않는다. 안전한 상관 식별 정보와 만료·조회 실패 사유를 사용한다. “자꾸 로그아웃됨”이라는 증상에서는 쿠키 차단, 세션 만료, 서버 간 상태 차이, 배포·재시작을 나누어 조사한다.

## 12. 핵심 정리

<callout icon="✅" color="green_bg">
쿠키는 브라우저의 저장·전송 장치이고 서버 세션은 로그인 상태를 찾고 검증하는 장치다. 전송 조건과 서버 유효성 검사를 함께 보아야 한다.
</callout>

- Set-Cookie와 Cookie는 방향과 담는 정보가 다르다.
- 쿠키 속성은 각각 다른 위협과 전송 범위를 제어한다.
- 브라우저 수명과 서버 세션 만료는 별개다.
- 로그인 시 ID 교체, 로그아웃 시 서버 무효화가 필요하다.

## 13. 이해도 확인 질문

1. 로그인 응답에 Set-Cookie가 있는데 후속 요청에 Cookie가 없다. 브라우저에서 어떤 조건과 화면을 확인해야 하는가?
2. HttpOnly 쿠키 값을 악성 스크립트가 읽지 못해도 XSS의 위험이 남는 이유는 무엇인가?
3. 브라우저 쿠키를 지웠지만 공격자가 복사한 ID는 계속 사용 가능했다. 로그아웃의 어떤 책임이 빠진 것인가?
4. 로그인 직후 세션 ID를 교체해야 하는 이유를 세션 고정 공격의 흐름으로 설명해 보라.

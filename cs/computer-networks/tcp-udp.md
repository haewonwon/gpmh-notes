**학습 범위**: Track C · Network / HTTP · TCP / UDP

IP 위에서 프로그램끼리 통신하는 방법을 살펴본다. TCP의 바이트 스트림과 UDP의 데이터그램, 신뢰성·지연·제어의 차이를 중심으로 다룬다.
</callout>

<table-of-contents />

## 1. 학습 목표

- IP와 전송 계층이 해결하는 문제를 구분한다.
- TCP의 스트림과 UDP의 메시지 경계를 설명한다.
- 손실 복구, 흐름 제어, 혼잡 제어의 목적을 구분한다.
- 통신 요구에 맞는 전송 방식을 판단하고 패킷 로그를 해석한다.

## 2. 이 주제를 왜 배우는가

IP는 목적지까지 패킷을 보내지만 손실되거나 순서가 바뀐 패킷을 애플리케이션에 맞게 복구해 주지는 않는다. 같은 장치에서 브라우저와 메신저가 동시에 통신할 때 수신 데이터를 어느 통신 종점으로 보낼지도 구분해야 한다. 이 역할을 IP 위의 **전송 계층**이 맡는다.

파일 다운로드에는 바이트 하나가 빠져도 문제가 생긴다. 반면 실시간 상태 갱신에서는 오래된 정보를 뒤늦게 받는 것보다 새 정보를 먼저 받는 편이 유용할 수 있다. 전송 프로토콜은 이런 요구에 필요한 기능과 비용을 결정한다.

## 3. 포트와 소켓, 연결의 식별

**포트**는 TCP·UDP 헤더에 들어가는 16비트 번호다. 운영체제는 프로토콜, 주소, 포트 등의 정보와 소켓 상태를 바탕으로 데이터를 전달한다. **소켓(socket)** 은 프로그램이 운영체제의 네트워크 기능을 사용하는 통신 인터페이스다.

예를 들어 TCP 연결은 보통 다음 네 값으로 식별한다.

```text
클라이언트 IP:포트       서버 IP:포트
192.0.2.20:53124  <-->  203.0.113.10:443
```

서버가 443번 포트 하나에서 수천 연결을 받을 수 있는 이유는 상대 주소·포트 조합이 다르기 때문이다. TCP 443과 UDP 443은 별도의 프로토콜 공간이며, 한쪽 허용이 다른 쪽 허용을 뜻하지 않는다.

## 4. TCP: 순서 있는 바이트 스트림

**TCP(Transmission Control Protocol)** 는 연결 상태를 유지하며 양쪽 프로그램에 신뢰성 있는 순서대로의 바이트 스트림을 제공한다. 스트림은 메시지 여러 개를 구분한 목록이 아니라 연속된 바이트의 흐름이다.

TCP는 각 바이트의 위치를 **시퀀스 번호**로 나타내고, 상대가 다음에 기대하는 바이트 위치를 **확인 응답(ACK)** 으로 알린다. 송신 측은 확인되지 않은 데이터를 보관하고 손실을 추정하면 재전송한다. 수신 측은 순서를 정리하고 중복 데이터를 처리한 뒤 프로그램에 전달한다. 연결이 끝내 복구되지 않으면 실패가 보고될 수 있다.

TCP가 확인하는 것은 상대 TCP 계층까지의 수신이다. ACK가 왔다고 주문이 데이터베이스에 저장되었거나 응답을 사용자에게 보여 주었다는 뜻은 아니다. 애플리케이션의 성공은 그 프로토콜의 응답으로 따로 확인한다. [RFC 9293 §2](https://www.rfc-editor.org/rfc/rfc9293.html#section-2) 참조.

## 5. 메시지 경계를 직접 정해야 하는 이유

프로그램이 `hello`와 `world`를 두 번 전송해도 수신 프로그램은 한 번에 `helloworld`를 받거나 `hel`, `lowor`, `ld`처럼 나누어 받을 수 있다. TCP는 송신 함수 호출의 경계를 보존하지 않는다.

그래서 상위 프로토콜은 길이 필드, 구분자, 정해진 프레임 형식으로 메시지 끝을 정한다. 다음은 길이를 붙이는 설명용 형식이다.

```text
송신 바이트: [길이 5][hello][길이 5][world]
수신 처리: 길이 읽기 -> 그 길이만큼 모으기 -> 메시지 해석
```

TCP 세그먼트 하나가 곧 요청 하나라는 가정은 잘못이다. 대용량 요청은 여러 세그먼트로 나뉘고, 작은 데이터 여러 개가 함께 담길 수도 있다. 패킷 캡처 도구의 TCP 재조립 화면과 개별 패킷 화면을 구분해 읽어야 한다.

## 6. 흐름 제어와 혼잡 제어

**흐름 제어(flow control)** 는 수신 프로그램과 버퍼가 감당할 수 있는 속도를 지키는 일이다. TCP 수신자는 수신 윈도 크기로 더 받을 수 있는 범위를 알린다. 프로그램이 데이터를 천천히 읽으면 윈도가 줄어 송신이 제한될 수 있다.

**혼잡 제어(congestion control)** 는 네트워크 경로가 감당할 수 있는 전송량을 조절하는 일이다. 송신자는 손실이나 지연 같은 신호를 참고해 전송 속도를 조절한다. 상대 버퍼가 넉넉해도 중간 링크가 혼잡하면 전송량을 줄여야 한다.

두 제어의 대상은 다르다. “서버는 빠른데 전송이 느리다”는 상황에서 수신 애플리케이션이 읽지 않는 문제와 경로 혼잡을 구분해야 한다. TCP는 이런 제어를 제공하지만 암호화나 무제한의 도착 시간 보장을 제공하지 않는다.

## 7. UDP: 경계를 보존하는 데이터그램

**UDP(User Datagram Protocol)** 는 개별 메시지인 데이터그램을 전달하는 간단한 전송 프로토콜이다. 기본 헤더에는 출발지 포트, 목적지 포트, 길이, 체크섬이 있다. TCP처럼 연결 설정·순서 복구·재전송·흐름 제어를 자체 제공하지 않는다.

수신된 UDP 데이터그램은 메시지 단위가 유지된다. 다만 수신 버퍼가 작거나 프로그램이 느리면 메시지가 잘리거나 버려질 수 있으며, 운영체제 API에 따라 처리 방식이 다르다. 네트워크에서 손실·중복·순서 뒤바뀜도 가능하다.

UDP의 체크섬은 전송 오류를 탐지하기 위한 것이며 공격자에 대한 인증이나 암호화 기능이 아니다. UDP를 사용하는 상위 프로토콜은 필요하면 순서 번호·응답·재전송·보안을 추가한다. UDP를 사용했다는 사실만으로 전체 통신의 신뢰성 수준이 정해지지는 않는다. [RFC 768](https://www.rfc-editor.org/rfc/rfc768.html) 참조.

## 8. 관련 계층과 선택 기준

| 항목 | TCP | UDP |
| --- | --- | --- |
| 기본 데이터 모델 | 순서 있는 바이트 스트림 | 개별 데이터그램 |
| 연결 설정 | 연결 상태를 설정 | 기본 프로토콜에는 없음 |
| 손실·중복·순서 처리 | TCP가 제공 | 필요하면 상위 계층이 설계 |
| 흐름·혼잡 제어 | TCP가 제공 | 상위 프로토콜·애플리케이션이 고려 |
| 기본 헤더 크기 | 최소 20바이트, 옵션으로 증가 | 8바이트 |
| 암호화·사용자 인증 | 자체 제공하지 않음 | 자체 제공하지 않음 |

둘 다 IP 위에서 동작한다. TCP가 연결을 만든다는 것은 전용 물리 회선을 예약한다는 뜻이 아니다. 네트워크의 다른 패킷들과 링크를 공유한다.

UDP는 헤더와 기본 절차가 작지만 애플리케이션이 복구 기능을 추가하면 비용이 늘어난다. 전송량, 손실률, RTT, 최신성 요구를 함께 비교해야 하며 “UDP가 항상 빠르다”는 식으로 선택하지 않는다.

## 9. 실제 전송 흐름과 로그 예시

TCP를 사용하는 다운로드의 흐름은 연결 준비, 바이트 전송, 확인·필요한 재전송, 수신 프로그램의 해석, 연결 종료로 나눌 수 있다. 아래는 연결이 이미 성립한 뒤의 가상 로그다.

```text
C -> S  Seq=1001 Len=100
S -> C  Ack=1101
C -> S  Seq=1101 Len=100   [경로에서 손실]
C -> S  Seq=1101 Len=100   [재전송]
S -> C  Ack=1201
```

`Seq=1001 Len=100`은 1001부터 1100까지의 바이트를 뜻한다. `Ack=1101`은 다음에 1101번을 기대한다는 누적 확인이다. 도구가 상대 번호를 표시할 수 있으므로 실제 캡처의 표시 설정을 확인한다. 위 로그는 재전송 타이밍을 단순화했으며 모든 ACK가 패킷마다 즉시 발생하는 것은 아니다.

UDP 상태 갱신에서는 상위 프로토콜이 붙인 메시지 번호 10, 11, 12 중 11이 없어도 12가 도착할 수 있다. 11을 복구할지, 최신인 12만 반영할지는 애플리케이션의 요구다. 번호 자체도 UDP가 자동으로 넣어 주지 않는다.

## 10. 흔한 오해·예외·주의점

- **TCP면 반드시 성공한다**: 연결 실패와 타임아웃은 여전히 발생하며 비즈니스 처리 성공도 따로 확인한다.
- **UDP는 항상 데이터가 순서 없이 온다**: 순서를 보장하지 않는다는 뜻이지 매번 뒤바뀐다는 뜻은 아니다.
- **한 번 send하면 한 번 receive한다**: TCP에는 그런 대응 관계가 없다.
- **TCP는 안전하고 UDP는 위험하다**: 암호화·인증은 별도 문제다. 어떤 상위 보안 프로토콜을 쓰는지 확인한다.

<callout icon="🔭" color="gray_bg">
**[미리보기: 연결 설정과 QUIC]**

TCP 연결의 SYN·ACK와 종료 상태는 바로 다음 TCP Handshake 주제에서 다룬다. HTTP/3가 사용하는 QUIC는 UDP 위에 신뢰성과 보안을 추가하며, 커리큘럼의 Keep-Alive / HTTP 버전별 특징 기초에서 비교한다.
</callout>

## 11. 보안·성능·운영·디버깅 관점

TCP 재전송이 보이면 손실 가능성을 조사하되 캡처 지점과 수집 누락도 확인한다. 재전송 하나만으로 서버 코드 오류를 결론 내릴 수 없다. 패킷 손실은 복구 대기와 전송량 조절로 사용자 체감 지연을 키울 수 있다.

UDP를 사용할 때는 무제한으로 보내지 말고 경로의 혼잡과 수신 용량을 고려한다. 큰 데이터그램은 경로 MTU를 넘을 위험이 있고 일부 조각의 손실이 메시지 전체 실패로 이어질 수 있다. 응답을 만드는 공개 UDP 서비스는 출발지 위조를 이용한 반사 공격 위험도 고려한다. [RFC 8085](https://www.rfc-editor.org/rfc/rfc8085.html)는 UDP 애플리케이션의 운영 지침을 제공한다.

디버깅은 프로토콜 종류, 양쪽 IP·포트, 수신 프로세스, 방화벽 규칙, 손실·재전송을 함께 확인한다. 브라우저 Network 패널의 HTTP 시간만으로 TCP의 모든 패킷 동작을 알 수는 없다.

## 12. 핵심 정리

<callout icon="✅" color="green_bg">
TCP는 순서 있는 바이트 흐름을 제공하고 UDP는 개별 메시지를 전달한다. 필요한 신뢰성·최신성·제어 기능을 어느 계층에서 제공하는지가 선택의 핵심이다.
</callout>

- TCP 스트림 위의 메시지 경계는 상위 프로토콜이 정한다.
- 흐름 제어는 수신자 용량, 혼잡 제어는 네트워크 경로를 보호한다.
- UDP 위에서도 신뢰성 있는 프로토콜을 설계할 수 있다.
- 어느 프로토콜이든 전송 성공과 애플리케이션 처리 성공은 구분한다.

## 13. 이해도 확인 질문

1. TCP로 `hello`와 `world`를 두 번 전송했다. 수신 프로그램이 메시지를 두 개로 해석하려면 무엇이 더 필요한가?
2. 서버가 TCP ACK를 보낸 직후 장애가 났다. 클라이언트는 주문 저장 성공을 단정할 수 있는가? 어느 계층의 근거가 필요한가?
3. 수신 윈도가 0인 상황과 경로 손실 때문에 전송량이 감소한 상황은 제어 목적이 어떻게 다른가?
4. 오래된 위치 갱신의 복구보다 최신 위치 전달이 중요한 서비스라면 어떤 요구를 기준으로 전송 방식을 판단해야 하는가?
5. TCP 443 연결은 되는데 UDP 443 통신은 실패한다. 네트워크 설정에서 무엇을 구분해 조사해야 하는가?

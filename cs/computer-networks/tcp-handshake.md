**학습 범위**: Track C · Network / HTTP · TCP 3-Way / 4-Way Handshake

TCP 연결을 만들고 종료하는 이유를 시퀀스 번호와 상태 전이로 설명한다. 일반적인 능동 연결과 정상 종료를 기준으로 하며, 동시 연결·동시 종료 같은 예외도 구분한다.
</callout>

<table-of-contents />

## 1. 학습 목표

- SYN·ACK·FIN·RST가 어떤 상태 변화를 뜻하는지 설명한다.
- 3단계 연결 설정을 양방향 시퀀스 번호 확인 과정으로 복원한다.
- 정상 종료, 반쪽 종료, 강제 종료를 구분한다.
- TIME_WAIT·CLOSE_WAIT와 연결 실패 로그를 보고 조사 방향을 정한다.

## 2. 이 주제를 왜 배우는가

TCP는 이미 존재하는 전용 선을 사용하는 것이 아니라 양쪽 운영체제에 연결 상태를 만든다. 데이터를 보내기 전에 상대의 통신 준비와 번호 기준을 확인하고, 끝낼 때는 남은 바이트를 전달한 뒤 각 방향을 닫아야 한다.

연결이 맺어지지 않아 생긴 지연은 HTTP 처리 지연과 다르다. 또 연결을 매번 새로 만들면 데이터가 작아도 왕복 시간이 누적된다. 연결 설정과 종료를 이해하면 접속 타임아웃, 포트 거부, 소켓 누수 같은 증상을 구분할 수 있다.

## 3. 제어 플래그와 번호의 의미

| 항목 | 역할 |
| --- | --- |
| SYN | 초기 시퀀스 번호를 알리고 연결을 동기화 |
| ACK 플래그 | 확인 응답 필드가 유효함을 표시 |
| 확인 응답 번호 | 다음에 받고 싶은 바이트 위치 |
| FIN | 이 방향에서 더 보낼 바이트가 없음을 표시 |
| RST | 연결을 거부하거나 현재 연결을 비정상적으로 중단 |

TCP 연결에는 두 방향의 바이트 흐름과 각각의 번호 공간이 있다. 클라이언트의 시작 번호와 서버의 시작 번호는 같을 필요가 없다. **SYN과 FIN은 각각 시퀀스 번호 하나를 소비**한다. 반면 데이터 없는 ACK만으로는 시퀀스 번호가 증가하지 않는다.

아래 예시는 옵션·재전송·데이터 동시 전송을 생략한 가상 값이다. 캡처 도구가 시작 번호를 0으로 바꿔 보여 주는 상대 시퀀스 번호 표시와 실제 헤더 값을 구분한다.

## 4. 관련 계층과 상태의 위치

| 단계 | 주로 관여하는 부분 | 확인되는 것 |
| --- | --- | --- |
| IP 전달 | 인터넷 계층·라우터 | 패킷을 상대 방향으로 전달 |
| TCP Handshake | 양쪽 운영체제의 TCP | 연결 상태와 번호 기준 |
| 애플리케이션 요청 | 브라우저·서버 프로그램 | 요청 해석과 처리 결과 |

서버의 **LISTEN**은 새 연결을 기다리는 수신 소켓의 상태다. 새 연결이 생겨도 수신 소켓은 계속 기다릴 수 있다. 각 클라이언트와의 연결은 별도의 상태를 가진다. TCP 연결 성공은 애플리케이션의 정상 처리와 구분해야 한다.

## 5. 3-Way Handshake의 실제 흐름

서버가 연결을 기다리고 있고 클라이언트가 먼저 시작한다고 가정한다.

```text
클라이언트                                      서버
CLOSED                                          LISTEN
    SYN, Seq=1000 ---------------------------->
SYN_SENT
                  <----- SYN+ACK, Seq=5000, Ack=1001
                                                SYN_RECEIVED
    ACK, Seq=1001, Ack=5001 ------------------->
ESTABLISHED                                     ESTABLISHED
```

1. 클라이언트는 SYN으로 자신의 시작 번호 1000을 알리고 `SYN_SENT`로 간다.
2. 서버는 SYN을 받아 클라이언트의 다음 번호 1001을 ACK로 확인하고, 자신의 SYN으로 시작 번호 5000을 알린다.
3. 클라이언트는 서버 SYN을 확인하는 `Ack=5001`을 보낸다. 서버가 이를 받으면 양쪽 번호 기준을 확인한 연결이 완성된다.

서버는 두 번째 메시지를 보냈다는 사실만으로 클라이언트가 서버의 SYN을 받았는지 알 수 없다. 마지막 ACK가 그 정보를 전달한다. 이 과정은 지연된 옛 연결 요청을 새 연결로 잘못 받아들이는 문제도 다룬다. 다만 상대의 사용자 신원을 인증하거나 경로의 미래 가용성을 보증하는 과정은 아니다. [RFC 9293 §3.5](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.5) 참조.

## 6. 왜 종료는 보통 4단계인가

TCP는 양쪽이 각각 보낼 수 있는 **전이중 통신**이다. 한쪽이 전송을 끝내도 반대쪽에 아직 보낼 데이터가 남아 있을 수 있다. FIN은 연결 전체의 즉시 삭제 명령이 아니라 해당 방향의 데이터 끝을 뜻한다.

데이터 전송 후 클라이언트의 다음 번호가 1101, 서버의 다음 번호가 5301이라고 하자.

```text
클라이언트                                      서버
    FIN+ACK, Seq=1101, Ack=5301 -------------->
FIN_WAIT_1                                      CLOSE_WAIT
                  <----- ACK, Seq=5301, Ack=1102
FIN_WAIT_2
                  <----- FIN+ACK, Seq=5301, Ack=1102
                                                LAST_ACK
    ACK, Seq=1102, Ack=5302 ------------------->
TIME_WAIT                                       CLOSED
    일정 시간 대기 -> CLOSED
```

서버가 첫 FIN을 ACK한 뒤에도 서버에서 클라이언트로 보낼 데이터는 남아 있을 수 있다. 이것이 한쪽 전송만 끝난 **반쪽 종료(half-close)** 다. 예시에서는 남은 데이터가 없다고 단순화했다.

이 네 메시지를 흔히 4-Way Handshake라고 부르지만 항상 패킷 네 개가 오가는 것은 아니다. 서버가 바로 종료할 준비가 되면 ACK와 FIN을 합칠 수 있고, 동시에 종료하면 상태 경로가 달라진다. 재전송이 있으면 메시지도 늘어난다.

## 7. TIME_WAIT와 CLOSE_WAIT

**TIME_WAIT**는 일반적인 정상 종료에서 마지막 ACK를 보내는 쪽이 잠시 상태를 보관하는 단계다. 상대가 FIN을 재전송하면 다시 ACK할 수 있고, 이전 연결의 지연 패킷이 새 연결과 혼동되는 위험을 줄인다. 프로토콜에서는 기본적으로 2×MSL을 기다리며 MSL은 세그먼트의 최대 생존 시간 개념이다. 실제 관찰 시간은 운영체제 구현과 설정에 따라 다르다.

TIME_WAIT는 항상 클라이언트에 생기는 것이 아니다. 서버도 능동적으로 종료하면 이 상태에 들어갈 수 있다. 많이 보인다는 사실만으로 장애라 판단하지 말고 연결 생성 빈도, 포트 사용량, 오류 증가를 같이 본다.

**CLOSE_WAIT**는 상대의 FIN은 받았지만 로컬 애플리케이션이 자신의 송신 방향을 아직 닫지 않은 상태다. 장시간 쌓이면서 소켓이 늘면 애플리케이션의 종료 처리나 자원 반납 누락을 조사한다. TIME_WAIT와 원인이 같다고 취급하면 안 된다. [RFC 9293 §3.6](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.6) 참조.

## 8. RST와 정상 종료의 차이

RST는 정상적인 FIN 교환을 완료하지 않고 연결을 거부하거나 중단하는 신호다. 수신하지 않는 TCP 포트에 SYN을 보냈을 때 RST 응답이 올 수 있다. 통신 중간의 장비나 애플리케이션·운영체제 정책에 의해서도 발생하므로 RST 하나만으로 정확한 발생 원인을 단정하지 않는다.

정상 종료는 남은 데이터의 전달과 각 방향의 끝을 순서대로 정리한다. 강제 종료는 아직 읽지 않은 데이터나 대기 중인 전송이 처리되지 못할 수 있다. 어떤 API가 어떤 종료를 만드는지는 런타임과 소켓 옵션까지 확인해야 한다.

## 9. 연결 로그와 관찰 예시

```text
00.000 C -> S  SYN
01.000 C -> S  SYN [재전송]
03.000 C -> S  SYN [재전송]
```

설명용 로그처럼 SYN만 반복되면 연결 설정이 완료되지 않은 것이다. 방화벽의 무응답 차단, 경로 손실, 서버 부하, 응답 경로 문제 등을 조사한다. 이 단계에서는 HTTP 상태 코드가 아직 나오지 않았다. 위 시간 간격은 특정 운영체제의 재전송 정책을 뜻하지 않는다.

반면 `SYN -> RST+ACK`가 보이면 거부 응답을 받은 상황이다. 포트 수신 여부와 장비 정책을 먼저 확인한다. 연결이 성립한 뒤 HTTP 요청을 보냈는데 응답이 늦으면 요청 도착 로그·서버 처리·의존 서비스까지 조사 범위를 옮긴다.

Linux의 `ss -tan`, macOS의 `netstat -an -p tcp`로 TCP 상태를 관찰할 수 있다. 패킷 캡처에서는 SYN·FIN·RST 필터를 활용하되 권한과 캡처 위치에 따라 보이는 범위가 달라진다.

## 10. 흔한 오해와 주의점

- **3단계면 패킷이 항상 세 개다**: 일반 흐름을 부르는 이름이며 손실·재전송·동시 연결에 따라 달라진다.
- **FIN을 받으면 반대 방향으로도 더 못 보낸다**: FIN이 끝내는 방향을 먼저 구분해야 한다.
- **TCP ACK는 HTTP 성공이다**: TCP 수신과 애플리케이션 처리 결과는 다르다.
- **TIME_WAIT를 없애면 성능이 좋아진다**: 상태의 목적과 자원 병목을 확인하지 않은 조정은 연결 혼동 위험을 높일 수 있다.

## 11. 보안·성능·운영·디버깅 관점

새 TCP 연결은 왕복 통신과 연결 상태를 필요로 한다. RTT는 패킷이 상대에게 갔다가 돌아오는 시간이다. 거리가 멀거나 손실이 많으면 요청을 보내기 전 준비 시간도 커진다. 연결 생성 횟수와 지속 시간을 측정하면 서버 코드 시간과 구분할 수 있다.

**SYN flood**는 연결 설정 요청을 많이 보내 반쯤 열린 연결 상태나 처리 자원을 압박하는 공격이다. 서버·네트워크는 SYN cookie 같은 방어와 자원 제한을 사용할 수 있지만, 공격 방어를 위해 애플리케이션의 모든 느린 요청을 같은 문제로 취급해서는 안 된다.

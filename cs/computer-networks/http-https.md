## 1. 학습 목표

- HTTP가 네트워크에서 맡는 역할과 리소스·표현의 의미를 설명한다.
- URL의 구성 요소를 연결 단계와 요청 단계에 대응시킨다.
- HTTP와 HTTPS의 공통점, 차이, 기본 포트를 구분한다.
- HTTPS가 막는 위협과 막지 못하는 애플리케이션 문제를 판단한다.

## 2. 이 주제를 왜 배우는가

IP와 TCP만으로 바이트를 전달할 수 있어도 상대 프로그램은 그 바이트가 “상품을 조회하라”는 뜻인지 “파일을 저장하라”는 뜻인지 알 수 없다. **HTTP(Hypertext Transfer Protocol)** 는 요청 대상, 요청 의도, 처리 결과, 데이터 형식을 공유하기 위한 응용 계층 프로토콜이다.

그 규칙이 같아도 통신 내용을 중간에서 읽거나 바꿀 수 있으면 로그인 정보와 응답 데이터가 위험하다. **HTTPS**는 HTTP 통신에 TLS 기반의 보안 보호를 적용한다. 요청의 의미와 그 요청을 운반하는 구간의 보호는 별개의 책임이다.

## 3. 리소스와 표현, 클라이언트와 서버

**리소스(resource)** 는 URL 등으로 식별하는 대상이다. HTML 파일뿐 아니라 상품 목록, 사용자 프로필, 생성 작업의 결과도 리소스가 될 수 있다. **표현(representation)** 은 그 대상의 상태를 전달하는 데이터와 관련 메타데이터다. 같은 리소스도 HTML 또는 JSON처럼 여러 형식으로 표현할 수 있다.

클라이언트는 요청을 시작하고 서버는 요청을 해석해 응답한다. 브라우저는 대표적인 클라이언트지만 명령줄 도구와 다른 서버도 HTTP 클라이언트가 된다. 서버는 디스크의 파일을 그대로 읽을 수도 있고 프로그램을 실행해 응답 데이터를 만들 수도 있다.

화면 하나를 여는 일은 보통 요청 하나로 끝나지 않는다. HTML을 받은 뒤 CSS·스크립트·이미지를 요청하고 추가 데이터를 조회할 수 있다. 사용자 동작, HTTP 요청 수, TCP 연결 수는 서로 다른 단위다.

## 4. URL의 어느 부분이 어디에 쓰이는가

```text
https://shop.example.com:443/products?page=2#reviews
```

| 부분 | 의미 | 주로 쓰이는 단계 |
| --- | --- | --- |
| `https` | 사용할 스킴과 보안 연결 방식 | 연결 준비 |
| `shop.example.com` | 대상 호스트 이름 | DNS, 서버 이름 검증, HTTP 대상 지정 |
| `443` | 명시한 서비스 포트 | 전송 종점 선택 |
| `/products` | 대상 리소스의 경로 | HTTP 요청 |
| `page=2` | 쿼리 문자열 | HTTP 요청 |
| `reviews` | 프래그먼트 | 클라이언트가 해석, HTTP 요청 대상으로 보내지 않음 |

일반적으로 `http`의 기본 포트는 80, `https`는 443이다. URL에 기본 포트를 생략할 수 있으며 다른 포트로 서비스를 운영할 수도 있다. 포트 번호만 보고 실제 보안 프로토콜 사용을 확신해서는 안 된다.

## 5. HTTP의 요청·응답과 무상태성

요청은 “어떤 대상에 무엇을 원하는가”를 전달하고 응답은 처리 결과와 필요한 데이터를 돌려준다. **메서드**는 요청 의도, **상태 코드**는 응답 결과의 분류, **헤더**는 메시지의 처리 정보를 나타낸다.

HTTP의 **무상태성(statelessness)** 은 서버가 이전 요청과의 대화 문맥을 자동으로 기억해야 하는 프로토콜이 아니라는 뜻이다. 같은 TCP 연결을 재사용한다고 자동으로 같은 로그인 사용자로 식별되는 것은 아니다. 반대로 애플리케이션이 필요한 상태를 저장하는 것도 가능하다.

<callout icon="🔭" color="gray_bg">
**[미리보기: HTTP 메시지와 로그인 상태]**

메시지 구조와 메서드·상태 코드의 판단 기준은 다음 두 HTTP 주제에서 자세히 다룬다. 요청 사이에서 사용자를 이어서 식별하는 방식은 Cookie / Session에서 다룬다.
</callout>

## 6. 관련 계층과 HTTP·HTTPS의 차이

HTTP/1.1과 HTTP/2의 일반적인 웹 연결은 TCP를 사용한다. HTTPS에서는 HTTP 데이터가 TLS로 보호된 뒤 전송된다. 아래는 책임을 이해하기 위한 단순화다.

```text
HTTP:   HTTP 메시지 -> TCP -> IP -> 링크
HTTPS:  HTTP 메시지 -> TLS 보호 -> TCP -> IP -> 링크
```

| 항목 | HTTP | HTTPS |
| --- | --- | --- |
| 요청·응답 의미 | HTTP 규칙 | 같은 HTTP 규칙 |
| 전송 중 기밀성 | 자체 제공하지 않음 | TLS로 제공 |
| 전송 중 무결성 | 자체 제공하지 않음 | TLS로 제공 |
| 접속 서버 신원 확인 | 자체 제공하지 않음 | 인증서 검증 등으로 제공 |
| 애플리케이션 버그 방지 | 보장하지 않음 | 보장하지 않음 |

여기서 **기밀성**은 내용을 읽지 못하게 하는 것, **무결성**은 몰래 변경한 데이터를 정상 데이터로 받아들이지 않게 하는 것이다. **서버 인증**은 의도한 이름의 서버와 연결했는지 검증하는 절차다. 인증서 경고를 무시하면 이 보호의 중요한 전제가 깨진다.

<callout icon="🔭" color="gray_bg">
**[미리보기: HTTP/3]**

HTTP/3는 TCP 대신 QUIC를 이용하며 보안 협상이 통합되어 있다. 연결 구조의 차이는 Keep-Alive / HTTP 버전별 특징 기초에서 비교한다.
</callout>

## 7. HTTPS 요청이 진행되는 실제 흐름

새 연결로 `https://shop.example.com/products`를 연다고 가정한다.

1. 클라이언트는 URL을 해석하고 호스트의 주소를 찾는다.
2. HTTP/1.1 또는 HTTP/2를 쓸 경우 서버의 TCP 종점에 연결한다.
3. TLS로 서버 이름을 검증하고 통신 보호에 필요한 준비를 한다.
4. 보호된 연결 안에서 HTTP 요청을 전송한다.
5. 서버가 요청을 처리해 HTTP 응답을 보낸다.
6. 브라우저가 응답을 해석하고 필요한 추가 리소스를 요청한다.

기존 연결이나 캐시가 있으면 일부 준비가 생략될 수 있다. 서버가 보내는 HTTP 오류 응답과, TLS 검증 실패로 HTTP 교환을 시작하지 못한 상황을 구분해야 한다.

## 8. HTTP 메시지와 관찰 위치 예시

아래는 HTTP/1.1 메시지의 축약 예시다. 연결 위에서 메시지 경계를 표시하는 필드는 설명을 위해 생략했다.

```http
GET /products HTTP/1.1
Host: shop.example.com
Accept: application/json
```

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"items":[]}
```

요청 대상과 응답 데이터의 의미는 HTTP와 HTTPS에서 동일하다. HTTPS에서는 이 데이터가 보호된 구간을 지나는 동안 암호화된다. 브라우저의 Network 패널은 브라우저가 이미 복호화한 논리적 메시지를 보여 주므로 헤더·본문을 읽을 수 있다.

반면 일반적인 중간 네트워크 캡처에서는 HTTPS의 경로·헤더·본문을 그대로 읽을 수 없다. 목적지 IP·포트·패킷 크기·타이밍 같은 메타데이터까지 모두 사라지는 것은 아니다. 로컬 키를 제공한 디버깅 환경이나 신뢰된 중간 프록시 등은 관찰 조건이 다르다.

## 9. 위협 모델과 HTTPS의 한계

위협 모델은 무엇을 지키며 어떤 공격자를 가정하는지 정리하는 것이다. 여기서는 네트워크 중간에서 트래픽을 읽거나 바꿀 수 있는 공격자로부터 로그인 정보와 응답을 지킨다고 생각한다. 올바른 TLS 검증이 이루어지면 평문 노출과 중간 변조 위험을 줄일 수 있다.

하지만 악성 사이트가 자기 이름으로 유효한 인증서를 받는 것은 가능하다. HTTPS 표시가 사이트의 정직함이나 상품의 안전성을 보증하지는 않는다. 서버 침해, 잘못된 권한 검사, 사용자 단말의 악성 코드도 전송 암호화만으로 해결되지 않는다.

비밀번호나 토큰을 URL 쿼리에 넣으면 HTTPS를 써도 브라우저 기록·서버 로그·분석 시스템 등 종점에서 남을 수 있다. 보호된 전송 구간과 종점의 데이터 취급을 함께 설계해야 한다.

## 10. 프록시와 TLS 종료 지점

실제 웹 서비스에는 브라우저와 애플리케이션 서버 사이에 **프록시**가 있을 수 있다. 프록시는 요청을 받아 다른 서버로 전달하는 중간 HTTP 참여자다. 로드 밸런서나 CDN이 TLS 연결을 받아 복호화한 뒤 내부 서버로 새 요청을 보낼 수 있다.

```text
브라우저 -- HTTPS --> 앞단 프록시 -- 별도 연결 --> 애플리케이션 서버
```

브라우저에서 HTTPS가 성공했다는 사실은 첫 보안 구간에 대한 근거다. 내부 연결도 보호할지는 네트워크·신뢰 경계에 따라 별도 설정한다. 프록시에서 보안을 종료하면 그 프록시는 평문 요청을 볼 수 있는 신뢰 대상이 된다.

## 11. 흔한 오해와 주의점

- **HTTPS는 다른 종류의 API 형식이다**: 같은 HTTP 의미를 보호된 연결로 주고받는다.
- **인증서가 있으면 사용자도 인증됐다**: 일반적인 HTTPS는 서버를 확인하며 사용자 로그인은 별도다.
- **암호화하면 로그도 비밀이 된다**: 종점 로그의 민감 정보와 접근 권한은 따로 관리한다.
- **443번 포트를 열면 HTTPS 설정이 끝난다**: 서버의 TLS 설정과 인증서 검증이 실제로 성립해야 한다.

## 12. 보안·성능·운영·디버깅 관점

HTTP를 HTTPS로 리다이렉트할 때 최초 평문 요청은 이미 노출될 수 있다. 민감 데이터를 처음부터 HTTPS로 보내고, 브라우저가 이후 HTTPS를 강제하도록 하는 HSTS 정책의 적용 범위도 검토한다. HTTPS 페이지가 평문 하위 리소스를 불러오는 **혼합 콘텐츠**는 브라우저가 차단하거나 업그레이드할 수 있으므로 개발자 도구에서 확인한다.

TLS 준비에는 비용이 있지만 연결 재사용과 구현 최적화가 영향을 준다. “HTTPS라서 느리다”로 결론 내리기보다 DNS·TCP·TLS·서버 대기·다운로드를 나누어 측정한다.

장애는 이름 조회 실패, TCP 연결 실패, 인증서 검증 실패, 실제 HTTP 오류 응답으로 분류한다. HTTPS 응답 500을 받았다면 서버 처리 범위를 조사하고, 인증서 오류라면 HTTP 요청이 해당 서버의 애플리케이션까지 도착했는지부터 구분한다.

## 13. 핵심 정리

<callout icon="✅" color="green_bg">
HTTP는 웹 요청·응답의 의미를 정하고 HTTPS는 그 통신 구간을 보호한다. 통신 보호, 서버 신원, 사용자 인증, 애플리케이션 정확성은 각각 확인할 문제다.
</callout>

- URL은 연결 대상과 요청 대상을 함께 표현한다.
- 무상태성은 연결 재사용 여부와 다른 개념이다.
- HTTPS에서 Network 패널에 보이는 평문은 종점에서 복호화한 결과다.
- TLS가 어디에서 끝나는지에 따라 신뢰 경계가 달라진다.

## 14. 이해도 확인 질문

1. `https://shop.example.com:8443/products?page=2#reviews`에서 DNS 조회, 전송 종점 선택, HTTP 요청에 쓰이는 부분을 각각 구분해 보라.
2. HTTPS 요청의 헤더가 브라우저 Network 패널에 보인다는 사실이 전송 암호화 실패를 뜻하지 않는 이유는 무엇인가?
3. 유효한 인증서를 가진 사이트에서 잘못된 사용자 데이터가 응답되었다. TLS가 보장하는 것과 애플리케이션이 확인할 것을 구분해 보라.
4. 브라우저와 프록시 사이만 HTTPS인 구조에서 내부 서버까지의 기밀성을 판단하려면 무엇을 더 확인해야 하는가?
5. 인증서 오류로 실패한 접속과 HTTPS로 500 응답을 받은 요청은 어느 단계까지 진행되었으며 조사 방향은 어떻게 다른가?

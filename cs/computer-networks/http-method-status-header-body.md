메서드·상태 코드·헤더·본문을 클라이언트와 서버의 판단 규칙으로 읽는다. API 서버 구현이나 인증 시스템 설계보다 HTTP 의미와 관찰에 집중한다.

## 1. 학습 목표

- 요청 의도, 처리 결과, 처리 정보, 실제 데이터의 역할을 구분한다.
- 안전성과 멱등성을 재시도 판단에 연결한다.
- 상태 코드와 헤더를 함께 읽어 다음 행동을 정한다.
- 데이터 형식·콘텐츠 협상·메시지 길이의 차이를 설명한다.

## 2. 이 주제를 왜 배우는가

응답이 왔다는 사실만으로 작업의 성공이나 실패가 충분히 설명되지는 않는다. 새 리소스가 생겼는지, 아직 처리 중인지, 다른 주소로 가야 하는지, 자격 증명을 보내야 하는지는 HTTP 메시지의 의미를 읽어 판단해야 한다.

또 전송 오류가 난 요청을 그대로 다시 보내도 되는지는 요청 의도에 달려 있다. 파일 조회와 결제 요청을 같은 방식으로 재시도하면 중복 작업이 생길 수 있다. HTTP의 의미는 단순한 코드 목록이 아니라 이런 자동화의 공통 기준이다.

## 3. 네 요소가 나누는 책임

| 요소 | 답하는 질문 | 예시 |
| --- | --- | --- |
| 메서드 | 대상에 어떤 작업을 요청하는가 | GET, POST, PUT |
| 상태 코드 | 서버가 어떤 결과를 알리는가 | 200, 201, 404 |
| 헤더 | 메시지와 데이터를 어떻게 처리할 것인가 | Content-Type, Location |
| 본문 | 실제로 주고받는 데이터는 무엇인가 | JSON, HTML, 이미지 |

이 네 가지는 함께 해석한다. `201`과 `Location`은 새 리소스의 생성과 위치를 설명하고, `Content-Type`과 본문은 그 응답을 어떻게 읽을지 정한다. 상태가 성공이어도 본문의 애플리케이션 데이터가 기대한 상태인지 추가 확인이 필요할 수 있다.

## 4. 메서드의 의미와 사용 판단

| 메서드 | 정의된 의도 | 안전 | 멱등 |
| --- | --- | --- | --- |
| GET | 현재 표현 조회 | 예 | 예 |
| HEAD | GET과 대응하는 메타데이터 조회, 응답 본문 없음 | 예 | 예 |
| POST | 대상 리소스가 요청 데이터를 처리하도록 요청 | 아니오 | 일반적으로 보장 안 됨 |
| PUT | 지정한 대상의 상태를 제공한 표현으로 생성·대체 | 아니오 | 예 |
| DELETE | 대상과 현재 기능의 연결 제거 요청 | 아니오 | 예 |
| PATCH | 정의된 수정 문서에 따라 부분 변경 | 아니오 | 일반적으로 보장 안 됨 |
| OPTIONS | 대상의 통신 옵션 조회 | 예 | 예 |

**안전(safe)** 은 클라이언트가 서버 상태 변경을 요청하지 않는다는 의미다. GET에도 접근 로그 기록이나 통계 집계 같은 부수 효과는 있을 수 있다. 하지만 `GET /delete-account`처럼 의도적으로 삭제를 실행하게 만들면 안전한 메서드라는 전제를 깨뜨린다. 링크 미리 읽기나 자동 수집도 GET을 실행할 수 있다.

**멱등(idempotent)** 은 같은 요청을 여러 번 적용한 의도된 효과가 한 번 적용한 효과와 같다는 뜻이다. 응답 코드나 로그까지 매번 같다는 뜻은 아니다. DELETE를 두 번 보내 처음에는 삭제 성공, 다음에는 대상 없음이 되어도 같은 대상을 없앤다는 효과는 같다. [RFC 9110 §9.2](https://httpwg.org/specs/rfc9110.html#method.properties) 참조.

## 5. 재시도와 PUT·PATCH의 주의점

클라이언트가 응답을 받기 전에 연결이 끊겼다면 서버가 요청을 실행했는지 모를 수 있다. 멱등 메서드는 이런 상황에서 재시도를 설계할 근거가 된다. 다만 인증·동시 수정·서비스 정책·실제 서버 구현도 함께 보아야 한다.

POST 결제가 실패한 것처럼 보여도 서버에서는 이미 결제했을 수 있다. 무조건 재전송하면 중복 처리 위험이 있다. 이런 작업은 애플리케이션이 중복 방지 키나 처리 상태 조회 같은 명시적 계약을 마련해야 한다. TCP 재전송은 바이트 전달을 위한 것이며 이 비즈니스 중복 문제를 대신 해결하지 않는다.

PUT을 “항상 기존 데이터 수정”으로 외우지 않는다. 지정한 주소에 새 리소스를 만들 수도 있으며, 제공한 표현으로 대상 상태를 대체한다는 의미가 핵심이다. PATCH의 멱등성은 수정 문서에 달려 있다. “이름을 pen으로 설정”과 “잔액에 100 추가”는 반복 효과가 다르다. PATCH의 정의는 [RFC 5789](https://www.rfc-editor.org/rfc/rfc5789.html)를 참고한다.

## 6. 상태 코드의 계열과 클라이언트 행동

| 계열 | 의미 | 먼저 할 판단 |
| --- | --- | --- |
| 1xx | 중간 정보 | 최종 응답이 더 오는지 확인 |
| 2xx | 요청을 성공적으로 처리·수용 | 본문·작업 완료 여부를 코드별로 확인 |
| 3xx | 리다이렉트 등 추가 처리 | Location 또는 캐시 검증 의미 확인 |
| 4xx | 요청에 관련된 문제 | 요청·자격·정책을 바꿔야 하는지 확인 |
| 5xx | 서버가 처리하지 못함 | 서버·중간 장비·의존 서비스 조사 |

4xx를 모두 사용자 잘못, 5xx를 모두 애플리케이션 코드 버그라고 보면 안 된다. 프록시나 인증 계층이 응답을 만들 수도 있고 클라이언트 코드가 잘못된 요청을 자동 생성했을 수도 있다.

| 코드 | 의미와 주의점 |
| --- | --- |
| 200 | 성공, 본문 의미는 메서드와 타입에 따라 해석 |
| 201 | 리소스 생성, Location 등으로 위치 확인 |
| 202 | 처리 요청 수용, 비동기 작업 완료를 보장하지 않음 |
| 204 | 성공했으며 응답 본문 없음 |
| 304 | 조건부 조회에서 저장된 표현을 계속 사용할 수 있음, 본문 없음 |
| 400 | 서버가 요청을 잘못된 것으로 판단 |
| 401 | 대상에 유효한 인증 자격이 필요, WWW-Authenticate 확인 |
| 403 | 요청을 이해했으나 수행 거절, 로그인 여부만으로 단정 불가 |
| 404 | 대상 표현을 찾지 못했거나 존재를 공개하지 않음 |
| 405 | 대상이 메서드를 허용하지 않음, Allow 확인 |
| 415 | 요청의 콘텐츠 형식 등을 지원하지 않음 |
| 429 | 요청량 제한, Retry-After 등이 있으면 정책 확인 |
| 500 | 서버의 예기치 못한 처리 실패 |
| 502·504 | 게이트웨이의 상위 서버 응답 문제·시간 초과 |

## 7. 리다이렉트는 주소와 메서드를 함께 읽는다

`Location` 헤더는 새 주소 등 후속 위치를 알린다. 301·308은 영구 이동, 302·307은 임시 이동에 사용한다. 303은 다른 리소스를 조회하도록 안내하며 일반적으로 후속 GET 조회로 이어진다. HEAD의 경우에는 HEAD가 유지될 수 있다.

307·308은 자동 리다이렉트 시 메서드를 바꾸지 않는다. 반면 301·302는 역사적 호환 때문에 POST가 GET으로 바뀔 수 있다. 본문이 있는 요청을 다른 주소로 옮길 때는 단순히 “3xx는 다시 요청”으로 처리하지 말고 메서드·본문·인증 정보의 처리까지 본다.

## 8. 헤더는 데이터를 다루는 규칙이다

| 헤더 | 구분 | 수신자가 내릴 판단 |
| --- | --- | --- |
| Host | 요청 | 어느 호스트의 리소스인가 |
| Accept | 요청 | 어떤 응답 미디어 타입을 선호하는가 |
| Content-Type | 요청·응답 | 지금 메시지의 본문을 어떻게 해석하는가 |
| Content-Length | 요청·응답 | 본문 경계 판단 등에 쓸 바이트 길이 |
| Content-Encoding | 표현 정보 | gzip 등 어떤 인코딩을 해제해야 하는가 |
| Location | 응답 | 생성 위치·이동 위치는 어디인가 |
| Allow | 응답 | 대상에서 지원하는 메서드는 무엇인가 |
| Retry-After | 응답 | 후속 시도를 언제로 미룰 것인가 |

헤더 이름은 대소문자를 구분하지 않지만 값의 규칙은 필드별로 다르다. 모든 중복 헤더를 쉼표로 합쳐도 된다는 규칙도 없다. HTTP 라이브러리와 각 필드의 문법을 따른다.

`Content-Type: application/json`은 본문을 JSON으로 해석한다는 뜻이지 데이터를 자동으로 JSON으로 바꾸는 명령이 아니다. `Content-Encoding: gzip`은 표현에 적용한 압축 등을 나타내며, HTTP/1.1 청크 전송인 `Transfer-Encoding`과 목적이 다르다.

## 9. 요청·응답을 함께 읽는 예시

```http
PUT /products/7 HTTP/1.1
Host: shop.example.com
Content-Type: application/json
Accept: application/json
Content-Length: 27

{"name":"pen","price":1000}
```

이 요청은 `/products/7`의 상태를 제공한 표현으로 생성·대체하도록 요청한다. 본문은 추가 줄바꿈이 없는 ASCII 27바이트다. 예시 API는 이 두 필드가 PUT에 필요한 완전한 입력이라고 가정한다.

```http
HTTP/1.1 204 No Content

```

클라이언트는 성공을 처리하되 본문을 JSON으로 파싱하지 않는다. 반대로 `202 Accepted`라면 요청이 수용되었다는 뜻이며 실제 작업 완료는 API의 후속 계약으로 확인해야 한다.

```http
HTTP/1.1 405 Method Not Allowed
Allow: GET, HEAD
Content-Length: 0

```

이 응답은 서버에 도달하지 못한 상황이 아니다. 해당 대상에 그 메서드가 허용되지 않는다는 HTTP 판단이다. 단순 재시도보다 메서드·대상·라우팅 계약을 확인한다.

## 10. 관련 계층과 실제 판단 흐름

HTTP의 메서드·상태·헤더·본문은 응용 계층 정보다. TCP는 이 메시지의 결제 의도나 403의 의미를 알지 못한다. 클라이언트는 메시지를 수신한 뒤 상태를 분류하고, 헤더로 후속 행동과 해석 방식을 결정하고, 필요한 본문을 파싱해 화면이나 애플리케이션 상태를 갱신한다.

Network 패널에서는 실제 메서드와 리다이렉트 후의 최종 메서드를 비교하고, 요청·응답의 Content-Type과 원문 본문을 함께 본다. 자바스크립트의 `fetch`는 HTTP 404·500만으로 Promise를 거절하지 않는다. 응답 객체의 `status`나 `ok`를 검사하는 처리와 네트워크 실패 처리를 나누어야 한다.

## 11. 흔한 오해와 보안·성능·운영 관점

GET 본문에 일반적으로 정의된 의미가 있는 것은 아니다. 구현이 거부하거나 중간 장비가 다르게 취급할 수 있으므로 조회 조건은 API 계약에 맞게 대상 쿼리 등으로 표현한다. GET을 사용하는 것만으로 요청 내용이 비밀이 되지도 않는다.

POST·PUT이라는 메서드 이름은 권한 검사를 대신하지 않는다. 서버는 신뢰할 수 없는 본문을 검증하고 사용자에게 그 대상 작업을 허용할지 판단해야 한다. 오류 응답에는 내부 경로·스택·비밀 정보를 과도하게 노출하지 않는다.

무제한 재시도는 장애 서버의 부하를 키운다. 실패 종류·멱등성·재시도 간격·횟수 제한을 함께 설계한다. 429나 503의 재시도 안내도 읽되, 재시도할 작업 자체가 안전한지 별도로 판단한다.

## 12. 핵심 정리

<callout icon="✅" color="green_bg">
메서드는 요청 의도, 상태 코드는 결과, 헤더는 처리 규칙, 본문은 실제 데이터다. 어느 하나만 보고 다음 행동을 결정하지 않는다.
</callout>

- 안전성과 멱등성은 다른 속성이며 재시도의 근거가 된다.
- 같은 효과라도 응답은 달라질 수 있다.
- 성공 코드마다 완료 여부와 본문 유무가 다르다.
- 리다이렉트·인증·재시도는 관련 헤더와 함께 해석한다.

## 13. 이해도 확인 질문

1. DELETE를 두 번 보냈더니 204와 404가 차례로 왔다. 이 사실만으로 멱등성이 깨졌다고 할 수 있는가?
2. POST 결제 요청 후 응답을 받기 전에 연결이 끊겼다. 자동 재시도 전에 어떤 불확실성과 API 계약을 확인해야 하는가?
3. 같은 작업에서 201, 202, 204를 받았을 때 클라이언트의 후속 행동은 어떻게 달라지는가?
4. JSON을 기대했는데 415 응답을 받았다. 요청의 어떤 헤더와 실제 데이터를 함께 확인해야 하는가?
5. 본문이 있는 POST가 302 또는 307로 이동했다. 후속 요청을 관찰할 때 무엇을 비교해야 하는가?

## 1. 학습 목표

- 함수와 정의 당시의 어휘 환경을 함께 보는 클로저를 설명한다.
- 바깥 함수 종료 후에도 바인딩에 접근하는 흐름을 추적한다.
- 같은 환경 공유와 호출별 독립 환경을 구분한다.
- 반복문 캡처와 불필요한 참조 유지 문제를 디버깅한다.

## 2. 이 주제를 왜 배우는가

한 번 만든 카운터가 다음 호출에도 이전 값을 기억하려면 상태를 어디에 둘지 정해야 한다. 전역 변수 하나에 두면 모든 카운터가 같은 상태를 사용하게 된다. 클로저는 함수가 필요한 상태를 자신의 정의 환경을 통해 사용할 수 있게 한다.

**클로저(closure)** 는 함수와 그 함수가 생성될 때 연결된 어휘 환경의 조합이다. 반환된 중첩 함수에서 특히 잘 드러나지만, “함수를 반환해야만 생기는 특수 기능”은 아니다. JavaScript 함수는 생성 시 바깥 환경과 연결된다.

### 상태를 두는 위치가 공유 범위를 정한다

카운터 값을 전역에 두면 카운터를 몇 개 만들든 같은 값을 쓸 수 있다. 생성 함수의 지역에 두면 그 생성 호출별로 상태를 구분할 수 있다. 클로저는 이 지역 상태를 필요한 함수들에 연결하는 도구다.

따라서 먼저 상태가 사용자별·객체별·모듈 전체 중 어디까지 공유되어야 하는지 결정한다. 클로저라는 문법적 기교를 먼저 고르기보다 같은 데이터를 읽고 쓰는 코드들의 경계를 정하는 것이 설계의 출발점이다.

## 3. 환경이 유지되는 실행 흐름

```javascript
function createCounter(start) {
  let count = start;
  return function next() {
    count += 1;
    return count;
  };
}
const counter = createCounter(10);
console.log(counter()); // 11
console.log(counter()); // 12
```

1. `createCounter(10)` 호출에서 `count` 바인딩을 만든다.
2. `next` 함수는 이 호출의 환경에 연결된다.
3. 바깥 호출은 반환해 호출 스택에서 빠진다.
4. `counter`가 보관한 함수를 호출하면 여전히 같은 `count`를 읽고 바꾼다.

호출 스택에서 빠지는 것과, 필요한 환경의 데이터가 더는 접근 가능하지 않게 되는 것은 다르다. 명세 모델상 연결이 유지되며, 실제 엔진은 관찰 가능한 결과를 지키면서 필요한 데이터만 최적화할 수 있다.

### 함수가 만들어질 때 연결되는 환경

[ECMAScript OrdinaryFunctionCreate](https://tc39.es/ecma262/multipage/ordinary-and-exotic-objects-behaviours.html#sec-ordinaryfunctioncreate)는 함수 객체에 바깥 환경과의 연결을 설정한다. 내부 슬롯 이름을 암기하기보다 이 연결이 함수 호출 위치가 바뀌어도 유지된다는 의미를 이해한다.

바깥 호출의 종료는 실행 진행이 복귀했다는 뜻이다. 반환된 함수를 통해 필요한 바인딩에 접근할 수 있다면 그 관찰 결과를 보존해야 한다. 실제 엔진이 바깥 프레임 전체를 그대로 보관하는지, 일부 값만 최적화하는지는 명세상의 연결 설명과 구별한다.

| 대상 | 바깥 호출 종료 뒤의 관찰 |
| --- | --- |
| 바깥 함수의 활성 호출 | 동기 호출 스택에서는 복귀함 |
| 반환한 함수 객체 | 호출자가 보관하면 다시 호출 가능 |
| 그 함수가 사용하는 바인딩 | 후속 호출에서 읽고 변경 가능 |
| 관련 없는 임시 데이터 | 구현과 도달 가능성에 따라 처리 |

## 4. 값의 사진이 아니라 바인딩 연결

```javascript
function createStore() {
  let value = 0;
  return {
    read() { return value; },
    write(next) { value = next; }
  };
}
const store = createStore();
console.log(store.read()); // 0
store.write(7);
console.log(store.read()); // 7
```

`read`와 `write`는 같은 호출 환경의 `value`를 사용한다. 함수 생성 순간의 `0`을 각각 복사해 고정한 것이 아니다. 하나가 바꾸면 다른 함수가 그 변경을 읽는다.

다만 함수 밖에서 계산한 `const message = "value=" + value`를 캡처하면 이미 계산한 문자열 값은 저절로 재계산되지 않는다. “클로저는 항상 최신의 모든 계산 결과를 제공한다”는 말도 틀리다. 어떤 바인딩을 읽고 그 값이 언제 계산되었는지 구분한다.

### 최신 바인딩과 계산 당시의 값

```javascript
function create() {
  let count = 0;
  const message = "count=" + count;
  return {
    increment() { count += 1; },
    readCount() { return count; },
    readMessage() { return message; }
  };
}
const value = create();
value.increment();
console.log(value.readCount(), value.readMessage()); // 1 count=0
```

두 읽기 함수는 각각 자신이 사용하는 바인딩을 정확히 읽었다. count는 갱신됐고 message는 처음 계산한 문자열이므로 변하지 않았다. “클로저가 오래된 값을 기억해서 버그가 난다”로만 설명하면 어떤 식이 언제 계산되었는지 빠진다.

최신 메시지가 필요하면 읽는 시점에 count로 문자열을 다시 계산하는 함수를 사용한다. 과거 시점의 스냅샷이 목적이면 처음 계산한 message가 올바른 설계일 수 있다. 무엇을 보존하려는지에 따라 선택이 달라진다.

## 5. 호출별 독립 환경

```javascript
function makeCounter() {
  let n = 0;
  return () => ++n;
}
const a = makeCounter();
const b = makeCounter();
const alias = a;
console.log(a(), a(), b(), alias()); // 1 2 1 3
```

`makeCounter`를 두 번 호출했으므로 `a`와 `b`는 서로 다른 `n`을 사용한다. `alias`는 새 카운터를 만든 것이 아니라 `a`와 같은 함수 객체를 가리킨다. 따라서 `alias()`는 `a`의 상태를 이어 사용한다.

```text
 a ─┐
    ├─> 함수 A → 환경 A의 n
alias┘
 b ───> 함수 B → 환경 B의 n
```

### 생성자 호출 횟수와 함수 별칭을 구분한다

함수 값을 새 변수에 대입하는 것은 새 환경을 만드는 작업이 아니다. 같은 클로저의 별칭을 여러 이름으로 호출하면 같은 상태에 접근한다. 반면 생성 함수를 다시 호출해 함수들을 만들면 각 호출 환경이 구분된다.

```javascript
function makeBox(initial) {
  let value = initial;
  return { read: () => value, write: next => { value = next; } };
}
const a = makeBox(1);
const alias = a;
const b = makeBox(1);
alias.write(5);
console.log(a.read(), b.read()); // 5 1
```

이 예제에서는 반환 객체의 별칭도 공유한다. 상태가 겹친다면 함수 생성 횟수뿐 아니라 반환 객체·내부 함수·캡처한 객체 값의 공유 관계까지 그려 본다.

## 6. 반복문의 var와 let

```javascript
const shared = [];
for (var i = 0; i < 3; i += 1) {
  shared.push(() => i);
}
console.log(shared.map(read => read()).join(",")); // 3,3,3

const separate = [];
for (let j = 0; j < 3; j += 1) {
  separate.push(() => j);
}
console.log(separate.map(read => read()).join(",")); // 0,1,2
```

첫 반복은 함수들이 같은 `i`를 읽는다. 호출은 반복이 끝난 뒤이므로 모두 종료 값 `3`을 본다. 두 번째 `for`의 `let`은 반복마다 구분된 바인딩을 제공하여 각 함수가 해당 반복의 값을 읽는다.

차이는 함수가 실행된 시점과 연결된 바인딩이다. “화살표 함수가 이상해서” 또는 “배열이 값을 바꿔서” 생긴 결과가 아니다. 타이머를 쓰지 않아도 같은 원리를 확인할 수 있다.

### let을 써도 공유 객체까지 분리되는 것은 아니다

```javascript
const shared = { value: 0 };
const readers = [];
for (let i = 0; i < 2; i += 1) {
  readers.push(() => i + ":" + shared.value);
}
shared.value = 9;
console.log(readers.map(read => read()).join(",")); // 0:9,1:9
```

반복 변수 i의 바인딩은 구분되지만 shared 객체는 같은 바깥 바인딩을 통해 읽는다. let 반복 규칙을 모든 캡처 데이터의 깊은 복제로 해석하면 안 된다. 어느 이름이 반복별로 달라지고 어느 이름이 바깥에서 공유되는지 따로 표시한다.

반복 시점의 원시 값을 보존하고 싶다면 그 반복에서 별도 지역 이름에 계산한 값을 연결할 수 있다. 반대로 실행할 때의 최신 공유 값을 원한다면 위 코드처럼 바깥 객체를 읽는 것이 요구에 맞을 수 있다.

## 7. 캡슐화와 사용 기준

클로저로 상태를 외부에서 직접 읽지 못하게 하고 읽기·갱신 함수를 공개할 수 있다. 이는 코드의 접근 경계를 만드는 방법이다. 모듈이나 클래스와 함께 상황에 맞게 선택하며, 보안상 비밀을 절대 추출할 수 없다는 의미의 암호화는 아니다.

함수를 만드는 위치는 상태의 수명을 정한다. 한 번만 만들어 여러 호출에서 재사용하면 상태를 공유하고, 매번 새로 만들면 별도 상태를 얻는다. 테스트에서 상태가 남는 버그도 이 생성 위치를 보면 설명할 수 있다.

### 접근 경계와 동시 사용자 분리

클로저로 내부 변수에 대한 직접 접근을 감추더라도 공개 메서드가 내부 객체를 그대로 반환하면 외부가 그 객체를 바꿀 수 있다. 캡슐화는 변수 이름을 숨겼다는 사실뿐 아니라 어떤 값과 변경 기능을 공개하는지로 결정된다.

서버·UI의 구체적 구현을 떠나 사용자별 상태를 분리해야 한다면 생성 함수를 사용자 또는 기능 인스턴스별로 호출하는지 확인한다. 모듈 최상위에서 한 번 만든 클로저를 모두 공유하면 의도와 다르게 상태가 섞일 수 있다. 환경의 생성 위치가 상태의 공유 범위를 만든다.

## 8. 흔한 오해·예외·주의점

- **외부 함수 종료 시 값은 모두 사라진다**: 접근 경로가 남아 있으면 필요한 데이터도 유지될 수 있다.
- **클로저는 생성 시의 숫자를 복사한다**: 바인딩을 통해 이후 변경을 읽을 수 있다.
- **함수 이름이 같으면 상태도 같다**: 어느 호출에서 생성된 함수인지 확인한다.
- **클로저가 있으면 모두 메모리 누수다**: 의도한 수명 동안 상태를 유지하는 것은 정상이다. 불필요하게 오래 참조할 때 문제가 된다.

### 메모리 유지와 메모리 누수를 구분한다

상태를 기억하는 카운터가 그 숫자를 유지하는 것은 의도된 동작이다. 문제는 더 이상 필요하지 않은 함수가 등록 목록·캐시 등에 남아 큰 데이터까지 계속 접근 가능하게 하는 경우다. 단순히 클로저가 존재한다는 이유로 누수라고 부르지 않는다.

수거를 원한다면 접근 경로를 끊어야 한다. 그러나 특정 줄에서 참조를 제거했다고 그 즉시 메모리가 반환된다는 보장은 없다. 메모리 조사에서는 생성 횟수, 해제 책임, 여전히 남아 있는 참조 경로를 확인한다.

## 9. 실무 적용과 디버깅 관점

오래 유지되는 함수가 큰 객체·캐시를 참조하면 더 이상 필요 없는 데이터의 수명도 길어질 수 있다. 등록한 함수를 해제하거나 보관한 참조를 제거하는 책임을 정한다. 가비지 컬렉션의 정확한 시점은 보장하지 않는다.

디버깅에서는 함수 생성 시점, 바깥 호출의 식별, 캡처한 이름, 읽는 시점을 기록한다. 값이 오래된 경우에는 원본 바인딩을 읽는지, 미리 계산한 다른 바인딩을 읽는지도 확인한다.

**[미리보기: Callback]** 나중에 실행하도록 전달한 함수도 자신의 어휘 환경을 사용할 수 있다. 이 성질이 후속 처리에 쓰이는 방식은 Async JavaScript의 Callback에서 다룬다.

### 상태가 섞이는 버그의 재현 표

함수를 만드는 호출에 임시 ID를 붙이고, 그 호출에서 만든 읽기·쓰기 함수들이 같은 ID를 사용하는지 기록한다. 다음으로 두 기능을 시작할 때 생성 함수를 정말 두 번 호출했는지 확인한다. 같은 함수 값의 별칭을 복사한 것을 새 인스턴스로 오해했는지 검사한다.

값이 오래된 경우에는 캡처한 이름의 현재 값과 미리 계산한 문자열·객체의 생성 시점을 구분한다. 상태가 섞이는 문제와 과거 계산 결과를 읽는 문제는 원인이 다르므로 같은 “클로저 문제”로 묶어 고치지 않는다.

### 통합 사례: 편집 초안의 현재 값과 시작 값

편집 기능에서 처음 값은 취소용으로 보관하고 현재 값은 계속 바꾸고 싶다고 하자. 둘을 같은 바인딩으로 취급하면 취소 기준이 함께 바뀔 수 있다. 원시 값 기준의 최소 사례에서 두 바인딩의 목적을 나눈다.

```javascript
function createDraft(initial) {
  const original = initial;
  let current = initial;
  return {
    set(value) { current = value; },
    read() { return current; },
    reset() { current = original; }
  };
}
const draft = createDraft("first");
draft.set("second");
console.log(draft.read()); // second
draft.reset();
console.log(draft.read()); // first
```

세 메서드는 하나의 생성 호출 환경을 공유한다. set은 current만 갱신하고 reset은 보존한 original을 다시 연결한다. createDraft를 다시 호출하면 별도 current와 original이 생긴다. 함수들의 수보다 어느 환경을 공유하는지 보는 것이 중요하다.

이 예제는 문자열이라 초기값의 내부가 변경되지 않는다. 객체를 그대로 두 바인딩에 연결하면 같은 객체가 공유되어 속성 변경이 취소 기준에도 보일 수 있다. 클로저의 바인딩 유지와 객체의 복사 깊이는 별개의 문제이며, 객체 기반 초안을 설계할 때는 뒤의 Shallow Copy / Deep Copy · Immutability 기준도 적용한다.

결국 원래 값과 현재 값이 필요한 이유, 생성 위치, 읽기·쓰기 경로를 먼저 정한다. 클로저는 그 상태를 유지하는 메커니즘이며 어떤 상태를 보존할지는 업무 계약이다.

## 10. 핵심 정리

클로저는 함수와 어휘 환경의 연결이다. 호출 스택이 끝나도 필요한 바인딩을 계속 사용할 수 있다. 공유하는 환경과 별도 호출 환경, 바인딩의 변경과 계산된 값의 고정을 구분한다.

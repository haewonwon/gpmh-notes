## 1. 학습 목표

- 동기·비동기와 블로킹·논블로킹을 구분한다.
- 작업 시작·완료·후속 코드 실행을 따로 추적한다.
- 비동기 결과를 호출 직후 사용할 수 없는 이유를 설명한다.
- 동시 진행과 병렬 실행, CPU 작업과 I/O 대기를 비교한다.

## 2. 이 주제를 왜 배우는가

서버 응답을 기다리는 동안 화면이 멈추면 입력과 스크롤도 지연될 수 있다. 반대로 작업을 시작하고 다음 코드를 계속 실행하면 결과가 아직 없는데 사용하려는 버그가 생긴다. 비동기는 느린 일을 빠르게 만드는 마법이 아니라 기다리는 동안 실행을 어떻게 이어 갈지 정하는 방식이다.

**동기(synchronous)** 호출은 호출한 코드가 해당 작업의 흐름을 직접 마친 뒤 다음 코드로 이어진다. **비동기(asynchronous)** 처리는 작업 완료를 나중의 후속 흐름으로 전달한다. 함수가 지금 반환했다는 사실과 요청한 작업이 완료됐다는 사실은 다를 수 있다.

### 시간과 제어 흐름은 별개다

매우 빠른 작업도 비동기 계약으로 결과를 전달할 수 있고, 오래 걸리는 작업도 동기 호출로 끝날 때까지 실행 자원을 점유할 수 있다. “오래 걸리면 비동기”라는 구분 대신 함수가 언제 반환하고 결과를 어떻게 전달하는지 확인해야 한다.

이 페이지의 시간 예제는 순서를 관찰하기 위한 것이다. 실제 네트워크 완료 시간을 작은 타이머 숫자로 대신 보장하지 않는다. 코드에서 신뢰할 수 있는 것은 문서화된 완료 신호와 실행 규칙이며, 단 한 번 측정한 지연값은 그 실행의 관찰값이다.

## 3. 동기 호출의 실행 흐름

```javascript
function double(n) {
  console.log("compute");
  return n * 2;
}
console.log("start");
const value = double(3);
console.log("result", value);
console.log("end");
```

출력은 `start`, `compute`, `result 6`, `end` 순서다. `double`이 끝나야 호출 표현식의 값 `6`을 받아 다음 줄로 간다. 같은 실행 스레드에서 긴 동기 계산을 하면 그 계산이 끝날 때까지 다른 JavaScript 실행도 기다릴 수 있다.

**블로킹(blocking)** 은 현재 실행 자원이 다음 일을 진행하지 못하고 묶여 있는 상태를 가리킨다. 동기·비동기는 완료를 전달하는 흐름의 관점이고 블로킹·논블로킹은 자원을 점유하며 기다리는지의 관점이다. 관련이 많지만 완전히 같은 분류는 아니다.

### 호출자도 끝날 때까지 기다리는 구간

```javascript
function first() {
  console.log("first start");
  const value = second();
  console.log("first end", value);
}
function second() {
  console.log("second");
  return 2;
}
first();
console.log("outside");
```

출력은 `first start`, `second`, `first end 2`, `outside`다. second의 결과를 필요로 하는 first뿐 아니라 first를 호출한 최상위 흐름도 해당 호출이 반환할 때까지 진행하지 않는다. 이 관계는 호출 스택의 중단·복귀 모델로 설명할 수 있다.

동기 함수가 파일 읽기나 긴 계산을 수행한다면 그 시간도 이 호출 구간에 포함될 수 있다. 동기라는 말은 빠르거나 느리다는 평가가 아니라 결과를 직접 돌려받는 제어 흐름의 계약이다.

## 4. 비동기 등록과 나중의 실행

```javascript
console.log("start");
setTimeout(() => {
  console.log("timer");
}, 0);
console.log("end");
```

```text
start
end
timer
```

`setTimeout`은 브라우저·`Node.js가` 제공하는 타이머 API다. ECMAScript 언어 자체의 함수가 아니다. 지금 함수 안의 본문을 실행하는 대신 타이머를 등록하고 반환한다. `0`은 바로 현재 코드를 끊고 실행하라는 뜻이 아니다.

**[미리보기: Callback]** 다른 API에 실행할 함수 값을 넘기는 것을 콜백이라고 한다. 이 함수가 받는 인자·반환값·오류 계약은 Async JavaScript의 Callback에서 자세히 다룬다.

### 등록 함수의 반환값과 작업 결과

브라우저 setTimeout의 반환값은 나중 출력값이 아니라 등록된 타이머를 식별하는 값이다. `Node.js에서는` 반환되는 타이머 객체의 형태도 다르다. 서로 같은 이름의 API라도 반환 계약과 환경 차이를 확인한다.

나중 실행할 함수는 등록 시점에 함수 값으로 준비된다. 그 함수 안에서 외부 변수를 읽는다면 읽는 것은 실행 시점의 바인딩 값일 수 있다. 등록할 때 모든 외부 값이 자동으로 복사되어 고정된다고 가정하지 않는다. 앞서 배운 클로저 규칙이 비동기 경계에서도 유지된다.

```javascript
let state = "before";
setTimeout(() => console.log(state), 0);
state = "after";
console.log("registered");
```

출력은 `registered` 다음 `after`다. 비동기 후속 실행과 공유 상태의 읽기 시점을 함께 추적해야 하는 예제다.

## 5. 작업 완료와 반환값의 혼동

```javascript
let result = "not ready";
function startWork() {
  setTimeout(() => { result = "done"; }, 0);
  return result;
}
console.log(startWork()); // not ready
setTimeout(() => { console.log(result); }, 20); // done
```

`startWork`는 후속 처리를 예약한 뒤 현재의 문자열을 반환한다. 나중에 `result`를 바꿔도 이미 반환한 문자열이 소급해서 바뀌지 않는다. 두 번째 출력은 이 예제에서 뒤에 등록한 타이머가 실행될 때 관찰한 결과이며, 임의의 실제 I/O 완료를 20ms로 보장한다는 뜻은 아니다.

실제 코드에서 “충분히 오래 기다리면 완료됐겠지”라는 타이머를 추가하는 방식은 안정적인 완료 신호가 아니다. 완료를 알리는 API의 계약에 맞추어 의존하는 코드를 이어 붙여야 한다.

**[미리보기: Promise · async/await]** Promise는 나중의 성공·실패를 나타내는 값이고 `await`는 해당 결과 이후의 흐름을 연결한다. 사용법은 뒤의 Promise와 async / await에서 다룬다.

### 결과를 필요로 하는 코드는 완료 흐름 안에 둔다

```javascript
function readLater(done) {
  setTimeout(() => done(7), 0);
  return "scheduled";
}
const returned = readLater(value => console.log("completed", value));
console.log("returned", returned);
```

출력은 `returned scheduled`, `completed 7`이다. 현재 반환값은 등록 결과이고 나중의 7은 별도 완료 경로로 전달된다. 이 둘을 하나의 변수로 억지로 합치면 아직 준비되지 않은 값을 사용하기 쉽다.

동기 함수와 같은 모양으로 결과를 즉시 반환하도록 바꾸려면 단순히 내부에 return을 추가하는 것만으로는 안 된다. 호출자도 완료 이후의 흐름에 참여해야 한다. 구체적인 콜백·Promise 표현은 뒤의 해당 문서에서 연결한다.

## 6. 동시 진행과 병렬 실행

**동시성(concurrency)** 은 여러 작업의 진행을 겹쳐 관리하는 것이고, **병렬성(parallelism)** 은 여러 실행 자원이 실제로 같은 시점에 일을 수행하는 것이다. 단일 JavaScript 실행 스레드에서도 I/O 대기 구간을 겹쳐 동시 작업을 다룰 수 있다.

런타임은 운영체제·다른 스레드 등을 활용할 수 있지만, 모든 비동기 API마다 반드시 새 스레드가 하나 생기는 것은 아니다. 일반적인 JavaScript의 현재 코드 조각은 해당 실행 스레드에서 순서대로 실행된다.

| 작업 | 주로 소요되는 것 | 비동기라는 이름만으로 해결되는가 |
| --- | --- | --- |
| 서버 응답 대기 | 외부 I/O 대기 | 대기를 겹칠 수 있으나 네트워크 자체 시간은 남음 |
| 큰 배열 정렬 | CPU 계산 | 같은 스레드에서 수행하면 오래 점유할 수 있음 |
| 타이머 대기 | 호스트의 시간 관리 | 정확한 실행 시각을 보장하지 않음 |

CPU 계산을 타이머 안으로 옮겨도 계산하는 동안의 점유는 남는다. 별도 실행 자원으로 분리하거나 작업을 적절히 나누는 설계는 호스트 API와 성능 요구에 따라 선택한다.

### I/O와 CPU를 구분한 시간표

```text
순차 시작: A 대기 ─ 완료 ─ B 대기 ─ 완료
겹친 시작: A 대기 ───────── 완료
           B 대기 ─ 완료
```

독립된 I/O 작업의 대기를 겹치면 전체 완료 시간을 줄일 수 있다. 하지만 서버가 동시에 처리할 수 있는 양과 네트워크 자원은 유한하므로 작업 수를 무제한으로 늘리는 것이 정답은 아니다. 실행량 제한은 비동기라는 계약과 별도로 설계한다.

CPU 계산은 같은 스레드에서 실제 연산하는 시간이다. 함수를 async로 선언하거나 타이머에 넣어도 그 연산 자체가 다른 스레드로 이동하지 않는다. [Node.js의 이벤트 루프 점유 지침](https://nodejs.org/learn/asynchronous-work/dont-block-the-event-loop)도 비동기 API 사용과 콜백 안의 계산 비용을 구분한다.

## 7. 실행 순서와 응답 순서

비동기 작업 A를 먼저 시작했다고 B보다 먼저 완료된다는 보장은 없다. 결과에 의존하는 코드라면 명시적으로 완료를 기다리고, 독립된 작업이라면 겹쳐 시작할 수 있다. 단순히 소스에 위아래로 나열한 것은 완료 순서를 정하는 계약이 아니다.

**[미리보기: Event Loop]** 완료된 작업의 후속 함수를 언제 실행할지는 런타임의 스케줄링 규칙과 연결된다. 현재 코드·타이머·후속 처리의 순서는 다음 Event Loop와 Task Queue / Microtask Queue에서 다룬다.

### 시작 순서가 다른 완료 순서를 강제하지 않는다

```javascript
const completed = [];
setTimeout(() => { completed.push("A"); console.log(completed.join(",")); }, 20);
setTimeout(() => { completed.push("B"); console.log(completed.join(",")); }, 0);
```

보통의 별도 실행에서는 `B`, `B,A` 순서로 관찰된다. 이 예제는 지연 조건을 다르게 주어 나중 등록한 후속 처리가 먼저 실행될 수 있음을 보여 준다. 실제 I/O라면 응답 크기·캐시·서버 부하 등이 완료 순서를 바꿀 수 있다.

여러 결과를 모을 때는 완료된 순서대로 저장할지 원래 요청 순서에 대응시킬지도 정해야 한다. 어떤 결과가 최신 요청의 것인지 중요하다면 요청 ID와 순서를 함께 관리한다. 나중에 도착한 결과가 무조건 최신 상태라는 뜻은 아니다.

## 8. 흔한 오해·예외·주의점

- **비동기는 항상 더 빠르다**: 전체 대기는 겹칠 수 있지만 개별 작업 시간과 관리 비용은 남는다.
- **비동기 함수 안의 모든 줄은 나중에 실행된다**: 등록·인자 계산·일부 본문은 지금 실행될 수 있다.
- **타이머 시간을 늘리면 완료가 보장된다**: 외부 작업의 완료 신호를 사용한다.
- **비동기이면 CPU 계산도 다른 스레드로 간다**: API와 런타임의 동작을 별도로 확인한다.

### 비동기 계약에도 지금 실행되는 코드가 있다

호스트 API를 호출하기 위한 인자 계산, 입력 검증, 등록 처리 등은 지금 실행될 수 있다. 따라서 비동기 작업을 시작하는 함수가 호출 직후 예외를 던지는지, 실패를 나중의 완료 신호로 전달하는지 문서에서 확인해야 한다.

완료 대기를 겹치더라도 공유 상태를 제자리 변경하면 실행 순서에 따라 결과가 달라질 수 있다. JavaScript 후속 함수들이 한 스레드에서 순서대로 실행된다는 사실만으로 논리적인 순서 의존이 모두 사라지는 것은 아니다. 어떤 값을 어느 시점의 것으로 사용할지 정한다.

## 9. 실무 적용과 디버깅 관점

로그를 작업 시작, 호스트 완료 통지, 후속 코드 진입으로 나누고 작업 ID를 함께 기록한다. 요청이 여러 개라면 시작 순서와 완료 순서가 뒤집히는 경우도 재현한다. 기다리는 중인지 JavaScript가 CPU를 쓰는 중인지 구분해야 성능 원인에 맞는 조치를 고를 수 있다.

### 대기와 점유를 분리하는 진단

기능 시작부터 최종 결과까지 길었다면 구간을 세분한다. 요청을 보내기 전 계산, 외부 대기, 완료 후 JavaScript 진입 대기, 결과 처리 계산을 각각 측정한다. 네트워크는 빨랐지만 긴 동기 작업 때문에 결과를 늦게 처리했을 수도 있다.

작업 ID를 붙여 시작·완료·반영을 별도로 남기면 순서 뒤집힘을 추적할 수 있다. 성능 개선도 외부 대기를 줄이는 것인지, 대기를 겹치는 것인지, 계산 점유를 줄이는 것인지 구분해 적용한다.

### 통합 사례: 시작·완료·반영을 구분한다

검색 입력 A 다음 B를 처리하는 경우를 단순한 타이머로 흉내 낸다. 목표는 나중에 도착한 결과를 무조건 최신으로 반영하는 것이 아니라, 어느 요청에 대응하는 완료인지 구분하는 것이다.

```javascript
let latestId = 0;
function request(label, delay) {
  const id = ++latestId;
  console.log("start", label);
  setTimeout(() => {
    console.log("complete", label);
    if (id === latestId) console.log("apply", label);
  }, delay);
}
request("A", 20);
request("B", 0);
```

이 별도 실행에서는 `start A`, `start B`, `complete B`, `apply B`, `complete A` 순서를 관찰한다. 두 작업은 시작 순서와 완료 순서가 다르다. 완료된 A도 여전히 실행되지만 최신 요청 ID와 다르므로 반영하지 않는다.

이 예제는 작업을 취소한 것이 아니다. 결과를 사용할지 판단하는 정책을 추가했을 뿐이다. 실제 API가 취소를 지원하는지와 이미 수행한 효과가 있는지는 별도 계약이다. 따라서 “비동기를 해결했다”보다 요청 식별·완료 관찰·결과 사용을 나누어 설명한다.

타이머 숫자는 외부 I/O 시간을 보장하지 않고 순서 역전 가능성을 재현하기 위한 값이다. 실제 코드에서는 요청 ID와 데이터 계약을 사용해 어떤 완료 순서에서도 의도한 결과만 반영하도록 설계한다.

## 10. 핵심 정리

비동기에서는 함수 반환과 작업 완료가 분리될 수 있다. 현재 값과 미래 결과를 혼동하지 않고 완료 신호를 따라 의존 코드를 배치한다. 동시 진행은 병렬 실행과 다르며 비동기 API 안의 계산도 실행 자원을 점유한다.

## 1. 학습 목표

- 일반 작업과 마이크로태스크의 실행 기회를 비교한다.
- 체크포인트에서 새로 등록한 마이크로태스크의 순서를 추적한다.
- 큐가 하나라는 가정과 “무조건 즉시”라는 오해를 교정한다.
- 마이크로태스크 과다 등록이 응답성을 해치는 이유를 설명한다.

## 2. 이 주제를 왜 배우는가

같은 시점에 후속 실행을 예약해도 타이머와 `queueMicrotask`의 순서가 다르다. 모두 “나중에 실행”이라는 말만으로는 결과를 설명할 수 없다. 어떤 큐에 언제 등록되었는지와 언제 그 큐를 처리하는지가 필요하다.

이 문서는 브라우저의 HTML 이벤트 루프를 기준으로 한다. `queueMicrotask`와 `setTimeout`은 호스트 API다. `Node.js에도` 제공되지만 Node 전용 큐와 단계까지 이 문서의 단순 모델로 일반화하지 않는다.

### 나중이라는 표현을 실행 경계로 바꾼다

후속 처리를 예약한 시각, 실행 준비가 된 시각, 실제 실행된 시각을 구분한다. task와 microtask는 이 마지막 실행 기회를 다른 규칙으로 얻는다. “먼저 예약했으니 먼저 실행”이라는 직감보다 큐 종류와 처리 경계를 표시해야 한다.

마이크로태스크는 짧다는 성능 측정값으로 분류되는 함수가 아니다. 그 처리 경로로 예약된 작업이라는 뜻이다. 긴 계산을 queueMicrotask에 넣어도 계산 시간이 줄어들지 않으며 다음 작업으로 돌아갈 기회는 오히려 늦어질 수 있다.

## 3. Task와 Microtask

**작업(task)** 은 이벤트 루프가 선택하여 처리하는 작업 단위다. 타이머 후속 실행이나 사용자 입력 관련 처리가 예다. **마이크로태스크(microtask)** 는 마이크로태스크 체크포인트에서 처리하는 후속 작업 단위다.

| 기준 | Task | Microtask |
| --- | --- | --- |
| 대표 등록 | 타이머·호스트 이벤트 등 | `queueMicrotask` |
| 처리 기회 | 이벤트 루프의 작업 선택 | 정해진 체크포인트 |
| 새 후속 작업 | 이후 작업 선택의 대상 | 같은 체크포인트에서 이어 처리될 수 있음 |
| 주의점 | 다른 작업 소스와 실행 가능 조건 | 연속 등록으로 다음 작업을 지연시킬 수 있음 |

“매크로태스크”는 일반 task와 비교할 때 자주 쓰는 교육 용어다. HTML 표준의 기본 용어는 task이며, 실제 task queue는 단 하나의 모든 작업 공용 FIFO가 아니다. 반면 한 이벤트 루프의 마이크로태스크 큐 처리에서는 등록 순서가 중요하다.

### 일반 큐와 체크포인트의 차이

task queue는 HTML에서 단순한 하나의 공용 FIFO로 정의되지 않는다. 이벤트 루프가 여러 큐 가운데 실행 가능한 작업을 선택하는 조건이 있다. 반면 마이크로태스크 체크포인트는 해당 큐의 항목을 차례로 처리하여 비우는 절차로 이해할 수 있다.

[HTML의 체크포인트 알고리즘](https://html.spec.whatwg.org/multipage/webappapis.html#perform-a-microtask-checkpoint)은 재진입을 막는 상태도 관리한다. 마이크로태스크 처리 중에 다시 체크포인트를 시작해 같은 큐를 무작정 중첩 처리하는 모델이 아니다. 내부 알고리즘의 세부 상태를 코드에서 직접 조작하는 것도 아니다.

이 구분은 “스택이 비면 매번 이벤트 루프가 새 작업 하나를 고른다”는 단순 그림을 교정한다. 현재 동기 실행 정리 중 수행되는 체크포인트와 다음 일반 작업 선택은 서로 다른 단계다.

## 4. 기본 실행 순서

```javascript
console.log("A");
setTimeout(() => console.log("T"), 0);
queueMicrotask(() => console.log("M"));
console.log("B");
```

```text
A
B
M
T
```

`queueMicrotask`는 함수를 지금 중간에 실행하지 않고 예약한다. 현재 동기 코드는 `B`까지 이어진다. 그 뒤 적절한 체크포인트에서 `M`을 실행하고, 다음 타이머 작업이 선택되면 `T`를 실행한다.

우선 처리된다는 뜻을 “현재 실행 중인 코드를 끊는다”로 이해하면 안 된다. 높은 우선순위라는 표현보다 어떤 경계에서 처리되는지로 설명하는 것이 정확하다.

### 등록이 즉시 호출을 뜻하지 않는다는 반례

```javascript
function schedule() {
  console.log("inside start");
  queueMicrotask(() => console.log("microtask"));
  console.log("inside end");
}
schedule();
console.log("outside");
```

출력은 `inside start`, `inside end`, `outside`, `microtask`다. 일반 함수 schedule이 반환하는 순간마다 무조건 마이크로태스크를 끼워 넣는 규칙이 아니다. 현재 스크립트의 동기 실행이 이어진다는 점을 확인한다.

예측 표에는 함수 진입·반환보다 호스트가 현재 실행을 정리하고 체크포인트를 수행하는 경계를 먼저 표시한다. 이 방식이면 “같은 함수 안이 아니니 microtask가 먼저겠지”라는 잘못된 추론을 피할 수 있다.

## 5. 체크포인트에서 큐가 빌 때까지

```javascript
queueMicrotask(() => {
  console.log("M1");
  queueMicrotask(() => console.log("M3"));
});
queueMicrotask(() => console.log("M2"));
setTimeout(() => console.log("T"), 0);
console.log("S");
```

출력은 `S M1 M2 M3 T` 순서다. 처음 큐에는 M1, M2가 있다. M1을 처리하는 중 M3를 뒤에 추가하므로 M2 다음에 M3가 실행된다. 체크포인트는 처음에 있던 마이크로태스크 하나만 실행하고 끝나지 않는다. 새 항목도 처리하여 큐를 비운다.

```text
현재 스크립트 끝: [M1, M2]
M1 실행 후:      [M2, M3]
M2 실행 후:      [M3]
M3 실행 후:      [] → 다음 작업을 선택할 수 있음
```

실제 체크포인트는 작업 끝 외에도 스크립트 실행 정리 과정 등 표준이 정한 지점에서 수행된다. “모든 함수 return마다 항상 큐를 비운다”는 규칙은 아니다. 임의의 일반 함수 호출 중간에 마이크로태스크가 끼어든다고 추측하지 않는다.

### 새 항목은 큐 뒤에 붙는다

M1이 M3를 추가한다고 M3가 현재 대기하던 M2 앞으로 순간 이동하지 않는다. 현재 실행 중인 항목은 끝까지 처리하고, 이미 대기 중인 항목 다음으로 새 항목을 처리한다. 이 관계를 큐 내용의 변화로 그리면 중첩 함수의 코드 위치에 덜 의존하게 된다.

또한 M1이 아주 많은 마이크로태스크를 추가하면 그 항목들까지 모두 처리한 뒤에야 다음 일반 작업으로 갈 수 있다. 원래 큐 길이를 처음에 한 번 저장한 뒤 그 개수만 처리하고 끝내는 모델과 다르다. 코드 분석에서는 각 콜백이 추가로 예약한 항목도 놓치지 않는다.

## 6. 타이머 작업 안에서의 등록

```javascript
setTimeout(() => {
  console.log("T1");
  queueMicrotask(() => console.log("M"));
  console.log("T1-end");
}, 0);
setTimeout(() => console.log("T2"), 0);
```

같은 환경에서 나란히 등록한 이 타이머 예제의 출력은 `T1 T1-end M T2`다. T1의 동기 코드를 끝내고 체크포인트에서 M을 처리한 뒤 T2로 진행한다. M이 등록 즉시 `T1-end` 앞에 실행되는 것도, 모든 타이머가 다 끝날 때까지 기다리는 것도 아니다.

다른 작업 소스들 사이의 전체 순서까지 이 타이머 예제로 일반화하지 않는다. 입력·네트워크·문서 상태가 섞인 경우에는 각 작업의 생성 규칙과 실행 가능 조건을 확인한다.

### 한 작업의 끝과 다음 작업의 시작 사이

```javascript
setTimeout(() => {
  console.log("T1");
  queueMicrotask(() => {
    console.log("M1");
    queueMicrotask(() => console.log("M2"));
  });
}, 0);
setTimeout(() => console.log("T2"), 0);
```

이 독립 예제의 출력은 `T1 M1 M2 T2`다. T1에서 준비한 M1과 그 안에서 추가한 M2를 체크포인트에서 처리한다. 타이머가 먼저 등록되었다는 이유로 T2가 마이크로태스크 사이에 끼어들지는 않는다.

같은 원칙을 모든 작업 소스의 절대 순서로 확대하지 않는다. 여기서는 같은 방식으로 등록한 두 타이머와 그 사이의 체크포인트라는 조건을 명시했다. 실제 페이지에서는 문서 상태와 여러 호스트 작업이 함께 작용할 수 있다.

## 7. Microtask starvation

**기아(starvation)** 는 한 종류의 실행이 계속 우선되어 다른 작업이 실행 기회를 얻지 못하는 상황이다. 마이크로태스크가 자기 자신을 무한히 다시 등록하면 큐를 비울 수 없어 다음 작업이나 렌더링이 계속 지연될 수 있다.

다음 코드는 유한한 예제로, 작업을 나누어 적어도 타이머에 실행 기회를 주지 않는다는 점을 보여 준다.

```javascript
let count = 0;
function step() {
  count += 1;
  if (count < 3) queueMicrotask(step);
  else console.log("microtasks done");
}
queueMicrotask(step);
setTimeout(() => console.log("timer"), 0);
```

`microtasks done` 다음 `timer`가 출력된다. 무거운 계산을 마이크로태스크 여러 개로 잘라도 그 사이 화면이 반드시 반응하는 것은 아니다. 다음 작업으로 제어를 넘기는 것과 체크포인트 안에서 후속 처리를 이어 가는 것은 다르다.

### 분할했지만 제어를 돌려주지 않은 경우

작업을 여러 마이크로태스크로 나누면 호출 한 번의 길이는 작아질 수 있다. 그러나 큐가 계속 채워지면 그 묶음 전체가 다른 작업의 실행 기회를 막는다. 성능에서 중요한 것은 함수 하나의 길이뿐 아니라 체크포인트 전체가 끝나는 데 걸린 시간이다.

예를 들어 1ms 계산을 1만 개 연속 예약하면 각 함수는 짧아도 다음 작업까지의 총 지연은 커질 수 있다. 이때 단순히 함수 이름을 작게 분리하는 것보다 작업 사이에 실제로 호스트에 제어를 돌려줄 필요가 있는지 판단한다. 렌더링과 입력 응답 요구가 있는 코드에서는 이 차이가 중요하다.

## 8. Promise와의 연결 범위

**[미리보기: Promise]** Promise의 `then` 후속 처리는 ECMAScript의 Job 규칙을 통해 브라우저의 마이크로태스크 처리와 연결된다. 상태 전이·반환값·오류 전파는 뒤의 Promise에서 다룬다.

Promise의 내부 규칙을 배우기 전에는 모든 `then`이라는 글자를 발견한 순간 큐에 들어간다고 외우지 않는다. 언제 실행 준비가 되는지는 그 Promise의 상태와 연결 관계에 달려 있다.

## 9. 흔한 오해·예외·주의점

- 마이크로태스크는 별도 스레드에서 병렬 실행되는 코드가 아니다.
- 타이머 시간을 작게 지정해도 마이크로태스크 체크포인트를 무시하지 않는다.
- 마이크로태스크 하나를 끝내도 큐에 새 항목이 있으면 계속 처리할 수 있다.
- `Node.js의` `nextTick`까지 “Promise와 같은 하나의 큐”로 합쳐 설명하지 않는다.

### 큐의 이름으로 업무 완료를 판단하지 않는다

마이크로태스크가 실행됐다고 관련 외부 작업이 전부 완료됐다는 뜻은 아니다. 그 함수가 무엇을 읽고 어떤 후속 작업을 시작하는지 확인해야 한다. 큐는 실행 시점의 계약이고 업무상 성공 여부는 각 작업의 결과 계약이다.

queueMicrotask는 브라우저가 제공하는 API이며 Promise 전체를 만들어 주는 문법이 아니다. `Node.js에서` 같은 이름을 제공하더라도 전용 nextTick 큐까지 하나로 합친 표를 만들지 않는다. 이 문서는 HTML의 task·microtask 관계에 적용 범위를 제한한다.

## 10. 실무 적용과 디버깅 관점

실행 예측은 동기 로그, 등록한 큐, 준비되는 시점, 큐 처리 후 추가된 항목을 표로 적는다. 로그에 등록 순번과 실제 실행 순번을 함께 넣으면 “늦게 등록했는데 먼저 실행”의 이유를 추적하기 쉽다. 응답성이 나쁘면 긴 함수 하나뿐 아니라 연속된 마이크로태스크 구간도 확인한다.

### 로그만으로 순서를 확인하는 방법

각 예약 지점에 등록 로그를, 각 후속 함수의 시작에 실행 로그를 둔다. 그리고 동기 구간이 끝났을 때 대기 중인 task·microtask를 별도 목록으로 적는다. 후속 함수가 새 항목을 추가하면 목록의 뒤에 표시하고 큐가 비는 시점을 찾는다.

예상과 다르면 로그의 작성 위치가 아니라 실제 등록 시점과 큐 종류부터 확인한다. 콜백 안에서 등록한 것을 최상위에서 등록한 것처럼 계산하거나 일반 함수 return을 체크포인트로 오해하는 경우가 흔하다. 큰 라이브러리 호출을 제거하고 queueMicrotask·타이머·동기 출력만 남기면 규칙을 검증하기 쉽다.

### 통합 사례: 큐 내용으로 중첩 예약을 계산한다

동기 스크립트가 M1과 타이머 T를 등록하고, M1은 M2를 등록한다고 하자. 타이머 T도 나중에 M3를 등록한다. 소스의 들여쓰기만 보지 말고 각 경계에서 남은 큐를 그려 본다.

```javascript
queueMicrotask(() => {
  console.log("M1");
  queueMicrotask(() => console.log("M2"));
});
setTimeout(() => {
  console.log("T");
  queueMicrotask(() => console.log("M3"));
}, 0);
console.log("S");
```

출력은 `S M1 M2 T M3`다. 스크립트 뒤 첫 체크포인트에서 M1과 새 M2를 처리한다. 그다음 T가 실행되고 T가 끝난 뒤의 체크포인트에서 M3를 처리한다. 처음부터 모든 M을 하나의 묶음으로 준비해 T 앞에 놓는 것이 아니다.

| 경계 | 준비된 마이크로태스크 |
| --- | --- |
| 스크립트 끝 | M1 |
| M1 실행 뒤 | M2 |
| 첫 체크포인트 종료 | 없음 |
| T 실행 뒤 | M3 |

이 표는 이미 등록된 작업과 앞으로 어떤 콜백이 실행되어야 등록될 작업을 구분한다. 복잡한 실행 순서 문제에서도 아직 실행하지 않은 함수 안의 예약 코드를 너무 일찍 큐에 넣지 않는 것이 핵심이다.

## 11. 핵심 정리

마이크로태스크는 현재 동기 코드를 끊지 않고 체크포인트에서 실행된다. 처리 중 추가한 항목도 같은 체크포인트에 이어질 수 있다. 다음 일반 작업으로 넘어가는 경계와 구분해야 순서와 응답성을 설명할 수 있다.

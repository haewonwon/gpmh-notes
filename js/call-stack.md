## 1. 학습 목표

- LIFO 규칙으로 중첩 함수 호출과 복귀를 설명한다.
- 스택 프레임과 지역 변수를 구분해 추적한다.
- 재귀의 종료 조건과 스택 한계를 설명한다.
- 오류 스택을 읽고 최초 원인과 호출 경로를 분리한다.

## 2. 이 주제를 왜 배우는가

오류 메시지에 함수 이름이 여러 줄 나열되는 이유는 오류가 발생한 함수에 이르기까지 호출 경로가 있기 때문이다. 최상단 메시지만 읽으면 어디서 잘못된 값을 만들었는지 놓칠 수 있다. 호출 스택은 함수가 누구를 부르고 어디로 돌아가는지를 정리한다.

**스택(stack)** 은 마지막에 넣은 항목을 먼저 꺼내는 LIFO 구조다. **호출 스택(call stack)** 은 활성 함수 호출을 추적하는 데 사용하는 모델이며, 현재 실행 중인 호출이 위에 놓인다. 명세는 실행 컨텍스트 스택으로 평가 전환을 설명한다.

### 오류 경로와 값의 생성 경로

`read.trim()`에서 TypeError가 발생해도 trim 자체가 원인인 것은 아닐 수 있다. 그 전에 호출자가 undefined를 넘긴 경로가 있다. 호출 스택을 읽으면 어디서 실패를 관찰했는지와 잘못된 값이 어디서 유입됐는지를 연결할 수 있다.

스택은 실행 시간 전체의 기록이 아니다. 이미 끝난 호출은 일반적인 활성 스택에서 빠진다. 따라서 현재 프레임 목록을 “프로그램 시작부터 실행한 모든 함수”로 읽지 않고, 아직 복귀하지 않은 호출의 관계로 읽는다.

## 3. 호출·프레임·복귀

**프레임(frame)** 은 디버거 등에서 하나의 활성 호출 상태를 나타낼 때 쓰는 말이다. 지역 변수, 인자, 복귀 위치를 구분해 보는 데 유용하다. 명세상의 컨텍스트와 엔진의 실제 프레임 구현이 항상 일대일로 같다고 단정하지는 않는다.

```javascript
function c() { return 3; }
function b() { return c() + 2; }
function a() { return b() + 1; }
console.log(a()); // 6
```

```text
최상위 → a → b → c
                  c가 3 반환
             b가 5 반환
        a가 6 반환
최상위가 결과 출력
```

`c()`가 실행되는 순간에는 `b()`와 `a()`가 모두 끝나지 않았다. 각 호출은 다음 계산을 이어갈 지점을 남겨 둔다. 스택이 바뀌는 것은 선언 순서가 아니라 실제 호출·반환 순서에 따른다.

### 프레임에는 복귀할 계산이 남아 있다

`return b() + 1`에서 b를 실행하는 동안 a는 단순히 아무 일도 하지 않는 것이 아니라 b의 결과에 1을 더해 반환할 위치를 남겨 두고 있다. LIFO 규칙은 이러한 중단 지점을 역순으로 이어 갈 수 있게 한다.

| 실행 지점 | 활성 호출을 아래에서 위로 읽기 | 다음 동작 |
| --- | --- | --- |
| a 진입 | 최상위, a | b 호출 |
| b 진입 | 최상위, a, b | c 호출 |
| c 진입 | 최상위, a, b, c | 값 반환 |
| c 복귀 뒤 | 최상위, a, b | b의 나머지 계산 |
| b 복귀 뒤 | 최상위, a | a의 나머지 계산 |

이 표에는 별도 프로세스나 다른 스레드의 실행은 포함하지 않는다. 한 실행 흐름의 활성 호출 관계를 먼저 정확히 그린 뒤 호스트의 비동기 처리와 연결한다.

## 4. 인자는 호출 전에 평가한다

```javascript
function left() { console.log("left"); return 2; }
function right() { console.log("right"); return 3; }
function add(a, b) { console.log("add"); return a + b; }
console.log(add(left(), right()));
```

출력은 `left`, `right`, `add`, `5` 순서다. 인자를 왼쪽부터 평가하면서 `left` 호출은 끝나고, `right` 호출도 끝난 다음 `add` 본문에 들어간다. 세 함수가 나란히 계속 스택에 쌓여 있는 것은 아니다.

실행 흐름을 그릴 때 “표현식에 함수 이름이 있으니 전부 동시에 들어간다”고 그리지 않는다. 호출의 인자 계산, 본문 진입, 반환을 나누어 적어야 한다.

### 중첩 표현식을 바깥부터 실행하지 않는다

```javascript
function mark(name, value) {
  console.log(name);
  return value;
}
function multiply(a, b) { return a * b; }
function total(a, b) { return a + b; }
console.log(total(mark("left", 1), multiply(mark("x", 2), mark("y", 3))));
```

출력은 `left`, `x`, `y`, `7`이다. 바깥 total의 본문을 먼저 실행하는 것이 아니라 인자 평가 안의 호출들을 완료한 뒤 결과 1과 6을 전달한다. 표현식의 괄호 깊이만 보고 모든 함수가 동시에 스택에 남아 있다고 그리면 안 된다.

분석할 때는 각 호출 표현식을 “대상·인자 평가 → 본문 → 반환값으로 치환” 순서로 줄여 본다. 이 방식은 코드 줄 수보다 표현식 안에 중첩 호출이 많은 경우 특히 유용하다.

## 5. 재귀와 별개의 지역 변수

**재귀(recursion)** 는 함수가 자기 자신을 다시 호출하는 방식이다. 각 호출의 매개변수와 지역 값은 구분된다.

```javascript
function sumTo(n) {
  if (n === 0) return 0;
  const smaller = sumTo(n - 1);
  return n + smaller;
}
console.log(sumTo(3)); // 6
```

```text
sumTo(3): 3 + sumTo(2)를 기다림
sumTo(2): 2 + sumTo(1)를 기다림
sumTo(1): 1 + sumTo(0)를 기다림
sumTo(0): 0 반환 → 1 → 3 → 6으로 차례로 복귀
```

필요한 것은 **종료 조건(base case)** 과 그 조건에 가까워지는 입력 변화다. 위 함수에 음수를 넣으면 `0`에 도달하지 못하므로 입력 계약도 필요하다. 종료 조건이 있어도 너무 깊으면 스택 한계를 넘을 수 있다.

### 같은 함수의 지역 값은 호출별로 구분한다

```javascript
function countDown(n) {
  console.log("enter", n);
  if (n > 0) countDown(n - 1);
  console.log("leave", n);
}
countDown(2);
```

출력은 `enter 2`, `enter 1`, `enter 0`, `leave 0`, `leave 1`, `leave 2`다. 안쪽 호출의 n을 줄였다고 바깥 호출의 n이 0으로 바뀌지 않는다. 별개 매개변수 바인딩이므로 복귀할 때 각각의 n으로 마지막 출력을 수행한다.

종료 조건에 도달하는 것과 모든 호출이 반환한 것은 다르다. 가장 안쪽이 끝나도 바깥 프레임의 남은 계산을 차례로 수행해야 한다. 재귀의 앞 처리와 뒤 처리가 서로 다른 순서로 나타나는 이유다.

## 6. 스택 오버플로와 반복문 선택

활성 호출을 계속 쌓으면 제한된 자원을 소모한다. 깊은 재귀는 환경에 따라 `RangeError: Maximum call stack size exceeded` 등으로 실패할 수 있다. 정확한 최대 깊이는 엔진·옵션·함수 상태에 따라 달라지므로 특정 숫자로 외우지 않는다.

```javascript
function sumToIterative(n) {
  let total = 0;
  for (let current = 1; current <= n; current += 1) {
    total += current;
  }
  return total;
}
console.log(sumToIterative(3)); // 6
```

반복문은 같은 계산을 추가적인 재귀 호출 없이 수행한다. 재귀가 구조를 더 잘 표현할 때도 있지만, 입력 크기가 큰 목록 처리에는 반복이 적합할 수 있다. 꼬리 호출 최적화가 모든 실행 환경에서 재귀 깊이를 해결해 준다고 기대하지 않는다.

### 종료 조건의 유효 범위

`if (n === 0)`이 있다고 모든 입력에서 종료하는 것은 아니다. 음수, NaN, 소수처럼 단계 변화가 조건에 도달하지 못하는 값도 고려한다. 재귀 함수의 계약에는 허용 입력과 각 호출이 목표에 가까워지는 규칙이 필요하다.

스택 사용량은 총 호출 횟수보다 **동시에 활성화된 깊이**와 더 직접적으로 연결된다. 반복문에서 함수를 백만 번 차례로 호출해도 각 호출이 돌아온 뒤 다음을 부르면 깊이가 계속 누적되지는 않는다. 반면 반환 전 재귀로 계속 들어가면 아직 끝나지 않은 호출이 쌓인다.

성능 조사에서는 깊이뿐 아니라 같은 하위 문제를 반복 계산하는지도 별도로 본다. 재귀와 반복 중 어느 문법을 썼는지 하나만으로 시간 복잡도까지 판단할 수는 없다.

## 7. 오류 스택을 읽는 방법

오류 스택은 보통 발생 지점과 그곳까지의 호출 경로를 보여 준다. `Error.stack`의 정확한 형식과 프레임 이름은 환경에 따라 다를 수 있다.

```javascript
function parseAge(value) {
  return value.trim();
}
function submit() {
  return parseAge(undefined);
}
// submit(); // 별도 실행 시 TypeError: undefined에서 trim을 읽을 수 없음
```

발생 지점은 `parseAge`의 속성 접근이지만, 잘못된 값을 넘긴 지점은 `submit`이다. 따라서 가장 위 프레임의 줄만 고치기보다 호출 인자가 어디서 만들어졌는지 거슬러 올라간다. 이 예제에서는 재귀가 없어도 타입 오류의 경로를 스택으로 추적할 수 있다.

### 실제 프레임에서 확인할 정보

오류 스택의 첫 관심사는 실패 위치, 다음은 바로 위 호출자가 전달한 값이다. 프레임 이름이 익명으로 보이거나 빌드 결과의 줄 번호라면 원본 코드와 연결하는 소스맵이 있는지도 확인한다. 엔진·도구가 일부 호출을 생략하거나 비동기 인과관계를 붙일 수 있다는 조건도 기록한다.

```text
TypeError: 값을 읽는 데 실패
  at parseAge (입력 사용 지점)
  at submit   (인자 공급 지점)
  at 최상위   (기능 시작 지점)
```

위는 설명용 모양이며 환경마다 동일한 문자열을 보장하지 않는다. 메시지의 정해진 줄 번호를 파싱하는 코드보다 오류 객체와 명시적 작업 정보를 함께 남기는 방식이 안정적이다.

## 8. 흔한 오해·예외·주의점

- 호출 스택은 모든 객체가 저장되는 공간이나 대기 작업 전체를 뜻하지 않는다.
- 함수가 반환했다고 그 함수가 만든 객체가 반드시 즉시 사라지지는 않는다.
- 중단점에서 보이는 프레임 수를 최대 재귀 깊이의 보편적인 규칙으로 사용하지 않는다.
- 오류 스택의 비동기 연결 표시는 디버거가 덧붙인 인과관계일 수도 있다. 그 전체가 한순간 실제로 활성화된 동기 호출 목록이라는 뜻은 아니다.

### 스택이 비어도 모든 일이 끝난 것은 아니다

현재 동기 호출들이 반환했다는 사실은 호스트의 대기 작업도 모두 완료됐다는 뜻이 아니다. 타이머나 I/O가 남아 있으면 나중에 새로운 실행 흐름이 시작될 수 있다. 반대로 반환된 객체는 다른 곳에서 참조하므로 해당 호출이 끝나도 계속 사용될 수 있다.

이 때문에 스택을 메모리 전체 또는 작업 대기열 전체와 같은 그림으로 그리지 않는다. “활성 호출”, “남은 작업”, “보관한 데이터”를 별도로 표시하면 호출 복귀와 비동기 완료, 데이터 수명을 섞지 않을 수 있다.

## 9. 실무 적용과 디버깅 관점

재귀 오류에서는 반복되는 함수 이름, 종료 조건의 입력, 한 단계마다 줄어드는 값을 확인한다. 일반 오류에서는 현재 프레임의 값과 호출자의 전달값을 비교한다. 코드를 작은 입력으로 줄여 호출·반환을 손으로 그리면 빠진 반환이나 잘못된 인자 계산을 찾기 쉽다.

**[미리보기: Event Loop]** 타이머의 후속 함수는 등록 위치의 동기 호출이 끝난 뒤 다른 시점에 실행될 수 있다. 대기 작업과 호출 스택의 연결은 Async JavaScript의 Event Loop에서 다룬다.

### 재귀 문제를 작은 입력으로 추적한다

최소 입력, 종료 입력, 정상적인 한 단계 큰 입력을 각각 실행한다. enter와 leave 로그를 나누어 깊이가 줄어드는지와 복귀 뒤 계산이 의도대로 수행되는지 본다. 음수 같은 허용되지 않는 입력은 함수 진입 경계에서 막을지 계약을 정한다.

프로덕션에서 최대 깊이를 찾기 위해 무한 재귀를 실행하는 것은 진단법이 아니다. 작은 재현으로 입력 변화와 복귀 흐름을 확인하고, 큰 입력이 합법적으로 필요하다면 반복이나 명시적인 자료 구조로 활성 깊이를 제한하는 설계를 검토한다.

### 통합 사례: 반환 전후 작업의 순서

폴더 구조를 내려가며 처리할 때 진입 로그와 복귀 로그의 순서가 다르게 나오는 이유를 간단한 재귀로 재현한다. 목표는 함수 이름이 반복된다는 사실보다 어느 호출이 무엇을 기다리는지 설명하는 것이다.

```javascript
function visit(n) {
  const name = "level-" + n;
  console.log("open", name);
  if (n > 0) visit(n - 1);
  console.log("close", name);
}
visit(1);
```

출력은 `open level-1`, `open level-0`, `close level-0`, `close level-1`이다. 안쪽 호출이 실행되는 동안 바깥 호출의 name은 level-1로 남아 있고, 안쪽은 자신의 name인 level-0을 사용한다. 안쪽이 끝나야 바깥 close로 돌아간다.

이 예제를 실행 표로 옮기면 진입마다 프레임을 하나 추가하고 복귀마다 가장 위 프레임을 제거한다. close가 순서대로 1,0이 나와야 한다고 예상했다면 진입 순서와 복귀 순서를 혼동한 것이다. 모든 처리 작업을 재귀 호출 앞에 둘지 뒤에 둘지에 따라 관찰 순서도 달라진다.

큰 데이터의 오류를 조사하기 전 깊이 0·1·2에서 이 순서를 확인한다. 입력이 한 단계씩 종료 조건에 가까워지는지도 함께 기록한다. 마지막 값만 맞는지 확인하는 것보다 각 호출이 언제 끝났는지 확인하면 종료 누락과 복귀 뒤 계산 오류를 나눌 수 있다.

## 10. 핵심 정리

호출 스택은 현재 끝나지 않은 호출의 순서다. 가장 안쪽 호출이 먼저 반환하고 호출자는 중단했던 계산을 이어 간다. 재귀는 입력 변화와 종료 조건뿐 아니라 깊이 한계도 고려해야 한다.

## 1. 학습 목표

- 실행 컨텍스트를 코드 평가에 필요한 상태로 설명한다.
- 함수 정의와 함수 호출 시 생기는 상태를 구분한다.
- 실행 준비·본문 평가·복귀의 흐름을 추적한다.
- 명세의 추상 모델과 엔진 내부 구현을 구분한다.

## 2. 이 주제를 왜 배우는가

같은 함수를 두 번 호출해도 매개변수와 지역 변수는 서로 섞이지 않는다. 다른 함수를 호출한 뒤에는 원래 위치로 돌아온다. 이 동작을 이해하려면 함수 코드뿐 아니라 “지금 어떤 호출을 실행 중인가”라는 상태도 추적해야 한다.

**실행 컨텍스트(execution context)** 는 ECMAScript 명세가 코드 평가의 진행 상황을 설명하기 위해 사용하는 장치다. 메모리에 반드시 같은 모양의 객체가 생성된다는 뜻은 아니다. 엔진은 최적화하더라도 관찰 가능한 언어 규칙을 지켜야 한다.

### 소스 코드와 현재 실행의 차이

`calculate(2)`와 `calculate(5)`는 같은 본문을 사용하지만, 현재 입력과 진행 위치는 다르다. 함수 소스만으로는 “어느 호출의 지역 변수인가”를 알 수 없으므로 실행 상태를 별도로 구별한다. 실행 컨텍스트는 이 차이를 설명하는 모델이다.

한 파일을 실행하면 파일 이름 하나만 상태로 들고 있는 것도 아니다. 최상위 코드를 평가하다가 함수로 들어가면 그 호출의 평가를 진행하고, 끝나면 원래 평가를 이어 간다. 코드의 정적 구조와 실행 중 상태를 분리해서 보면 동일한 함수의 재사용과 중첩 호출이 자연스럽게 연결된다.

## 3. 컨텍스트에 필요한 정보

컨텍스트에는 현재 함수·스크립트·모듈과 평가 진행 상태, 이름을 해석할 환경 정보 등이 연결된다. **환경 레코드(Environment Record)** 는 이름과 바인딩을 관리하는 명세상의 구조다. 실제 변수 값을 이름으로 찾을 수 있게 한다.

| 관점 | 추적하는 내용 |
| --- | --- |
| 코드 평가 상태 | 어느 지점까지 실행했고 어디서 이어갈지 |
| 함수·ScriptOrModule | 어느 함수 또는 소스 단위의 평가인지 |
| Realm | 기본 내장 객체 등과 연결된 실행 환경 |
| 어휘·변수 환경 | 이름을 찾고 바인딩을 관리하는 정보 |

`this`는 이 표의 모든 컨텍스트가 직접 소유하는 동일한 필드라고 단정하지 않는다. 함수 종류와 환경 규칙을 통해 해석된다. 예전 교재의 “변수 객체·스코프 체인·this 세 묶음”은 학습 모델이며 현재 명세 구조 전체와 일치하지는 않는다. [ECMAScript 실행 컨텍스트](https://tc39.es/ecma262/multipage/executable-code-and-execution-contexts.html#sec-execution-contexts) 참조.

### 환경 레코드는 변수 목록 이상의 계약이다

환경 레코드는 단순히 `{ 이름: 값 }`인 일반 JavaScript 객체라고 보면 부족하다. 이름이 존재하는지, 초기화되었는지, 재할당할 수 있는지 등을 언어 규칙에 맞게 관리한다. 미초기화 이름을 읽을 수 없는 것과 존재하지 않는 객체 속성의 읽기가 undefined인 것은 서로 다른 처리다.

컨텍스트의 어휘 환경은 현재 이름 해석에 사용할 환경을 가리킨다. 변수 환경은 일부 선언의 준비에 사용하는 환경을 나타낸다. 둘을 물리적으로 복사된 두 변수 창고로 이해하지 않는다. 같은 환경을 가리킬 수도 있고 평가 과정에서 다른 환경을 참조할 수도 있는 명세상의 연결이다.

**[미리보기: Scope]** 블록 진입이 현재 이름 해석 환경에 주는 영향은 렉시컬 중첩과 연결된다. 선언별 범위와 이름 검색은 뒤의 Scope · Lexical Scope · Scope Chain에서 자세히 다룬다.

명세의 [Environment Records](https://tc39.es/ecma262/multipage/executable-code-and-execution-contexts.html#sec-environment-records)는 환경을 바인딩 조작 연산으로 정의한다. 실제 디버거가 이 내부 상태 전부를 그대로 보여 준다고 기대하지 않는다.

## 4. 정의와 호출은 다른 단계다

```javascript
function addTax(price) {
  const tax = price * 0.1;
  return price + tax;
}
const first = addTax(100);
const second = addTax(200);
console.log(first, second); // 110 220
```

함수를 정의하면 나중에 호출할 수 있는 함수 객체가 만들어진다. 본문을 실제로 평가하는 것은 호출 시점이다. 각 호출에는 별개의 매개변수·지역 바인딩이 있으므로 첫 호출의 `price`와 두 번째 호출의 `price`는 같은 저장 공간으로 취급되지 않는다.

모든 호출이 무조건 하나의 단순한 전역 컨텍스트를 덮어쓰는 구조라면 중첩 호출과 재귀가 올바르게 동작할 수 없다. 호출마다 상태를 구별하고, 호출이 끝나면 중단했던 호출자로 복귀하는 모델이 필요하다.

### 같은 매개변수 이름을 별도 호출에 연결한다

```javascript
function format(value) {
  const text = "value=" + value;
  return text;
}
const first = format(2);
const second = format(5);
console.log(first, second); // value=2 value=5
```

첫 호출에서는 `value → 2`, `text → "value=2"`가 해당 평가의 상태다. 반환 후 두 번째 호출을 시작하면 `value → 5`, `text → "value=5"`인 별도 상태를 준비한다. 두 결과 문자열은 호출자에게 전달되어 변수 first와 second에 연결된다.

함수를 만드는 것과 호출 준비를 구분하면 함수 값 여러 개가 반드시 실행 컨텍스트 여러 개를 뜻하는 것도 아님을 알 수 있다. 함수 객체를 배열에 저장해 두기만 했다면 해당 본문을 평가하는 호출은 아직 없다. 반대로 같은 함수 객체를 여러 번 호출하면 각각 평가 상태가 필요하다.

## 5. 실행 준비와 본문 평가

일반적인 함수 호출은 다음과 같이 읽을 수 있다.

```text
호출 대상과 인자 평가
→ 해당 호출을 실행할 컨텍스트·환경 준비
→ 매개변수와 선언에 필요한 바인딩 준비
→ 함수 본문을 순서대로 평가
→ 반환 또는 예외로 호출을 종료하고 호출자에게 복귀
```

이 설명은 학습용 요약이다. 선언 종류에 따라 준비 규칙이 다르므로 “모든 변수가 먼저 undefined로 초기화된다”고 일반화하지 않는다. 매개변수 기본값, 블록, 모듈 등에도 각자의 준비 규칙이 있다.

**[미리보기: Hoisting · TDZ]** 선언 바인딩의 준비와 실제 초기화는 같은 시점이 아닐 수 있다. 선언 종류별 차이는 JavaScript Core의 Hoisting · TDZ에서 자세히 다룬다.

### 실행 준비는 본문을 대신 실행하지 않는다

선언 준비는 뒤에서 사용할 이름과 규칙을 마련하는 과정이다. 그렇다고 초기값 표현식이나 함수 본문을 전부 미리 수행하지는 않는다. 예를 들어 `const total = calculate()`의 calculate 호출은 그 초기화 코드를 평가할 때 실행된다. 함수 선언이 준비되는 것과 그 함수를 호출하는 것은 별개다.

| 시점 | 관찰할 질문 | 잘못된 추론 |
| --- | --- | --- |
| 호출 인자 평가 | 어떤 값이 실제로 전달되는가 | 매개변수 이름이 호출자의 이름과 공유된다 |
| 호출 준비 | 어느 함수의 어떤 호출인가 | 함수 선언 시 모든 호출 상태를 만든다 |
| 본문 평가 | 지금 어느 문장을 실행하는가 | 준비 단계에서 본문도 실행했다 |
| 복귀 | 어느 위치에 어떤 결과를 전달하는가 | 호출이 끝나면 결과 값도 모두 사라진다 |

명세는 인자 전달, this 처리, 선언 준비 등에 개별 절차를 둔다. 학습용 “생성 단계·실행 단계”를 사용할 때는 각 선언의 세부 규칙까지 모두 동일하다는 뜻으로 확장하지 않는다.

## 6. 중첩 호출의 실행 흐름

```javascript
function double(value) {
  console.log("double", value);
  return value * 2;
}
function calculate(base) {
  console.log("calculate", base);
  const result = double(base + 1);
  console.log("resume", result);
  return result + 10;
}
console.log("answer", calculate(3));
```

```text
calculate 3
double 4
resume 8
answer 18
```

`calculate`는 `double`을 부르는 동안 본문 진행을 잠시 멈춘다. `double`이 `8`을 반환하면 그 값을 `result`에 연결하고 다음 출력으로 이어간다. 반환된 숫자와 `double`의 실행 상태는 다른 것이다. 컨텍스트가 끝나더라도 반환한 값은 호출자에서 계속 사용한다.

### 진행을 멈춘 호출은 결과를 기다린다

```javascript
function make(value) {
  console.log("make", value);
  return { value: value };
}
function outer() {
  const first = make(1);
  const second = make(2);
  return first.value + second.value;
}
console.log(outer());
```

출력은 `make 1`, `make 2`, `3`이다. 첫 make 평가가 끝나면 outer는 결과 객체를 first에 연결하고 두 번째 make를 호출한다. 두 make 호출이 동시에 활성 상태로 남아 있는 것은 아니다. outer는 각각의 반환 뒤에 다음 위치로 진행한다.

반환된 객체는 make의 지역 이름과 별개의 접근 경로를 얻는다. 지역 평가의 종료와 값의 사용 가능 여부를 나누면 “지역 변수였는데 왜 반환 객체는 살아 있는가”라는 혼동을 줄일 수 있다.

## 7. 컨텍스트·범위·호출 순서의 구분

컨텍스트는 현재 평가의 상태이고, 범위는 이름이 어디에서 해석되는지에 관한 규칙이다. 둘은 관련이 있지만 같은 말이 아니다. 함수를 어디서 호출했는지와 함수 안의 바깥 이름이 어디를 가리키는지도 구분해야 한다.

**[미리보기: Call Stack · Scope]** 활성 호출을 쌓고 복귀하는 순서는 다음 Call Stack에서, 함수가 바깥 이름을 찾는 규칙은 Scope · Lexical Scope · Scope Chain에서 다룬다.

최상위 코드도 실행 형태를 구분한다. 브라우저의 일반 스크립트, ESM, Node.js CommonJS의 파일 래퍼는 같은 최상위 규칙을 갖지 않는다. 특히 “최상위 변수는 모두 전역 객체 속성이다”는 설명은 모듈과 `let`·`const`에 그대로 적용되지 않는다.

### Realm과 전역 환경을 구분한다

Realm은 기본 내장 객체와 전역 환경 등을 묶어 코드 평가의 기반을 제공하는 명세 개념이다. 모든 함수 호출이 새로운 Realm을 만드는 것은 아니다. 일반적으로 같은 실행 기반에서 여러 컨텍스트가 코드를 평가한다.

이 구분은 메모리·격리·동시성의 모든 개념을 한 번에 설명하려고 할 때 중요하다. “새 호출”이 곧 “새 스레드”, “새 전역 객체”, “새 브라우저 창”이라는 뜻은 아니다. 컨텍스트는 평가 상태, Realm은 그 코드가 사용하는 실행 기반이라는 서로 다른 질문에 답한다.

## 8. 흔한 오해·예외·주의점

- **함수를 선언하면 호출 컨텍스트도 실행된다**: 정의와 호출은 다르다.
- **실행 컨텍스트는 소스 파일이다**: 같은 코드라도 호출마다 평가 상태를 구분한다.
- **컨텍스트가 끝나면 관련 데이터가 즉시 모두 삭제된다**: 실행 종료와 데이터의 도달 가능성·수거 시점은 별개다.
- **엔진의 C++ 객체나 메모리 레이아웃을 그대로 나타낸다**: 명세상의 장치다. 구현의 배치나 최적화는 달라질 수 있다.

### 추상 모델을 물리 메모리 그림으로 고정하지 않는다

엔진은 변수를 레지스터에 둘 수도 있고, 일부 계산을 생략하거나 함수를 인라인할 수도 있다. 이런 구현 차이가 있더라도 JavaScript 코드에서 관찰되는 값과 실행 순서는 언어 계약을 따라야 한다. 따라서 특정 엔진의 메모리 배치를 모르면 이 주제를 이해할 수 없는 것은 아니다.

“컨텍스트가 끝나서 값이 삭제됐다”는 설명도 조심한다. 이름의 지역적 접근이 끝나는 것, 값에 대한 다른 참조가 남는 것, 엔진이 메모리를 실제로 회수하는 시점은 다른 문제다. 여기서는 실행 상태와 반환 흐름을 중심으로 설명하고 객체 수명을 추정해 단정하지 않는다.

## 9. 실무 적용과 디버깅 관점

중첩 호출을 디버깅할 때 현재 함수의 인자·지역 변수와 호출자의 변수를 따로 본다. 이름이 같아도 다른 호출의 변수일 수 있다. 함수 진입·호출 직전·복귀 직후에 중단점을 두면 값이 어느 단계에서 달라지는지 확인할 수 있다.

모듈 문제를 디버깅할 때는 실행 소스 형식도 기록한다. 개발자 도구가 보여 주는 호출 프레임은 유용한 관찰 도구지만, 명세의 모든 내부 상태를 그대로 표시하는 화면은 아니다.

### 디버거 관찰을 실행 표로 바꾼다

함수 진입 전에는 호출자의 인자를, 진입 후에는 현재 호출의 매개변수를 기록한다. 중첩 호출에서는 “현재 함수·중단된 호출자·복귀 지점·예정된 계산” 네 칸으로 표를 만든다. 동일한 이름이 여러 프레임에 있어도 어느 호출의 바인딩인지 구분할 수 있다.

반환값이 틀리면 준비 단계의 이름 문제인지 본문 계산 문제인지 먼저 나눈다. 본문 첫 줄에서 입력부터 틀렸다면 호출자나 인자 계산을 조사한다. 입력은 맞지만 반환 직전만 틀렸다면 해당 본문의 분기와 변경을 조사한다. 명세 모델은 이런 관찰 가능한 단계들을 일관되게 연결하는 데 사용한다.

### 통합 사례: 같은 함수의 두 실행을 구분한다

가격 계산 함수가 호출될 때마다 다른 결과를 낸다고 하자. 먼저 함수 정의가 달라졌는지보다 각 호출의 입력과 현재 평가 상태를 구분해야 한다. 함수 소스 하나와 호출 상태 여러 개를 따로 보는 연습이다.

```javascript
function calculate(base) {
  const fee = 2;
  return adjust(base) + fee;
}
function adjust(value) { return value * 2; }
const first = calculate(3);
const second = calculate(5);
console.log(first, second); // 8 12
```

첫 calculate의 준비에서는 base가 3에 연결되고 본문에서 fee가 2로 초기화된다. adjust(3)를 평가하는 동안 calculate는 더할 fee와 복귀 위치를 유지한다. adjust가 6을 반환하면 calculate는 8을 반환한다. 그다음 두 번째 calculate 호출이 별도의 입력 5로 시작한다.

중단점을 adjust 안에 두면 현재 value는 3이고 호출자 프레임의 base도 3인 첫 실행을 볼 수 있다. 다음 호출에서는 두 값이 각각 5다. 값이 같다는 것은 호출자와 피호출자의 바인딩이 하나라는 뜻이 아니다. 각 프레임의 이름을 별도로 읽어야 한다.

여기서 얻을 검증 기준은 함수 객체의 개수가 아니라 호출별 입력·지역 초기화·중첩 반환·호출자 계산이다. 이 네 단계가 맞으면 결과를 명세의 평가 전환으로 설명할 수 있으며, 실제 엔진의 프레임 메모리 배치를 추측할 필요는 없다.

## 10. 핵심 정리

실행 컨텍스트는 현재 코드 평가를 진행하고 다른 평가와 구별하기 위한 상태다. 함수 객체를 만드는 단계와 호출을 실행하는 단계를 나누어 본다. 준비·평가·복귀의 모델을 사용하되 명세 모델을 엔진의 물리 구조로 단정하지 않는다.

## 1. 학습 목표

## 2. 이 주제를 왜 배우는가

“1초 뒤 실행” 타이머가 2초 뒤 실행되거나 클릭에 대한 반응이 늦어지는 상황은 타이머 자체의 고장만으로 설명되지 않는다. 실행할 준비가 된 후속 코드도 현재 JavaScript가 실행 자원을 오래 사용하면 기다려야 한다.

**이벤트 루프(event loop)** 는 호스트가 준비된 작업들을 선택하고 실행하며 다른 처리를 조정하는 실행 모델이다. 이 문서의 기본 모델은 브라우저 HTML 표준이다. ECMAScript는 함수·Promise 같은 언어 규칙을 정하고, 브라우저는 이벤트·타이머·렌더링과 그 규칙을 연결한다.

### 준비된 일도 실행 기회를 기다린다

외부 작업이 완료된 시각과 그 결과를 처리하는 JavaScript가 실행된 시각 사이에는 차이가 있을 수 있다. 이벤트 루프를 배우면 이 간격을 “비동기가 느리다” 하나로 묶지 않고 현재 실행 부하와 스케줄링의 문제로 나눌 수 있다.

실제 서비스에서 입력 반응 지연은 외부 요청이 없어도 생긴다. 긴 계산이나 대량 동기 변환이 같은 실행 자원을 차지하면 이미 준비된 입력 관련 처리도 기다릴 수 있다. 현재 실행을 언제 끝내고 제어를 돌려주는지가 응답성의 핵심이다.

## 3. 엔진과 호스트의 역할

| 구성 | 역할 | 예 |
| --- | --- | --- |
| JavaScript 언어·엔진 | 코드 평가·함수 호출·값 처리 | 연산·호출 스택 |
| 호스트 API | 환경의 기능과 외부 작업 관리 | 타이머·네트워크·이벤트 |
| 이벤트 루프 | 실행 가능한 작업 선택과 처리 조정 | 타이머 후속 코드·사용자 입력 작업 |

타이머를 등록하면 호스트가 시간 조건을 관리한다. JavaScript 호출 스택에 타이머 함수가 1초 동안 그대로 쌓여 있는 것은 아니다. 시간 조건을 만족한 후 실행 가능한 작업으로 다루며, 실제 실행 시점은 다른 실행 상태의 영향을 받는다.

모든 비동기 작업이 똑같은 큐에 들어가거나 각 작업마다 별도 스레드를 받는다고 가정하지 않는다. 네트워크와 타이머의 준비 방법도 호스트의 책임이다.

### 호스트에 위임한 대기와 JavaScript 실행

setTimeout을 부르면 호출 자체는 타이머를 등록하고 반환한다. 타이머가 준비될 때까지 JavaScript가 반복문으로 시계를 확인하는 것이 아니다. 호스트가 조건을 관리하고, 준비된 후속 처리를 실행 모델에 연결한다.

이 때문에 호출 스택 그림에는 타이머 등록 함수를 1초 동안 남겨 두지 않는다. “현재 JavaScript 호출”과 “호스트가 보관한 대기 작업”을 다른 상자로 그린다. 호스트가 내부적으로 커널·스레드·다른 프로세스를 활용하는지는 개별 API 구현의 문제이며 작업마다 별도 스레드가 생긴다고 단정하지 않는다.

## 4. 한 번의 동기 실행과 다음 작업

```javascript
console.log("A");
setTimeout(() => {
  console.log("C");
  console.log("D");
}, 0);
console.log("B");
```

출력은 `A B C D` 순서다. 타이머 등록은 현재 스크립트를 중단하지 않는다. 현재 코드가 `B`까지 실행된 뒤 나중에 타이머 후속 코드가 실행된다. 그 후속 코드의 `C`와 `D`도 일반적인 동기 코드다.

이를 **run-to-completion** 원칙으로 설명한다. 현재의 동기 실행 구간을 다른 이벤트 루프 작업이 임의로 중간에 끊어 들어오지 않는다. 현재 코드가 직접 다른 함수를 호출하는 중첩 실행은 이 원칙과 다른 문제다.

### 작업 하나 안에서도 중첩 호출은 가능하다

```javascript
function inner() { console.log("inner"); }
function outer() {
  console.log("outer start");
  inner();
  console.log("outer end");
}
setTimeout(() => console.log("timer"), 0);
outer();
console.log("script end");
```

출력은 `outer start`, `inner`, `outer end`, `script end`, `timer`다. outer가 inner를 직접 부르는 것은 현재 실행 흐름 내부의 동기 호출이다. 타이머 작업이 외부에서 현재 실행을 가로채는 것과 다르다.

run-to-completion을 “함수 안에서는 아무 함수도 호출되지 않는다”로 해석해서는 안 된다. 현재 흐름은 중첩 호출과 복귀를 모두 수행하고 호스트에 제어를 돌려준 뒤 다른 일반 작업의 선택으로 이어진다.

## 5. 이벤트 루프의 개념적 흐름

```text
실행 가능한 작업 선택
→ 해당 작업의 JavaScript 등 처리
→ 필요한 후속 정리와 마이크로태스크 체크포인트
→ 조건이 맞으면 렌더링 관련 처리
→ 다음 작업 선택
```

이는 학습을 위한 요약이며 실제 HTML 알고리즘에는 문서 상태와 렌더링 기회 판단 등 더 많은 조건이 있다. 작업 큐는 하나의 전역 FIFO라고 단순화할 수 없으며, 작업 종류에 따른 선택과 실행 가능 조건이 있다.

**[미리보기: Task Queue / Microtask Queue]** 마이크로태스크는 다음 일반 작업 전에 체크포인트에서 처리되는 후속 작업이다. 큐의 차이와 중첩 등록 순서는 바로 다음 Task Queue / Microtask Queue에서 다룬다.

### task source와 task queue의 역할

HTML은 타이머·사용자 상호작용 등 작업의 원천을 구분하고 작업을 큐에 연결한다. 하나의 이벤트 루프가 여러 작업 큐를 가질 수 있고, 실행 가능한 작업을 선택하는 규칙도 고려한다. 모든 네트워크·입력·타이머를 단일 배열에 등록 순서대로 넣는 도식은 전체 표준을 설명하지 못한다.

같은 작업 소스의 순서 보장과 서로 다른 소스 사이의 선택을 나누어 읽어야 한다. 또한 문서 상태 때문에 당장 실행할 수 없는 작업이 있을 수 있어 단순한 첫 항목 꺼내기 모델만으로는 부족하다. [HTML 이벤트 루프 처리 모델](https://html.spec.whatwg.org/multipage/webappapis.html#event-loop-processing-model)을 기준으로 이 조건을 확인한다.

다만 입문 예제에서 서로 다른 소스의 모든 가능한 순서를 외울 필요는 없다. 현재 동기 구간이 끝나는 경계와, 특정 예제에서 확실히 보장되는 관계만 먼저 적고 나머지는 환경·조건에 따른다고 구분한다.

## 6. 긴 동기 코드와 지연

```javascript
// 브라우저 또는 Node.js: 짧은 점유를 관찰하는 실험
const started = Date.now();
setTimeout(() => {
  console.log("timer after", Date.now() - started);
}, 0);
while (Date.now() - started < 50) {
  // 교육용으로 현재 스레드를 점유한다.
}
console.log("work done");
```

먼저 `work done`이 출력되고 나중에 `timer after`와 대략 50ms 이상의 경과 시간이 출력된다. 정확한 숫자는 실행 환경과 시계 해상도에 따라 달라진다. 호스트에서 시간 조건이 충족되어도 현재 코드가 계속 실행 중이면 타이머 후속 코드가 끼어들지 못한다.

브라우저의 같은 메인 실행 자원을 사용하는 입력 처리와 화면 갱신도 긴 코드의 영향을 받을 수 있다. 실서비스에서 이처럼 바쁘게 기다리는 반복문으로 시간을 지연시키면 안 된다. 타이머는 대기를 등록하고 제어를 돌려주기 위한 도구다.

### 긴 작업을 뒤로 미루는 것과 잘게 나누는 것

무거운 함수를 setTimeout으로 한 번 감싸면 시작 시점은 나중으로 이동하지만 그 함수가 실행되는 동안의 긴 점유는 그대로다. 작은 단위로 나누고 작업 사이에 제어를 돌려주는 설계와 다르다.

작업을 나누면 한 번의 점유는 줄어들 수 있으나 전체 처리 비용과 중간 상태 관리가 추가된다. 중간 결과를 다른 코드가 읽어도 되는지, 취소 시 어디까지 처리됐는지 등도 필요할 수 있다. 단순히 타이머 횟수를 늘리는 것을 보편적인 성능 해결책으로 삼지 않는다.

측정에서도 총 완료 시간과 입력을 처리하지 못한 가장 긴 구간을 따로 본다. 전체가 조금 오래 걸려도 긴 점유를 줄여 사용자 반응이 좋아질 수 있고, 반대로 총 시간이 짧아도 한 번에 몰아 계산하면 눈에 띄게 멈출 수 있다.

## 7. 타이머와 렌더링의 보장 범위

`setTimeout(fn, 100)`은 정확히 100ms에 실행한다는 예약이 아니다. 최소 지연 조건, 중첩 타이머 제한, 백그라운드 상태, 다른 실행 부하 등이 영향을 줄 수 있다. 시간 측정에서는 등록 시점과 실행 시점을 따로 기록한다.

작업 하나가 끝날 때마다 반드시 화면을 그리는 것도 아니다. 브라우저는 렌더링 기회와 문서 상태 등을 고려한다. 스타일을 바꾼 직후 타이머를 등록했다고 그 사이 특정 화면이 사용자에게 보였다고 단정할 수 없다. 화면 갱신 API의 세부 사용은 Track B의 브라우저 스케줄링 범위다.

### 렌더링 기회는 setTimeout의 반환 계약이 아니다

스타일 변경 뒤 0ms 타이머를 등록해도 그 사이 브라우저가 꼭 프레임을 표시한다는 보장은 없다. 타이머의 역할은 후속 작업 예약이고 렌더링은 브라우저의 별도 판단과 처리 단계다. 둘을 같은 계약으로 묶으면 로딩 표시가 실제로 보이기 전에 긴 계산을 시작할 수 있다.

타이머 지연은 요청한 시간뿐 아니라 중첩 제한·문서 활성 상태·실행 부하 등의 영향을 받는다. 시간 임계값이 지났다는 사실과 JavaScript 진입이 가능한 시점을 구분한다. 세부 화면 갱신 API 선택은 Track B의 requestAnimationFrame·브라우저 스케줄링 학습에 연결한다.

## 8. `Node.js와의` 경계

`Node.js도` 이벤트 루프를 사용하지만 브라우저의 화면 렌더링 모델을 그대로 적용하지 않는다. 타이머·I/O·즉시 실행 후속 처리 등에 단계가 있고 `process.nextTick` 같은 고유 기능도 있다. `Node.js의` 단계별 순서를 브라우저 설명에 섞으면 잘못된 예측이 생긴다.

**[미리보기: Node.js 런타임]** `setImmediate`·`process.nextTick`·libuv 단계와 버전별 타이머 변화는 Track A의 7–9주 `Node.js에서` 다룬다. 여기서는 브라우저와 같은 모델이라고 단정하지 않는 수준으로 구분한다.

### 같은 출력 결과가 같은 런타임 구조를 뜻하지 않는다

간단한 동기 출력과 타이머 예제는 브라우저와 `Node.js에서` 같은 순서로 보일 수 있다. 그렇다고 입력·렌더링·파일 I/O·전용 예약 API까지 같은 처리 단계를 사용한다는 증거는 아니다. 공통 예제에서 확인한 계약만 공통으로 적용한다.

환경이 섞인 자료를 읽을 때는 예제의 실행 위치와 Node 버전·ESM/CJS 여부를 기록한다. 특히 Node 전용 API의 순서를 브라우저의 일반 task·microtask 표에 그대로 추가하지 않는다. 환경 차이를 제거한 최소 예제와 환경 고유 예제를 따로 실행하는 것이 진단에 유리하다.

## 9. 흔한 오해·예외·주의점

- **이벤트 루프가 JavaScript를 병렬로 실행한다**: 준비된 실행을 조정하는 것과 여러 스레드의 병렬 계산은 다르다.
- **0ms면 즉시 실행한다**: 현재 동기 구간은 이어진다.
- **외부 작업 완료면 후속 코드도 이미 실행됐다**: 준비 시점과 실행 시점은 다르다.
- **큐가 비면 무조건 렌더링한다**: 호스트의 렌더링 기회 판단이 있다.

### 큐가 준비됐다는 말의 범위를 제한한다

큐에 작업이 있다는 사실만으로 즉시 그 작업을 실행할 수 있다고 결론 내리지 않는다. 현재 평가, 실행 가능 문서 조건, 체크포인트, 다른 작업 선택 등의 단계가 있다. 반대로 스택이 비었다는 사실이 외부 대기까지 끝났다는 뜻도 아니다.

이벤트 루프를 모든 문제의 원인으로 삼는 것도 피한다. 잘못된 함수 참조를 전달했거나 입력 데이터가 틀린 문제는 스케줄링을 설명해도 해결되지 않는다. 등록·준비·실행의 각 시점에서 실제 값과 호출 대상을 확인한다.

## 10. 실무 적용과 디버깅 관점

지연을 조사할 때 요청·타이머의 준비 시간과 JavaScript 진입 시간, 그 앞의 긴 작업을 함께 본다. 브라우저 Performance 기록에서 메인 스레드의 긴 실행 구간을 확인한다. 전체 시간이 긴 원인이 네트워크 대기인지 후속 코드 실행 지연인지 나누어야 조치도 달라진다.

### 지연을 구간별로 기록하는 사례

버튼을 누른 뒤 결과 표시가 늦었다면 입력 발생, 처리 함수 진입, 외부 요청 시작·완료, 결과 처리 시작·끝을 분리한다. 입력 발생과 함수 진입 사이가 길면 앞의 실행 부하를, 요청 대기가 길면 외부 통신을, 처리 시작 이후가 길면 계산·렌더링 관련 작업을 조사한다.

브라우저 Performance 기록은 이런 실행 구간과 프레임 처리의 상관관계를 보는 도구다. 한 번의 console 출력 순서만으로 실제 렌더링 시점을 단정하지 않는다. 순서 예측을 위한 작은 실험과 사용자 체감 지연을 위한 프로파일링을 각각의 질문에 맞게 사용한다.

### 통합 사례: 타이머가 늦는 이유를 시간 구간으로 분리한다

0ms 타이머가 늦었다는 현상만으로 호스트의 타이머 구현이 잘못됐다고 판단할 수 없다. 등록 시각, 현재 동기 작업의 종료 시각, 실제 콜백 진입 시각을 나누어 본다.

```text
0ms     타이머 등록
0~50ms  현재 JavaScript가 동기 계산
50ms    현재 스크립트의 계산 종료
그 이후 타이머 콜백 진입 가능
```

타이머의 최소 지연 조건은 앞쪽에서 이미 충족될 수 있지만 같은 실행 흐름이 계속 점유 중이면 후속 JavaScript가 실행되지 못한다. 따라서 타이머 진입까지의 총 경과 시간을 곧 타이머 대기 시간으로 읽으면 현재 동기 부하를 외부 지연으로 오해한다.

진단에서는 먼저 긴 동기 계산을 제거한 최소 예제와 원래 기능을 비교한다. 그다음 긴 계산을 나중 작업 하나로 옮겼을 때는 멈추는 시점만 이동하는지, 작은 단위로 분리했을 때는 실행 기회가 생기는지 관찰한다. 어떤 실행 기회가 생기는지는 선택한 호스트 예약 API의 계약에 따라 달라진다.

이 문서가 보장하는 것은 특정 밀리초 값이나 프레임 수가 아니라 현재 코드의 종료와 다른 작업의 진입 사이의 제약이다. 실제 사용자 응답성을 판단하려면 이 순서 모델에 Performance 기록의 실행 구간을 함께 연결한다.

## 11. 핵심 정리

이벤트 루프는 호스트의 준비된 작업과 JavaScript 실행을 연결한다. 현재 동기 실행은 다른 작업이 임의로 끊지 않으며, 준비된 타이머도 실행 기회를 기다린다. 브라우저의 렌더링과 `Node.js의` 단계는 환경을 구분해서 배운다.
